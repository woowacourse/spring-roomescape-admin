##### 미션 안내사항과 힌트

레이어별 책임과 역할에 따라 클래스를 분리하고, 분리한 클래스를 **Spring Bean으로 등록**한다.

| 레이어                  | 책임       |
| -------------------- | -------- |
| **Controller**       | 웹 요청·응답  |
| **Service**          | 비즈니스 플로우 |
| **DAO (Repository)** | DB 접근    |
| **Domain**           | 비즈니스 규칙  |

- `ReservationController`에 `JdbcTemplate` 필드가 **남아있지 않아야** 한다

- 컨트롤러는 웹 요청/응답 책임만 가지도록 수정한다.
- DB 접근 책임은 DAO(Data Access Object)에 위임한다.
- 비즈니스 플로우 책임은 서비스에 위임한다.
- 비즈니스 규칙 책임은 도메인에 위임한다.

- 분리한 클래스를 빈으로 등록할 때 `@Component` · `@Service` · `@Repository` 등을 활용할 수 있다. 매번 새로운 인스턴스를 만들지 않고 **스프링 컨테이너가 관리**하도록 설정한다.

---

기존 `ReservationController`에 뭉쳐있던 로직을 `Controller` -> `Service` -> `DAO`로 분리하고, 이들의 의존성을 생성자 주입으로 연결했다.

변경이 있을 때 변경의 이유가 있을 때 관련 있는 책임들이 응집되도록 하고 의존관계 주입을 하여 결합도를 낮추는 것이라고 생각하고 진행했다.

이 과정에서 인터페이스를 주입해야 하지 않는가?에 대해서 고민을 했다.
인터페이스 없이 구체 클래스만으로 3계층을 분리하기로 했다.
그 이유는 단일 구현체만 존재하는 상황에서의 인터페이스 도입은 오버엔지니어링이라고 느껴졌기 때문이다.

### 4. AI 피드백

#### 자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고, 유용했던 제안 1가지 이상 기록

- **스프링 철학의 진화와 실용주의**: 토비의 스프링 초반부처럼 수동 빈 팩토리와 인터페이스를 억지로 짜지 않아도, 현대 스프링 부트는 어노테이션(`@Component` 등) 하나로 싱글톤 레지스트리와 DI를 완벽하게 대행해준다는 통찰. 구현체가 명백히 1개라면 굳이 인터페이스를 추출하지 않는 실무적 관례를 배워 불필요한 고민을 덜어냈다.
- **DTO(Record) 도입의 아키텍처적 이점**: `Map` 대신 DTO를 쓰면 클라이언트와의 API 스펙(계약)이 코드로 강제되며, `toEntity()`를 통해 조립 책임을 DTO 스스로 지게 만드는 것이 훨씬 더 객체지향적이라는 피드백이 유용했다.
- **도메인 책임 분리의 중요성**: 컨트롤러 하나에 `/reservations`와 `/times`를 섞지 않고 별도의 계층으로 분리해야만 SRP에 부합하며 향후 도메인 확장 시 안전하다는 조언.
