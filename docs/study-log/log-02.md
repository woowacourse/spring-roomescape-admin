### 2. 이번 타임의 학습 전략
- 이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?
  - 흐름 스케치할 때 데이터가 어떻게 변환되는지까지 그려보자. 요청 JSON → 객체 변환 → id 부여 → 저장 → 응답 처럼 데이터 흐름을 같이 그리면 @RequestBody id 문제 같은 걸 미리 잡을 수 있다.
  - 찜찜한 부분을 다음 타임 시작 전 10분 안에 짧게 정리하고 시작하자. 찜찜한 채로 넘어가면 다음 단계에서 같은 곳에서 또 막힌다.

- 실제로 어떻게 학습했는지 디테일한 과정을 써보세요.
```angular2html
1. 흐름 스케치로 요청 → Controller → Repository → JdbcTemplate → DB 구조를 잡았다.
2. 핵심 키워드(JdbcTemplate, RowMapper, KeyHolder)를 AI로 먼저 정리하고 코드를 작성했다.
3. 막힌 지점들
   - Jackson 기본 생성자 누락 → Cannot construct instance 에러
   - @PathVariable 파라미터 이름 미지정 → @PathVariable("id")로 해결
   - @ResponseBody 누락으로 DELETE 404
   - ResponseEntity.ok().build() 의미를 몰랐음
4. 단위 테스트를 작성하려다 JdbcTemplate 없이는 불가능하다는 걸 깨달았고,
   Repository를 인터페이스로 분리하면 가능하지만 지금 구조에선 의미가 적다고 판단해 통합 테스트로 대체했다.

해당 내용에 대해 미션 정리 문서를 작성하였다.
```

### 3. 전략 평가
- 효과적이었던 것과 그 이유
  - 흐름 스케치에 데이터 흐름을 추가한 것. @RequestBody로 받은 id가 null이라는 점을 코드 작성 전에 인식하고 있어서 KeyHolder를 미리 찾아볼 수 있었다.
  - 오류 메시지를 먼저 읽고 한 줄로 정리한 뒤 검색하는 방식. Cannot construct instance, Name for argument not specified 같은 메시지를 키워드로 바로 검색하니 빠르게 해결됐다.

- 비효과적이었던 것과 그 이유
  - 이전 타임의 찜찜한 부분(ResponseEntity)을 해결하지 않고 시작했다. 결국 이번 타임에도 같은 지점에서 막혔다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
  - "개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다"에 체크한 게 실제 막힌 지점과 일치했다. 키워드 중심 학습 + AI/공식문서 교차 검증 방식과 잘 맞았다.

### 4. AI 피드백
- 자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고,
  유용했던 제안 1가지 이상 기록
  > 이전 타임의 찜찜한 부분을 해결하지 않고 시작하는 패턴이 반복되고 있다.
  >
  > ResponseEntity가 찜찜한 채로 넘어갔고, 이번 타임에도 같은 지점에서 막혔다. 찜찜한 부분을 적는 것만으로는 부족하고, 다음 타임 시작 전에 반드시 해결했는지 체크하는 장치가 필요하다. 학습 로그 맨 위에 "이전 찜찜함 해결 여부: O/X"를 한 줄 추가하는 것만으로도 넘어가는 걸 막을 수 있다.
