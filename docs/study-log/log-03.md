### 2. 이번 타임의 학습 전략

"핵심/부가 깊이 차등화 + 비교 가능한 시점에 묶어 정리" 전략을 적용했다.
3단계는 Reservation 도메인을 만들 때와 거의 동일한 패턴으로 `reservation_time` 도메인을 추가하는 흐름이었기에 수월하게 할 수 있었고, 모르는 부분은 AI와의 즉문즉답으로 빠르게 쳐냈다.

### 3. 전략 평가
- 효과적이었던 것
  - 전단계에서 학습을 꼼꼼하게 해서 수월하게 할 수 있었다.
- 비효과적이었던 것
  - 아는 내용이라 급하게 코드를 짜다 보니 JSON 필드명이 어긋나 시간을 낭비했다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
  - "개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다"에 해당하는 막힘이라, AI 즉문즉답이 잘 맞았다. 
    다만 익숙해진 영역은 필드명 불일치 등의 코드를 읽지 않으면 해결할 수 없는 문제들이 발생했다.

### 4. AI 피드백

"익숙한 단계일수록 '구현 시작 전 30초 스케치'를 의식적으로 끼워 넣어라." → 이번 JSON 필드명 오류처럼 익숙해서 건너뛴 검증이 오류를 불러올 수 있다.

### 5. 다음 타임에 바꿀 것
- 유지할 것
  - **핵심/부가 깊이 차등화**: 이번 타임에 시간 분배가 균형 잡혔다.
  - **이전 단계에서 정리한 패턴 재사용**: 같은 패턴은 다시 학습하지 않고 본질적인 결정(연관관계 모델링, 조회 책임 위치)에 시간을 쓸 수 있었다.
- 바꿀 것
  - **익숙한 영역에서도 "30초 스케치" 끼워 넣기**: 요청 JSON → DTO → 도메인 → DB 컬럼을 한 줄로 미리 적어둔다. 이번 JSON 필드명 오류처럼 익숙해서 건너뛴 검증이 침묵 오류로 돌아오지 않도록.


### 6. 단계 전환 체크

2단계의 "정리하며 학습하기" 전략에 "핵심/부가 깊이 차등화"를 얹은 것이 이번 단계에서 가장 잘 작동했다. 
익숙한 패턴은 그대로 재사용하고 새로 결정해야 하는 부분에만 시간을 몰아준 결과, 같은 시간에 더 본질적인 결정을 내릴 수 있었다. 이 방식은 다음 단계에서도 유지한다.

다만 이번 단계에서 새로 드러난 한계는 "익숙해진 영역의 침묵 오류"다. JSON 필드명 불일치처럼 컴파일도 통과하고 요청도 성공하는 오류는 AI 즉답 학습으로는 잡히지 않고, 본인이 코드를 다시 읽어야만 발견된다. 
따라서 다음 타임에는 AI 즉답을 그대로 들고 가되, 그 위에 "구현 시작 전 스케치"와 "토론을 통한 설계 검증"을 추가한다.
