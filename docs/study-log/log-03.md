### 2. 이번 타임의 학습 전략

이번에는 새로운 개념을 처음부터 깊게 공부하기보다, 테스트와 에러 메시지를 기준으로 문제를 좁혀가는 방식으로 학습했다.
코드를 구현하고 실행하다가 에러가 발생하면 아래 순서로 학습하였다.

1. 에러 메시지를 먼저 읽는다.
2. 내가 생각한 원인 후보를 세운다.
3. 코드에서 원인 후보를 확인한다.
4. 혼자 판단이 어렵다면 검색한다.
5. 그래도 막히면 AI에게 원인 분석을 요청한다.

### 3. 전략 평가

- 효과적이었던 것과 그 이유
    - 에러 메시지를 먼저 읽는 방식은 효과적이었다. 에러 안에 원인에 가까운 단서가 들어 있는 경우가 많았고, 무작정 코드를 바꾸는 시간을 줄일 수 있었다.
    - 검색 전에 원인 후보를 먼저 세운 점이 도움이 되었다. 검색 결과를 그대로 받아들이는 것이 아니라, 내 상황과 맞는지 비교하면서 볼 수 있었다.
    - AI를 마지막 단계에서 사용한 것도 효과적이었다. 스스로 파악한 흐름을 바탕으로 질문하니, AI 답변을 맹목적으로 따라가기보다 검증하면서 활용할 수 있었다.

- 비효과적이었던 것과 그 이유
    - 처음에는 에러가 발생한 위치를 계층별로 나누어 보지 못했다. DB 문제인지, 요청 매핑 문제인지, Repository 문제인지 구분하지 못해 시간을 더 사용했다.
    - 원인 후보를 세우긴 했지만, 그 후보를 검증하는 순서가 명확하지 않았다. 그래서 같은 코드를 여러 번 왔다 갔다 하며 확인했다.
    - 기술 블로그를 볼 때 아직 필요한 부분만 빠르게 골라보는 데 익숙하지 않았다. 이전보다는 나아졌지만, 여전히 글의 흐름을 오래 따라가는 경향이 있었다.

- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
    - 이번 어려움은 "모르는 개념을 공부하는 문제"라기보다 "에러를 보고 원인을 찾아가는 문제"에 가까웠다. 그래서 공식문서를 처음부터 읽는 방식보다, 에러 메시지와 테스트 흐름을 기준으로
      역추적하는 방식이 더 잘 맞았다.
    - 다만 요청 바디 매핑처럼 배경지식이 부족한 부분은 에러 메시지만으로는 한계가 있었다. 이 경우 검색과 AI를 함께 사용하는 것이 필요했다.

### 4. AI 피드백

- 에러를 보면 바로 해결책을 찾기보다, 먼저 에러를 분류한다.
    - SQL 에러인지
    - JSON 매핑 에러인지
    - 조회 결과가 없는 에러인지
    - 테스트 기대값과 실제 응답이 다른 에러인지
- 질문할 때는 "왜 안 돼?"가 아니라 "이 요청이 들어왔을 때 어느 값이 null이 될 수 있는가?", "이 SQL 에러가 발생하려면 어떤 조건이 필요한가?"처럼 검증 가능한 질문으로 바꾼다.
- AI 답변은 최종 답이 아니라 원인 후보 중 하나로 본다. 답변을 받은 뒤에는 반드시 에러 메시지, 테스트, 코드 흐름으로 다시 확인한다.

### 5. 다음 타임에 바꿀 것

- 유지할 것과 그 이유
    - 에러 메시지를 먼저 읽고 원인 후보를 세우는 방식은 유지한다. 문제를 스스로 해석하는 데 도움이 되었기 때문이다.
    - 스스로 파악이 어렵다면 검색, AI 순서로 활용하는 방식도 유지한다. 바로 AI를 사용했을 때보다 내가 이해한 상태에서 답변을 검증하기 쉬웠다.

- 바꿀 것과 그 이유
    - 에러가 발생하면 먼저 계층을 분류한다. DB, 요청 매핑, Controller, Repository, 테스트 기대값 중 어디에 가까운 문제인지 나누고 확인한다.
    - 원인 후보를 세운 뒤에는 검증 순서를 정한다. 가장 가능성이 높은 것부터 하나씩 확인해 같은 코드를 반복해서 보는 시간을 줄인다.
    - 기술 블로그를 볼 때는 처음부터 끝까지 읽지 않고, 지금 막힌 문제와 직접 관련 있는 부분만 먼저 확인한다.
    - AI에게 질문하기 전에 내가 세운 가설을 함께 적는다. 그래야 AI 답변이 내 가설을 강화하는지, 반박하는지 판단할 수 있다.
