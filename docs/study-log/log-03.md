## 학습 로그 #3

**시간**: 4/30 02:00 ~ 05:00 (약 180분)
**학습 범위**: 3단계 시간 관리

### 1. 막힌 것의 종류
이번에 막힌 것은 어떤 종류의 어려움이었는가? (해당하는 것에 체크)
- [ ] 개념 자체를 모르겠다 (예: "스프링 빈이 뭔지 모르겠다")
- [ ] 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 (예: "JdbcTemplate 문법을 모르겠다")
- [ ] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [x] 이전의 JPA 방식에 익숙해져, 연관관계를 직접 쿼리 조회하는 것이 낯설게 느껴지고 어렵게 느껴졌다.

### 2. 이번 타임의 학습 전략
- 이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?
  - 학습할 내용에 대해 일정 주기로 꺼내보고 한번쯤 심도있는 학습을 진행하는 것과 직접 구현하는 것을 목표로 삼았다. 따라서 연관관계 매핑을 위해 직접 코드를 작성해보는 것부터 시도하였다.
- 실제로 어떻게 학습했는지 디테일한 과정을 써보세요.
  - save 메서드의 경우, Time을 Reservation에 앞서 먼저 조회해 온 이후에 이를 저장하는 것을 목표로 삼고 직접 구현해보았다. 실제 연관관계가 어떻게 매핑되는지 구상해본 이후 시도한 내 나름대로의 시도였고, 이를 AI에게 자문을 받아 적절한 구현인지 되물어보는 학습법을 선택하였다.

### 3. 전략 평가
- 효과적이었던 것과 그 이유
  - 직접 연관관계를 JPA가 어떻게 구현했는지를 역으로 생각해본 계기였다. 솔직히 JPA를 사용할 때는 연관관계 매핑 어노테이션을 사용해서, 내부적으로 어떻게 쿼리가 날라가는지, 조회 혹은 생성되는지를 생각해본 경험이 없었는데, 이번 기회에 이를 의식적으로 시도하려고 노력했다고 생각한다.
- 비효과적이었던 것과 그 이유
  - 사실 모든 메서드들을 다 최선의 선택인지 자문하고 돌려보는 것 또한 앞서 경계한 완벽주의라고 생각이 들었다. 결국 내가 고민지점이 느껴져야 이를 자문하는 형태로 진행하는 것이 더 건강하다는 생각이 들었다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
  - 직접 시도함으로써 내부 구현도 한번 고민해보게 되었고, 직접 쿼리를 작성하는 과정에서 어떻게 데이터베이스의 타입이 어플리케이션 타입과 매핑되는지도 고민해볼 수 있는 경험이었다.

### 4. AI 피드백
- 자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고,
  유용했던 제안 1가지 이상 기록
  - 직접 구현을 통해 JPA의 내부 동작을 역으로 이해하려는 시도는 효과적인 학습 방식이라고 피드백을 받았다. 특히 추상화된 도구에 익숙해진 상태에서 이를 벗어나 로우 레벨로 내려가 보는 경험은 이해도를 높이는 데 큰 도움이 된다는 점을 긍정적으로 평가받았다.
    - 다만, 모든 선택에 대해 검증을 시도하기보다 스스로 의문이 드는 지점에 집중해서 깊게 파고드는 것이 더 효율적이라는 피드백을 받았다.
  - 유용했던 제안:
    - 모든 코드를 검증하려 하기보다 스스로 이상하다고 느껴지는 지점에 집중해 깊이 있게 탐색하는 방식이 더 좋을 것 같다는 부분이 인상 깊었다.
    
### 5. 다음 타임에 바꿀 것
- 유지할 것과 그 이유
  - 추상화된 기술에 대한 이해도를 높이는 데 도움이 되었기 때문에, 직접 구현을 통해 내부 동작을 이해하려는 방식은 유지할 예정이다. 
- 바꿀 것과 그 이유
  - 불필요한 완벽주의를 줄이고 학습 효율을 높이기 위해, 모든 선택을 검증하려 하기보다 의문이 드는 지점에 집중해 탐색하는 방식으로 수정할 계획이다.
