스프링 프레임워크의 모듈 중에는 웹 계층을 담당하는 몇 가지 모듈이 있다.
웹 계층에 서블릿(Servlet) API를 기반으로 클라이언트의 요청을 처리하는 모듈이 있는데 이를 스프링 웹 MVC(spring-web-mvc) 또는 스프링 MVC라고 한다.
Spring MVC는 클라이언트의 요청을 편리하게 해주는 기능을 제공한다.

### 서블릿(Servlet)이란?
서블릿은 클라이언트의 요청을 처리하도록 특정 규약에 맞춰 Java 코드로 작성하는 클래스 파일이다.
아파치 톰캣(Apache Tomcat)은 이러한 서블릿들이 웹 애플리케이션으로 실행할 수 있도록 해주는 서블릿 컨테이너(Servlet Container) 중 하나이다.
Spring MVC 내부에서는 서블릿을 기반으로 웹 애플리케이션을 동작하며, 스프링 부트는 기본적으로 아파치 톰캣이 내장되어 있다.

> 솔직히 서블릿을 말 했는데 잘 이해되지 않아
> 서블릿은 요청을 처리하는 자바 프로그램이고, 톰캣은 서블릿을 실행해주는 서버, 스프링은 서블릿을 쉽게 쓰게 해주는 도구임
>  ![[Pasted image 20260428140859.png]]
> 이러한 방식으로 서블릿을 만들어서 보내야 했는데, 스프링에서는
> ![[Pasted image 20260428140932.png]]
> 이렇게 처리하고 끝이란거 같음
> 
> 원래는 서블릿 코드를 다 작성해서 해야하는데 스프링에서는 @GetMapping 만 하면 되도록 축약 된거겠네?
> 맞는 말이긴 한데, 단순 축약이 아니라 역할 분리와 자동화임.
> 
> 원래는 서블릿이 요청 파싱/URL 판단/로직 실행/응답 생성 다 했는데, 스프링은 URL 매핑, 로직, 응답 데터만 보내주면 서블릿이 알아서 처리해주는거겠네?
> 스프링 + 서블릿이 실행하는 거임
> 
> 약간 어찌 보면 @GetMapping을 하면 그 사이에 서블릿 코드가 자동적으로 생긴다는거네? 그걸 우리는 안만들어도 되는거고?
> 아 생기는게 아니라 원래 서블릿은 존재하고 디스패쳐서블릿에 등록되는 거임.
> 그니까 즉, @GetMapping("/hello")라고 하면 "이 URL 오면 이 메서드 써" 라는 규칙이 등록이 되는거임

> 
> 아 원래는 스프링이 없으면 아파치 톰캣을 실행시키고, 서블릿 코드를 실행시켜야했는데 스프링은 내제되어있는거임?
> 스프링에 내장되어 있는게 아니라 스프링 부트에 내장 되어있는 거고, 스프링에서는 원래 코드를 작성하고 WAR 파일을 톰캣에 배포해야되는 과정이 있었는데 현재는 스프링 부트가 한번에 해버렸다는거네? 굿굿

## MVC란?
MVC 패턴은 애플리케이션을 개발할 때 사용하는 디자인 패턴이다.
애플리케이션의 개발 영역을 MVC(Model, View, Controller)로 구분하여 각 역할에 맞게 코드를 작성하는 개발 방식이다.
MVC 패턴을 도입하면서 UI 영역과 도메인(비즈니스 로직) 영역으로 구분되어 서로에게 영향을 주지 않으면서 개발과 유지보수를 가능하게 되었다.

**Model(모델)**
Spring MVC 기반의 웹 애플리케이션이 클라이언트의 요청을 전달받으면 요청 사항을 처리하기 위한 작업을 한다.
처리한 작업의 결과 데이터를 클라이언트에게 응답을 돌려주어야 하는데, 이때 클라이언트에게 응답으로 돌려주는 **작업의 처리 결과 데이터를 Model**이라 한다.
클라이언트의 요청 사항을 구체적으로 처리하는 영역을 서비스 계층(Service layer)라고 하며, 요청 사항을 처리하기 위해 Java 코드로 구현한 것을 비즈니스 로직(Business Logic)이라 한다.

> 모델에서는 비즈니스 로직을 처리하지 않는건가?
> Model에서는 자기 상태를 지키는 최소한의 로직만 포함함(예: 값 검증, 상태 변경 규칙), 서비스는 여러 Model을 조합해서 "비즈니스 흐름"처리
> 그니까 즉 Model과 Service 차이점은 모델은 자기 자신만 서비스는 여러 모델을 사용해서 겪는 시나리오임.

**View(뷰)**
View는 Model을 이용하여 웹 브라우저와 같은 애플리케이션의 화면에 보이는 리소스(Resource)를 제공하는 역할을 한다.
Spring MVC에는 다양한 View 기술이 포함되어 있다.
- HTML 페이지 출력
- PDF, Excel 등의 문서 형태로 출력
- XML, JSON 등 특정 형식의 포맷으로 변환

> 그러면 뷰는 결과값을 담고 보내는 친구만 담당하는건가?
> View는 데이터를 화면으로 표현하는 역할만 함.

> 내가 이전에 사이드 프로젝트 할 때에는 View 계층이 명확하지 않았는데, DTO가 View 인건가?
> 컨트롤러와 뷰 사이에서 데이터를 전달하는 객체일 뿐임. 단순하게 전달용 객체라는 뜻 임.

**Controller(컨트롤러)**
컨트롤러는 클라이언트 측의 요청을 직접적으로 전달받는 엔드포인트(Endpoint)로써 Model과 View의 중간에서 상호작용을 해주는 역할을 한다.
클라이언트 측의 요청을 전달받아 비즈니스 로직을 거친 후, Model 데이터가 만들어지면, 이 Model 데이터를 View로 전달하는 역할을 한다.

**MVC 패턴의 구조**
MVC 패턴에서도 여러 가지 구조를 가진다.
![[Pasted image 20260428135448.png]]

여러 가지 구조를 가진 MVC 패턴 중 위 그림의 구조를 그대로 사용하고 있는 것이 Spring MVC이다.
일반 MVC 패턴도 유지보수하기에 좋은 패턴임은 확실하나, 구조가 복잡해지는 한계가 있다.
이러한 한계를 극복하게 해주는 것이 Spring MVC이다.

### **Spring MVC의 동작 방식과 구성 요소**
![[Pasted image 20260428135613.png]]

**DispatcherServlet**
DispatcherServlet은 HttpServlet을 상속받아 사용하고, 서블릿으로 동작한다.

- DispatcherServlet → FrameworkServlet → HttpServletBean → HttpServlet
	DispacherServlet을 사용하면 서블릿으로 등록하면서 모든 경로에 (urlPatterns=”/”)에 대해 매핑한다.

> 솔직히 하나도 이해 안됨 ㅋㅋㅋ, 서블릿은 알겠는데
> 모든 HTTP 요청을 한 곳에서 받아서, 알맞은 Controller로 보내주는 중앙라우터임.
> 
> 하나로 모으는 장점이 뭐지?
> 공통 처리 + 일관된 흐름 + 유지보수 용이성의 장점이 있음
> 
> 인증 체크, 로그 기록, 예외 핸들링을 한다는데 이건 어케 하는거임? 
> DispatcherServlet 앞/주변에 **필터·인터셉터·예외 핸들러를 붙여서 공통 로직을 한 번에 처리**한다.
> 
> 이 3개는 내가 구현안해도 이미 되어있는건가?
> 인증은 기본이 없고, Spring Security 쓰거나 직접 구현해야하고,
> 로그는 기본 로그는 있으나, 상세 요청 로그는 직접 구현해야하고,
> 예외 처리는 기본 에러 응답이 있으나, 커스터마이징은 직접 해야함.
> 
> global 패키지에 전역 예외처리 이런거 다 커스터마이징하잖아, 디스패처 서블릿이 쓰는건가...?
> ㄴㄴ 
> 요청이 오면
 → DispatcherServlet
 → Controller
 → 예외 발생
 → global.exception.GlobalExceptionHandler 실행
 → 공통 에러 응답 반환
 >
 >디스패쳐서블릿은 HTTP 요청이 들어오면 각 @RestController를 등록하면 여기서 알맞게 보내개 하는건가?
```
[스프링 시작 시]
"/user" → UserController.getUser 등록됨
	[요청 시]
	GET /user
	 → DispatcherServlet
	 → HandlerMapping 조회
	 → UserController.getUser 실행
```
 >
 >그러면 디스패처서블릿은 즉 톰캣인건가?
 > 아니다, 톰캣 안에서 실행되는 하나의 서블릿일 뿐임.
 > 
 > 스프링 부트를 하면 아파치 톰캣에서 항상 디스패쳐 서블릿으로만 보내는건가?
 > 기본 설정에선 **대부분 요청을 DispatcherServlet으로 보내지만, “항상”은 아니다. (다른 서블릿/정적 리소스는 제외)**
 
**요청 흐름**
- 서블릿이 호출되면 HttpServlet이 제공하는 service()가 호출된다.
- 스프링 MVC는 FramworkServlet.service()를 시작으로 여러 메서드가 호출되면서 **DispacherServlet.doDispatch()**가 최종적으로 호출된다.

**동작 순서**
1. 핸들러 조회 : 핸들러 매핑을 통해 URL에 매핑된 핸들러(컨트롤러)를 조회한다.
2. 핸들러 어댑터 조회 : 핸들러를 실행할 수 있는 핸들러 어댑터를 조회한다.
3. 핸들러 어댑터 실행 : 핸들러 어댑터를 실행한다.
4. 핸들러 실행 : 핸들러 어댑터가 실제 핸들러를 실행한다.
5. ModelAndView 반환 : 핸들러 어댑터는 핸들러가 반환하는 정보를 ModelAndView로 변환하여 반환한다.
6. viewResolver 호출 : 뷰 리졸버를 찾고 실행한다.
7. View 반환 : 뷰 리졸버는 뷰의 논리 이름을 물리 이름으로 바꾸고, 렌더링 역할을 담당하는 뷰 객체를 반환한다.
8. 뷰 렌더링 : 뷰를 통해 뷰를 렌더링한다.

> 핸들러 매핑이 뭐지?
> 요청 URL -> 실행할 Controller 메서드를 찾아주는 매핑 테이블임.
> 
> 그러면 디서패처서블릿에 등록된 컨트롤러들에서 핸들러매핑을 해서 어디 컨트롤러에가야할지 찾고 거기서 어떤 요청을 했는지 매핑하고 실행하고 반환하는건가?
> 컨트롤러가 디스패처서블릿에 등록되는 것이 아니라 핸들러 매핑이 매핑 정보를 관리한다는데, 그니까 즉 스프링이 시작할 때, @RestController, @GetMapping 같은 어노테이션을 스캔해서 매핑 정보에 저장하고 DispatcherServlet에서 요청을 받으면 DispatcherServlet이 HandlerMapping한테 이 URL 누군지 물어보고 요청을 저기로 보내는거네?
> 
> DispatcherServlet이 직접 보내는게 아니라 즉 HandlerAdapter를 통해 실행하는거임.
>
> 그니까 즉 DispatcherServlet은 요청을 받고, HandlerMapping을 통해 등록되어있는지 찾고 목적지를 설정하면, HandlerAdapter가 그 컨트롤러를 실행시키고 결과값을 받고 오는건 이해했는데 결과를 반환해서 어떻게 보내주는데?
> 이제 그 결과는 HandlerAdapter -> DispatcherServlet -> (ViewResolver 또는 HttpMessageConverter)를 거쳐 HTTP 응답으로 변환함.
> 
> ViewResolver는 그러면 HTML/CSS/JS가 담겨서 보내지는거고 HttpMessageConverter같은 경우는 JSON 이런 응답 결과를 반환하는건가?
> View 이름 → 실제 템플릿 파일 찾고 → 서버에서 렌더링이고 **HttpMessageConverter** 객체를 JSON/XML로 변환
> 
> 핸들러 어댑터는 뭐고?
> 이미 공부했으니까 내가 답변을 하면, 핸들러 매핑을 해서 어디로갈지 목적지를 알면 이제 핸들러 어댑터가 목적지의 컨트롤러에게 알맞는 기능을 실행시키고 결과값을 받아오는 존재임.
> 
> 핸들러를 실행한다는 건 뭐지?
> 위에 말했듯이 핸들러를 실행한다는 것은 어댑터가 컨트롤러에 가서 알맞은 매핑에서 실행시키는게 실행한다는 건듯
> 
> 그런데 그냥 이전에 했던 내 프로젝트에서는 View가 없었었는데 필요 없는건가?
> → 맞다. **API 서버(@RestController)면 View는 필요 없다. JSON이 View 역할을 대신한다.**

**인터페이스 살펴보기**
스프링 MVC의 큰 장점은 DispatcherServlet 코드의 변경 없이 원하는 기능을 변경하거나 확장할 수 있다는 것이다. 동작에 필요한 대부분의 기능을 확장할 수 있도록 인터페이스로 제공한다.

따라서 인터페이스들만 구현하여 DispatcherServlet에 등록하면 원하는 기능의 컨트롤러를 만들 수도 있다.

주요 인터페이스
- 핸들러 매핑 : org.springframework.web.servlet.HandlerMapping
- 핸들러 어댑터: org.springframework.web.servlet.HandlerAdapter
- 뷰 리졸버: org.springframework.web.servlet.ViewResolver
- 뷰: org.springframework.web.servlet.View
