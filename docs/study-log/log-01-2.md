1-1 한 줄 정의 (Problem-Driven)
- 스프링 MVC는 정형화된 웹 어플리케이션을 좀 더 쉽게 하기 위해 만들어졌다.

1.2 흐름 스케치 (Structural Thinking)

- 흐름 : 요청 → ??? → Controller → 해당 내용 처리 → 응답
- 요청 (JSON body) → DispatcherServlet → Controller → 데이터 추가 → 추가된 데이터 반환
- 요청 (URL에 id) → DispatcherServlet → Controller → 데이터 삭제 → 200 응답
- 꼭 알아야 할 핵심 키워드
- `@PostMapping` : 해당 URL로 POST 요청이 오면 이 메서드가 처리한다고 선언하는 방법
- `@DeleteMapping` : 해당 URL로 DELETE 요청이 오면 이 메서드가 처리한다고 선언하는 방법
- `@RequestBody` : HTTP 요청의 JSON body를 자바 객체로 변환해준다. POST로 데이터를 받을 때 필수
- `@PathVariable` : URL 경로에서 값을 꺼낸다. DELETE `/reservations/{id}` 에서 `id`를 꺼낼 때 사용
- `ResponseEntity` : 응답 상태코드를 직접 지정할 수 있다. 단순히 객체를 반환하면 항상 200이다.

### 3. 전략 평가
- 효과적이었던 것과 그 이유
  - 흐름을 먼저 스케치하고 ???로 모르는 부분을 표시하는 방식. 
  - 이번에도 요청 → ??? → Controller → 처리 → 응답 구조를 먼저 잡으니 @PostMapping, @RequestBody, @PathVariable 같은 키워드를 어디에 끼워야 하는지 빠르게 찾을 수 있었다.
  - 막힌 종류를 지난 타임보다 정확하게 진단했다. "개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다"로 체크한 게 실제 막힌 지점과 일치했다.

- 비효과적이었던 것과 그 이유
  - @RequestBody로 받은 객체의 id가 null이 된다는 것, 즉 클라이언트가 보내는 데이터와 서버가 저장하는 데이터가 다르다는 점을 미리 생각하지 못했다. 흐름 스케치 단계에서 데이터가 어떻게 변환되는지까지 그려봤으면 더 빨리 해결됐을 것이다.
  - ResponseEntity와 상태코드에 대한 학습이 부족했다. 찜찜한 부분으로 남긴 건 좋은데, 다음 타임 전에 짧게라도 정리해두는 게 낫다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
  - 이번엔 진단과 전략의 궁합이 지난 타임보다 좋았다. "코드로 어떻게 쓰는지 모르겠다"는 키워드 중심 학습 + AI/공식문서 교차 검증 방식과 잘 맞았다.
