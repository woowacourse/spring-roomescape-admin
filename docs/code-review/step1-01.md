#### `@Repository` 어노테이션

우선 직관적으로 와닿은 Spring Repository 의 차이점은 `throws SQLException` 의 배제였습니다.  
이전 미션에선 Repository / DAO 의 모든 Connection 메서드에 throws 구문을 붙여야 했지만  
그것이 생략되었다는 것은 Spring 이 어떤 방식으로나마 예외를 처리(not Solve)해 주기 때문이라 생각했어요.

어노테이션의 Javadoc 내용을 활용해 학습해봤어요.

`번역`

- 이 어노테이션이 붙은 클래스는 도메인 주도 설계(DDD)에서 정의한  
  "저장, 조회, 검색 행위를 캡슐화하여 마치 객체 컬렉션처럼 동작하는 메커니즘"인 'Repository' 임을 나타냅니다.
- [X] 전통적인 J2EE 패턴인 'DAO(Data Access Object)'를 구현하는 팀들도  
  이 어노테이션을 사용할 수 있지만, 적용하기 전에  
  DAO와 DDD 스타일 Repository의 차이를 이해하는 것이 좋습니다.
- 이 어노테이션이 붙은 클래스는 PersistenceExceptionTranslationPostProcessor와 함께 사용될 때,  
  하부 데이터베이스의 원시 예외를 스프링의 범용적인 DataAccessException으로  
  자동 변환(Translation)해 주는 자격을 얻습니다.
- 또한, 이 어노테이션은 @Component의 특수한 형태이므로 클래스패스 스캔을 통해  
  스프링 컨테이너에 자동으로 빈(Bean)으로 등록됩니다.

생각했던 대로 `데이터베이스의 원시 예외를 범용직인 예외로 변환` 한다는 내용이 포함되어 있었습니다.  
또한,  
데이터베이스의 원시 예외는 사용하는 기술에 따라 다르기에 그것을 직접 던진다면  
서비스는 예외 처리에 데이터베이스의 종류에 의존하게 되고, 그것을 방지하기 위해  
`@Repository` 어노테이션이 예외를 변환해서 던져 주는 것임을 확인할 수 있었어요.

이런 계층간 의존/종속 제거에 [앞선 답변]() 내용이 포함된다 생각했어요.  
예외 처리 측면에서 예외를 포장해서 던짐으로써 하부 데이터베이스의 종류에 대한 종속을 제거하듯  
기능 구현 측면에서 저장소를 인터페이스로 추상화함으로써 동일한 종속 제거가 가능한 것이 아닐까요?

#### 정리

일단 여전히 셀프 검증과 디테일 체크가 부족함을 확인할 수 있었어요.  
처음에 클래스를 생성하며 자연스럽게 어노테이션을 붙이고

### 💬 Apply 03

#### DTO 를 활용한 계층 간 의존 제거

도메인 객체 저장 / 생성을 위한 정보를 모두 포함하고 있어 재사용했지만  
Request 객체를 만든 근본 목적인 레이어 간 구분을 파괴하는 재사용이었네요.

같은 정보를 전달하더라도 다른 계층 간 전송엔 다른 DTO 를 활용해야  
변경의 전파를 줄이고 의존을 끊어낼 수 있음을 숙지하겠습니다.  
DTO 를 패키지로 묶어 관리하기보다 각 계층에 두는 것도 import 문을 확인해서  
계층 간의 일방향 의존이 깨졌는지 확인할 수 있는 좋은 방법이겠네요!

#### 도메인 객체의 무결성에 대한 실무적 타협

다만 정말로 모든 계층 간 DTO 를 분리하면  
서비스가 복잡해질수록 클래스 폭발의 위험이 심각하기에  
어떤 해결 방법이 있을까 찾아봤어요.

도메인은 그 자체로서 무결성과 완결성을 보장해야 하지만  
식별자 생성 전, 엔티티가 되기 전 VO 상태인 도메인 객체를 표현하기 위해  
비영속(transient) 상태의 도메인 객체를 허용하는 방식을 택했어요.

```java
public record Reservation(long id, String name, String date, long reservationTimeId) {

    public static Reservation transientOf(ReservationRequest reservationRequest) {
        return new Reservation(0, reservationRequest.name(), reservationRequest.date(), reservationRequest.timeId());
    }
}
```

비영속 상태로 전달되어 저장(영속화)되고, 이후 새로운 객체를 조회해서 반환한다면  
불완전한 도메인이지만 요청 - 전달 - 저장 이라는  
짧은 라이프사이클에 한정되도록 할 수 있다는 생각이었어요.

#### 정리

객체 지향적 프로그래밍을 위해, 계층 간 의존을 제거하기 위해 도입된 DTO 는  
무작정 지양하지도, 마구잡이로 도입하지도 말아야 하며  
그 근본적인 목적과 목표를 준수할 수 있도록 고민하고 활용해야 함을 상기할 수 있었습니다.

피드백 04 와도 연관된 내용이지만  
도메인과 데이터베이스의 필연적 차이가 꽤나 다양한 문제와 고민을 유발함을 알 수 있었어요.  
또 transient 용어에 대한 탐색 과정에서 별 생각 없이 사용했던 다양한 도구가  
선배 개발자들의 수많은 고민의 결과였음을 재확인하는 경험이었어요.
