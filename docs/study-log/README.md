# 학습법 V1

### 도서를 통한 개념 공부

객체지향 이라는 큰 개념 공부 할 때,
가이드가 되어줄 수 있는 도서를 선택하고,
그 도서를 이정표 삼아서 학습 후에 코드를 작성하면서 적용시켰습니다.

### AI를 활용한 인사이트 활용

미션 중 만약 모르는 개념이 생겼을 때에는,
바로 AI에게 물어보는 것을 경계하고,
먼저 생각을 해본 뒤에 생각대로 해보고, 그래도 모르겠으면 AI에게 인사이트를 얻었다.

### 막힐 때 해결하기

언제 막히는가?
새로운 개념과 혼자 생각하기 어려운 부분들을 만났을 때에는
AI를 통해 빠르게 프로토 타입의 개념을 익히고 인지한 뒤에,
Web에 검색하여 공식 문서나 블로그를 통해 세부적 지식을 공부하였습니다.

**효과적이었던 것:**
학습이라는 것은 배울 학 익힐 습으로
**`지식이나 기술을 배우고(Input) 그것을 반복하여 자기 것으로 익히는(Output) 전 과정`**
이라고 생각하는데, 새로운 개념을 만났을 때, 지치기 전에 빠른 프로토타임의 개념을 공부하고,
궁금한 점을 만드는 것이 중요하다고 생각하고, 그 궁금점을 해소하고 그것을 직접 나의 것으로 익히는 과정이라고 생각한다.

그래서 이때, 개념과 방법을 익힐 때, 그냥 글을 읽기만 한다면 금방 휘발되기 때문에 읽으면서 같이 notion에 정리를 하거나 경험을 하여 실천하는 방법이 좋다고 생각한다.

# 학습법 V2

### 도서 중심의 학습

큰 개념에 대한 학습을 할때

책을 통한 학습은 지식의 깊이를 다지는 데에 확실하지만, 시간과 체력이 너무 많이 소보 되기 때문에
처음부터 다 완벽하게 읽으려고 하지 않는다.
인사이트를 얻는 책들은 기록보다는 내가 읽고 머리로 이해하려고 한다.
책에 밑줄을 긋거나 형광펜을 칠하면서 기록하자.
기록을 위한 독서를 경계한다.

### 인풋에 대한 아웃풋

새로운 개념을 읽힐 때 단순히 글을 읽고 넘기는 것을 경계하지만, 너무 휘발에 대한 걱정은 덜어낸다.
어차피 중요한 개념이라면 나중에 또 나오게 된다.
필요하다고 판단되는 개념들이라면 빠르게 경량화된 아웃풋 프로세스를 적용해본다.

### 고민의 시간과 빠른 시도

모르는 것이 생겼을 때,

먼저 이 문제가 고민할 가치가 있는가를 판단을 한다.

고민할 가치가 있다면은 고민을 진행하고
그럴만한 가치가 없다면은 쉽게 지치기 것을 대비하여 AI로 핵심 개념 프로토타입 개념을 파악하고 직접 부딪혀보며 궁금점을 해소하면서 학습 사이클의 속도를 올리자.

## 개인 학습 시도

주제: Virtual Thread

**학습법이 어디서 잘 동작하였나**

빠른 개념을 익히는데에는 효과적이었다.

**어디서 잘 동작하지 않았는가**

어떻게 적용을 해야할지에 대한 부분에 대해서는 막막하였다.

**왜 그런가?**

개념이 어려운 것이 나왔을 때에는 적용을 하기에 처음 시도에 대한 장벽이 높다.

# 학습법 V3

**1. `지식의 착각을 깨는 '백지 인출 연습 (Blank Page Retrieval)'`**

문서를 읽거나 AI가 작성해 준 완성된 코드를 보면 우리의 뇌는 그것을 '내가 안다'고 착각합니다. 이를 인지 심리학에서는 '**지식의 착각(Illusion of Competence)'**이라고 부릅니다.
백엔드의 뼈대가 되는 설계 원칙들은 눈으로 읽는 것만으로는 절대 체화되지 않습니다.

- **실행 방법:**
  AST(추상 구문 트리) 구조나 Visitor 패턴 같은 복잡한 객체지향 설계 패턴을 학습한 직후, 즉시 모든 참고 자료와 IDE를 닫으세요.

그리고 빈 종이를 꺼내 방금 배운 패턴의 핵심 인터페이스와 클래스 다이어그램을 펜으로 직접 그려보거나,
순수 자바(Java) 코드의 핵심 로직만 기억에 의존해 텍스트 편집기에 적어보세요.
- **전문가의 멘탈 모델:** 뇌과학적으로 기억을 가장 강력하게 강화하는 방법은 정보를 머릿속에 집어넣는 것이 아니라 **억지로 '끄집어내는(Retrieval)**' 과정입니다.
  기억이 나지 않아 뇌가 고통을 느끼는 바로 그 순간,
  느슨했던 신경망이 굵고 단단하게 연결되며 진정한 내 지식이 됩니다.

**2. `뇌에 마찰력을 주는 '교차 학습과 의도적 파괴 (Interleaving & Desirable Difficulties)'`**

하나의 주제(예: Spring 프레임워크 한 과목)만 연속적으로 공부하는 '**블록 학습**'은 장기 기억 형성에 비효율적입니다. 또한, 코드가 오류 없이 성공적으로 돌아가는 해피 케이스(Happy Case)만 경험하면 뇌는 성장을 멈춥니다.

- **실행 방법:**
  학습 주제를 역동적으로 섞으세요(교차 학습).

예를 들어, Virtual Thread의 동시성 모델을 공부하다가,
완전히 다른 맥락인 다국어 환경의 코드 디버깅 로직('Debug Run' 같은 복잡한 환경)으로 넘어가
BDD(행동 주도 개발) 테스트 코드를 작성해 보는 식입니다.

더 나아가, 잘 돌아가는 코드에 의도적으로 매직 넘버를 주입하거나 객체의 단일 책임 원칙을 망가뜨려 보세요.
그리고 테스트 프레임워크가 이를 어떻게 잡아내는지, 시스템이 어떻게 붕괴하는지 관찰하세요.
- **전문가의 멘탈 모델:** 뇌에 `의도적으로 적절한 마찰력(바람직한 어려움)`을 제공할 때 진짜 실력이 쌓입니다.
  서로 다른 개념을 교차로 학습하고 고의로 에러 상황에 스스로를 노출시키면,
  뇌는 패턴 간의 차이를 더 깊이 인식하게 되고
  예측 불가능한 실무 환경에 대비할 수 있는 유연성을 갖추게 됩니다.

**3. `분산 모드를 활용한 '시각적 은유 (Visual Metaphors)'`**

서버의 비동기 처리나 네트워크 I/O 같은 개념을 텍스트 파일이나 코드의 논리로만 이해하려고 하면
워킹 메모리가 금방 지칩니다. 이럴 때는 강제로 모니터 앞을 떠나야 합니다.

- **실행 방법:** 억지로 코드를 들여다보며 고민하는 대신, 산책을 하거나 샤워를 하면서 복잡한 백엔드 아키텍처를 현실 세계의 친숙한 물건에 빗대어 상상해 보세요. 예를 들어, 스레드 풀(Thread Pool)을 식당의 주방장 체계로 비유하거나, 클라이언트의 요청이 서버를 거쳐 DB까지 도달하는 과정을 거대한 물류 센터의 레일로 시각화해 보는 것입니다.
- **전문가의 멘탈 모델:** 고도의 집중(Focused Mode)은 세부 사항을 파고들 때 유용하지만, 큰 그림을 이해하고 추상적인 개념을 연결할 때는 뇌의 **분산 모드(Diffuse Mode)**가 켜져야 합니다. 코드를 현실의 이미지로 치환(은유)하면, 뇌는 완전히 새로운 개념이라도 이미 존재하던 기존의 신경망에 빠르고 강력하게 걸고 넘어갈 수 있는 '훅(Hook)'을 만들어냅니다.

---

**샌드박스 주도 마이크로 청킹 (4단계 학습법)**

1단계: `가벼운 개념 스캐닝 (기존 강점 유지)`

- **실행:** 기존처럼 책의 큰 흐름을 읽고, AI를 통해 핵심 개념을 빠르게 파악합니다.
- **목표:** 깊은 이해보다는, 뇌의 분산 모드(Diffuse Mode)를 활용해 새로운 기술이 어떤 문제를 해결하기 위해 등장했는지 '`지도`'만 그리는 단계입니다.

2단계: `초소형 샌드박스 구축 (장벽의 해체)`

- **실행:** 핵심은 "가장 작은 단위로 성공을 경험하는 것"이다. 단, 개념의 성격에 따라 샌드박스의 형태를 다르게 가져간다.

  - **순수 Java 개념** (Virtual Thread, 디자인 패턴 등): 기존 코드베이스를 배제하고 `main` 메서드 하나짜리 빈 프로젝트에서 10줄만 작성한다.
  - **프레임워크 통합 개념** (JdbcTemplate, Jackson 등): 프레임워크 맥락 안에서만 의미가 있는 개념이므로, 기존 프로젝트에 직접 적용하되 **딱 하나의 기능만** 동작시키는 것에 집중한다. 한 번에 모든 것을 적용하려 하지 않는다.

- **전문가의 멘탈 모델:** 뇌가 두려움을 느끼지 않도록 진입 장벽을 밀리미터 단위로 낮추는 작업입니다. "가장 작은 성공"의 형태는 개념마다 다르지만, 외부 변수를 최소화하고 한 번에 하나씩 확인한다는 원칙은 동일합니다.

3단계: `의도적 파괴와 한계 테스트 (바람직한 어려움)`

- **실행:** 코드가 정상적으로 돌아간다면, 이제 샌드박스 안에서 안전하게 사고를 칠 차례입니다. 기존 스레드 풀로 100만 개의 작업을 돌려 서버가 터지는(Out of Memory) 상황을 눈으로 확인하고, 동일한 로직을 Virtual Thread로 교체해 평온하게 돌아가는 것을 대조해 봅니다.
- **전문가의 멘탈 모델:** 개념이 왜 대단한지 글을 읽고 넘기는 것은 '지식의 착각'을 부릅니다. 극단적인 상황을 연출하고 두 눈으로 성능의 차이와 에러 로그를 확인하는 순간, 기술의 진가가 뇌에 강렬한 시각적/경험적 훅(Hook)으로 박히게 됩니다.

4단계: `마이크로 회고와 점진적 결합 (메타인지와 스캐폴딩)`

- **실행:** 바로 이 시점에 질문자님의 '회고'를 진행합니다. *"샌드박스에서 무엇을 부숴보았는가? 어떤 에러를 만났는가? 이제 이것을 객체지향적인 코드 흐름 속에 어떻게 녹여낼 것인가?"*를 짧게 기록합니다. 이후, 이 단단해진 청크를 TDD 기반의 테스트 코드나 실제 구현하려는 기능의 일부로 조금씩 확장(Scaffolding)해 나갑니다.

# 학습법 V4

> **막힌 것을 진단하고 → 유형에 맞는 전략을 선택하고 → 회고를 완성한다.**

V1~V3의 전략들은 그대로 유효하다. V4는 그것들을 **언제 꺼내 쓸지**를 명확하게 해주는 실행 레이어다.

기존 학습법에서 빠진 핵심:
> 전략은 있는데, 지금 내 막힘이 어떤 종류인지 먼저 진단하는 과정이 없다.

전략이 아무리 좋아도, 막힌 것의 유형과 맞지 않으면 효과가 반감된다.

---

### 막힌 것 유형 → 전략 매핑표

학습 타임을 시작하기 전, 또는 막혔을 때 **먼저 유형을 진단하고 이 표에서 전략을 골라 실행한다.**

| 막힌 것의 유형 | 진단 질문 | 권장 전략 |
|---|---|---|
| 개념 자체를 모르겠다 | "이 단어의 뜻을 설명할 수 있는가?" | AI 프로토타입 → 초소형 샌드박스 (V3 2단계) |
| 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 | "알긴 아는데 손이 안 움직이는가?" | 초소형 샌드박스 + 의도적 파괴 (V3 2~3단계) |
| 코드는 돌아가는데 이게 맞는지 모르겠다 | "왜 이렇게 짰는지 남에게 설명할 수 있는가?" | 설계 리트머스 테스트 (아래 신규 전략) |
| 막힌 게 뭔지 자체를 모르겠다 | "뭐가 문제인지도 모르겠는가?" | 백지 인출 연습 (V3 1번) → 빈 곳이 막힌 곳 |

---

### 신규 전략: 설계 리트머스 테스트

**언제 쓰는가:** 코드가 동작하지만 설계가 맞는지 확신이 없을 때

**실행 방법 (3단계):**

**1단계 — 페인만 설명**

코드를 닫고, 내가 왜 이렇게 설계했는지를 말 또는 글로 설명한다.
설명이 막히는 부분 = 실제로 이해가 안 된 부분이다.

```
예시: "왜 Controller에서 바로 DB 접근을 안 하고 Service를 두었나?"
→ 설명할 수 없다면, 계층 분리 이유 자체를 아직 모른 것
→ 설명할 수 있다면, 설계는 맞을 가능성이 높음
```

**2단계 — 단일 책임 체크**

복잡한 원칙 전체를 볼 필요 없다. 하나만 묻는다.

> "이 클래스/메서드가 하는 일이 한 가지인가?"

한 가지가 아니라면 분리 기준이 잘못된 것이다.

**3단계 — AI 코드 리뷰 (마지막 수단)**

"내 코드가 맞는지 검색"이 아니라, 코드를 직접 보여주고 구체적으로 묻는다.

```
좋은 질문: "이 ReservationController가 Service를 통하지 않고
             Repository를 직접 쓰는 게 맞나요? 계층 분리 관점에서 피드백 주세요."

나쁜 질문: "MVC 계층 분리 어떻게 해요?"
```

### 회고 완성 규칙

**규칙: 학습 로그의 5번 섹션(다음 타임에 바꿀 것)을 채우지 않으면 다음 타임을 시작하지 않는다.**

분량은 중요하지 않다. 아래 두 줄이면 충분하다.

```
유지: [내용] — [이유]
바꿀 것: [내용] — [이유]
```

"뭘 바꾸겠다"보다 **왜 바꾸는가**가 더 중요하다. 이유가 없으면 다음 타임에 같은 실수를 반복한다.
