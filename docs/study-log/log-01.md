## 2. 이번 타임의 학습 전략

미션을 진행하기 전 토론 활동을 통해서 v2 학습법에서 현재의 v3 학습법으로 재구성했다. 그 과정에서 바뀐 전략은 학습을 본격적으로 진행하기 전 학습 목적 뿐만 아니라 완료 조건까지 작성하고 진행하는 것이다.
따라서 이번 타임의 학습 전략에서 학습을 진행하기 전 목적과 완료 조건을 작성하고 실행하였다.

LMS에서 이번 단계1의 힌트를 처음부터 보지 않고 스스로 먼저 설계해본 뒤, 막힐 때만 참고하는 전략을 택했다.

### 실제 진행 과정

**1. 학습 포인트 발견 과정**

LMS의 1단계: 웹 요청-응답의 요구사항 항목을 읽으면서 다음과 같은 문항을 발견했다.

> 별도의 데이터베이스 없이 메모리(`List` + `AtomicLong`)로 예약 상태를 관리한다. …

- 여기서 `List`는 잘 알고 있는 컬렉션이지만, `AtomicLong` 자료형에 대해서는 처음 접하게 되었다. 자료형의 명칭을 보았을 때 `Long`과 유사한 자료형으로 추측해볼 수 있었고, 예약 데이터의 id
  값을 선언하는 자료형으로 사용할 것으로 예상했다.
- 그러나 정확히 `AtomicLong` 자료형이 어떤 것인지, 어떤 식으로 선언하는지, 어떤 내부 메서드가 존재하는지 등 알지 못하는 부분들이 많다고 판단했다.
- 따라서 1단계 미션을 수행하는 과정에서 `AtomicLong`에 대해 학습하게 되었다.

**2. 학습 전략 적용: 학습 목적과 완료 조건 명시하기**

- **목적**: `AtomicLong`이 무엇인지 이해한다.
- **완료 조건**: `AtomicLong`과 `Long`의 차이를 구별하고 사용할 수 있다.

**3. 검색 및 AI 도구 활용**

먼저 검색창에 `AtomicLong`에 대해 검색해 포스팅을 읽으며 빠르게 이해했다.

해당 포스팅을 통해서 `Long`으로 Id를 관리할 때, 싱글 스레드 환경에서는 정확하게 동작할지라도 멀티스레드 환경에서는 코드의 결과값이 실행할 때마다 달라져 일치하지 않게 된다는 점을 발견했다.

이 부분이 처음에 직관적으로 이해되지 않아 예시 상황을 AI에게 요청하였고, 다음과 같이 정리할 수 있었다.

`Long`으로 id를 관리할 때:

```java
private long id = 0;

public long generateId() {
    return ++id;
}
```

| 스레드 A     | 스레드 B     | id 값       |
|-----------|-----------|------------|
| id 읽기 (0) | id 읽기 (0) | 0          |
| +1 계산     | +1 계산     | -          |
| id에 1 저장  | id에 1 저장  | 1 ← 둘 다 1! |

포스팅에는 내가 알고자 하는 정보 외에도 다양한 정보가 나열되어 있었다. 따라서 완료 조건을 벗어난 부분은 더 이상 탐구하지 않고, 학습 기록에 키워드 형태로만 남겨두었다.

- **남겨둔 키워드**: 그 외의 Atomic Operations, CAS 연산법
- 이 키워드들은 추후 관련 개념의 필요성을 느껴 살펴보게 될 때 나선형 학습으로 수행할 예정이다.

또한 AI 도구를 활용해 InMemory 환경에서 DB 연동을 구현하고 ID 생애주기 관리를 `AtomicLong`으로 구현할 때 주요 사용 메서드 목록을 질문했고, 다음과 같이 정리할 수 있었다.

| 메서드                 | 설명      |
|---------------------|---------|
| `get()`             | 조회      |
| `incrementAndGet()` | +1 후 반환 |
| `getAndIncrement()` | 반환 후 +1 |
| `set(10)`           | 값 설정    |
| `addAndGet(5)`      | +5 후 반환 |

## 3. 전략 평가

**효과적이었던 것**

레벨1에서의 학습법의 가장 큰 문제였던 탐구의 깊이와 미션 목표 사이의 경계를 인식하지 못했던 부분이 이전보다 훨씬 개선되었다. 현재의 학습 전략인 "학습 목표와 완료 조건을 먼저 명시하기"가 너무 깊은 탐색 범위를
잘라내는 데 실제로 작동했다. 실제로 CAS 연산이나 Long 외의 Atomic 연산들에 대해 더 탐구하지 않고 키워드만 메모하고 넘어갈 수 있었다. 이전이었다면 이 두 키워드에 대해 물어보느라 미션 수행에 차질이
생겼을 것이다.

**비효과적이었던 것**

포스팅을 먼저 읽은 뒤 AI 검색으로 보완한 순서가 그다지 효율적이지 못했던 것 같다. AI에 너무 의존할 것 같아 이번 학습에서는 포스팅을 먼저 찾아보고 정리되지 않는 부분에 대해서만 AI에게 질문하고자 했는데,
오히려 너무 딥다이브하게 될 요소에 노출된 것 같다.

## 4. AI 피드백

**유용했던 제안: 검색 도구 선택 기준을 사전에 정해두기**

포스팅을 먼저 살펴보고 AI로 보완하는 이번 학습 전략이 비효율적이라고 판단한 이유는, 포스팅이 완료 조건 범위를 초과하는 정보를 포함하고 있었고 그 노출 자체가 불필요한 딥다이브 유혹을 만들었기 때문이다.
반대로 "개념 자체를 모르겠다" 유형의 막힘은 AI에게 완료 조건을 직접 전달해 질문하는 방식이 범위 제어에 더욱 유리하다.

따라서 학습을 시작할 때 아래 기준을 먼저 판단하고 도구를 선택한다.

| 막힌 유형             | 도구 선택                  |
|-------------------|------------------------|
| 개념 자체를 모르겠다       | AI에게 완료 조건을 함께 전달하며 질문 |
| 개념은 알지만 사용법을 모르겠다 | 공식 문서 또는 포스팅 우선 참고     |

> ⚠️ 포스팅은 학습 완료 조건을 벗어난 정보에 노출되기 쉬우므로 이를 인지하고 사용한다.
