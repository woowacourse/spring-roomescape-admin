# 학습법 개선

## V1 → V2 → V3 → V4

---

### V1 (log-01 · 1단계 MVC)

**전략**: 필요한 개념 학습 → 코드 실험 → AI에게 발표 후 피드백

**문제**: AI가 꼬리질문을 계속 하다 보니 피드백이 50개에 달하고 딥다이브 범위를 스스로 제어하기 어려웠다.

**개선**: AI 프롬프트에 제약 추가

- 피드백은 중요도 순 최대 5개
- 각 피드백에 중요도(상/중/하) 표시
- 지금 바로 공부할 것 vs 나중에 봐도 되는 것 구분

---

### V2 (log-02 · 2단계 DB 연동)

**전략**: V1 + AI 피드백 제한(최대 5개)

**문제**: 막힐 때마다 매번 학습 → 설명 → 피드백 루프를 반복하니 시간이 너무 많이 소요. 간단히 검색으로 충분한 내용도 AI 설명 과정을 거치는 게 비효율적이었다.

**개선**: 구현 흐름 끊지 않기

- 막히면 5분 이내로만 찾아보고 바로 구현 진행
- 의문점은 노션에 한 줄로만 기록 (`"KeyHolder가 뭐지?"`)
- 단계 구현 완료 후, 기록 리스트에서 우선순위 정해 일괄 학습

---

### V3 (log-03 · 3단계 트러블슈팅)

**전략**: V2 + 구현 우선 / 의문점 노션 기록 후 일괄 학습

**문제**: 기록한 항목들의 우선순위를 정할 때 "무엇이 더 중요한가"에 대한 확신이 없었다.

**개선**: 우선순위 체크리스트 도입

```
1순위: 지금 발생한 오류의 직접 원인인가?
2순위: 앞으로 자주 반복될 가능성이 높은가?
3순위: 잘못 이해하면 설계/구현 방향이 틀어지는가?
4순위: 지금 미션에서 다시 만날 가능성이 있는가?
5순위: 단순 호기심인가?
```

---

### V4 (log-04 · 4단계 계층 분리)

**전략**: V3 + 우선순위 체크리스트

**문제**: "정답이 없는 설계 문제"(예: Service가 응답 형식을 알아야 하나?)는 기존 전략(검색 → 학습 → AI 설명)이 잘 맞지 않았다.

**개선**: 문제 유형에 따라 전략 분기

- **정답이 있는 개념** → 기존 V1~V3 전략 유지
- **정답이 없는 설계 문제** → 크루/여러 AI의 의견 수렴 → 스스로 판단
- 판단을 내렸다면 **판단 근거와 기준을 기록**으로 남겨 다음에 비슷한 상황에서 참고

---

### 현재 전략 요약

| 상황          | 행동                                  |
|-------------|-------------------------------------|
| 구현 중 막힘     | 5분 이내 검색 후 바로 구현, 의문점은 노션 한 줄 기록    |
| 단계 완료 후     | 체크리스트로 우선순위 → AI 설명·피드백 루프(최대 5개)   |
| 정답 없는 설계 고민 | 크루·AI 다양한 의견 수렴 → 스스로 판단 → 판단 근거 기록 |

---

## 최종 학습법 (V4 기준)

### STEP 1. 구현 중 막혔을 때

1. 검색 또는 AI에 질문해 당장 구현에 필요한 최소한의 답만 얻는다.
    - "이게 어떻게 동작하는지"까지 파고들지 않는다.
    - 구현을 돌아가게 만드는 데 필요한 문법·방향만 파악한다.
2. **의문점은 노션에 한 줄로(db에 페이지 추가) 기록**하고 바로 구현을 재개한다.
    - 예: `"KeyHolder가 내부적으로 어떻게 id를 가져오는 거지?"`
    - 예: `"@ResponseBody에서 왜 getter가 public이어야 동작하지?"`

---

### STEP 2. 단계별 구현 완료 후 — 일괄 학습

#### 2-1. 우선순위 정하기

노션에 쌓인 의문점 목록을 아래 체크리스트로 순위를 매긴다.

```
1순위: 지금 발생한 오류의 직접 원인인가?
2순위: 앞으로 자주 반복될 가능성이 높은가?
3순위: 잘못 이해하면 설계/구현 방향이 틀어지는가?
4순위: 지금 미션에서 다시 만날 가능성이 있는가?
5순위: 단순 호기심인가?
```

시간이 부족하면 1~3순위만 학습하고, 4~5순위는 다음으로 미룬다.

#### 2-2. 개념 학습

1. AI, 공식 문서, 블로그 등을 통해 해당 개념을 학습한다.
2. 실패하는 코드를 의도적으로 작성해보며 동작 구조를 실험으로 확인한다.
    - 예: getter를 private으로 바꾸면 JSON에 어떻게 나오는지 직접 돌려본다.

#### 2-3. AI 발표·피드백 루프

학습한 내용을 **공부 자료를 보지 않고** AI에게 발표하듯 설명한다.

AI 프롬프트에 아래 제약을 반드시 포함한다.

```
1. 내 설명에서 부족하거나 틀린 부분을 정답을 알려주지 않고 질문으로 유도해서 피드백해줘.
2. 피드백은 중요도 순으로 최대 5개만 줘.
3. 각 피드백에 중요도(상/중/하)를 표시해줘.
4. 지금 바로 공부해야 할 것과 나중에 봐도 되는 것을 구분해줘.
```

AI의 피드백을 받은 뒤 부족한 부분을 보완하고, 필요하면 한 번 더 설명 루프를 돈다.

---

### STEP 3. 정답이 없는 설계 고민일 때

1. **주변 크루들에게 각자의 생각을 먼저 물어본다.**
    - 내가 생각하지 못한 다른 접근법을 파악하는 것이 목적이다.
2. **AI에게도 동일한 질문을 던져 다양한 관점을 수집한다.**
3. 수집한 의견들을 바탕으로 **각 방법의 장단점·트레이드오프를 스스로 정리**하고 최종 판단을 내린다.
4. **판단 근거와 기준을 기록으로 남긴다.**
    - 예:
      `"Service에서 생성된 객체를 반환하는 이유: Controller가 응답 형식을 제어하도록 하기 위함. Service는 비즈니스 결과를 반환하는 것이지 HTTP 응답을 신경 쓰는 게 아니라고 판단."`
    - 다음에 비슷한 상황이 오면 이 기록을 먼저 참고한다.

## 코칭 이후 주말에 추가 학습법 개선

주말에 시도할 것: 얼마나 깊이 공부할 것인가에서 LMS 미션의 학습 목표, 미션 후 답할 수 있는 질문 등에 나온 내용을 판단기준에 적용한다.

적용 시나리오:

1. 주말간 코드 리뷰 및 선택 요구사항(UI) 구현을 하다가 막히는 부분이 생길때
2. 노션에 쌓인 목록 우선순위 판단시, 기존 체크리스트보다 아래 기준을 우선적으로 적용한다.
    - LMS 미션의 학습 목표에 부합하는가?
    - 미션 후 답할 수 있는 질문에 대한 답을 얻는 데 필요한 개념인가?
3. 해당 주제에 대해 학습하고 AI와 피드백과 꼬리질문을 주고 받는다.
4. LMS 미션의 학습 목표 및 가이드를 참고해 충분히 설명가능하다고 판단하면 더 깊이 들어가지 않고 중단한다.
