### 2. 이번 타임의 학습 전략
* **이전 전략**: 새로운 2-Track 전략 실행. 일단 동작하는 코드를 짜는 데 집중(BFS)한 뒤, `KeyHolder`의 매개변수 구조나 스프링의 DTO 자동 매핑 원리 등 유독 궁금했던 지점만 골라 가볍게 파고드는(v3) 방식 적용.
* **학습 과정 상세**:

#### 🔑 JdbcTemplate.update와 KeyHolder의 설계 의도 추적 (v3 딥다이브)
* `update` 메서드는 기본적으로 '영향받은 행의 개수(`int`)'를 반환하도록 약속되어 있음. 자바는 반환값이 하나뿐이므로, 생성된 ID를 받아오기 위해 `KeyHolder`라는 바구니 객체를 매개변수로 우회하여 전달하는 구조임.
* `String[]{"id"}`로 받는 이유: JDBC API 설계자의 큰 그림. 복합키나 여러 개의 자동 생성 번호(예: 고유 ID, 랜덤 발급되는 회원 번호 등)가 생길 미래의 상황에 대비해 배열로 설계됨.

#### 🔄 중첩 DTO와 제어의 역전(IoC)
* **과거의 멘탈 모델**: "DTO에는 원시타입(`String`)만 써야 하고, 개발자가 직접 객체로 변환해야 한다."
* **스프링의 멘탈 모델**: 스프링은 내부적으로 Jackson을 통해 타입 변환을 자동으로 해줌. `LocalTime`을 그대로 쓰면 변환의 책임이 개발자에서 프레임워크로 완전히 넘어감(**IoC**). 오히려 비즈니스 로직 진입 전에 프레임워크 단에서 타입 에러를 검출할 수 있어 훨씬 안전함.

#### 🔗 SQL Inner Join (`ON` vs `USING`)
* `Reservation`(예약 정보)과 `ReservationTime`(시간 정보)이 외래키(`time_id` -> `id`)로 분리되면서 Join의 필요성 발생.
* **ON**: 가장 범용적. 컬럼 이름이 달라도(`A.time_id = B.id`) 조인 가능.
* **USING**: 컬럼 이름이 완전히 같을 때 쓰는 지름길 문법. 결과에서 중복 컬럼이 합쳐져서 나옴.

### 3. 전략 평가
* **효과적이었던 것**: **'BFS 선행 구현 + v3 후행 탐구' 사이클**. 미션 구현이라는 무거운 짐을 BFS 모드로 먼저 내려놓은 뒤에, `String[]{"id"}`나 IoC 같은 궁금증을 파고드니 전체 맥락 속에서 "왜 설계자가 이렇게 만들었는지"가 단번에 이해되었음.
* **비효과적이었던 것**: 순수 자바 시절의 고정관념(DTO는 무조건 String 수동 변환) 때문에 초반에 스프링의 마법을 믿지 못하고 헤맨 것.
* **궁합**: 기능 구현(엔지니어링)과 원리 이해(체화)를 분리하는 이 2-Track 전략은, 마감 기한과 학습 퀄리티를 모두 잡아야 하는 현재 상황에서 최고의 궁합을 보여줌.
