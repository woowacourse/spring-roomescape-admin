### 2. 이번 타임의 학습 전략
* **이전 전략**: 완벽주의를 내려놓고 속도감을 높이기 위해 **'BFS 모드(실전 스프린트)'** 프롬프트 도입. 얕고 넓게 훑어 코드를 먼저 동작시키고, 깊은 원리는 '기술 부채'로 미루는 전략 실행.
* **학습 과정 상세**:

#### 🗄️ H2 DB와 스프링 자동 설정 (Auto-configuration)
* `spring-boot-starter-jdbc`와 `h2` 의존성 추가.
* 테스트와 로컬 환경을 분리하기 위해 `testImplementation`과 `runtimeOnly`를 구분하고, H2 접속 모드(mem, file, tcp)의 차이를 가볍게 훑음.
* `schema.sql`을 두면 스프링 부트가 서버 시작 시 자동으로 DDL을 실행해 주는 편리함 확인.

#### 🔄 제어의 역전(IoC)과 Spring Container (인사팀 비유)
* 과거 순수 JDBC 시절에는 개발자가 직접 DB 커넥션을 맺고 자원을 해제(`try-catch-finally`)해야 했음.
* 이제는 프레임워크가 주도권을 가짐(**IoC**). 스프링 컨테이너(인사팀)가 시작될 때 `application.properties`를 읽어 `JdbcTemplate`(행정 요원)을 준비해 두고, 생성자 주입을 통해 서비스/레포지토리 직원들에게 도구를 알아서 쥐어줌.

#### 🛠️ JdbcTemplate과 Data Mapping
* **RowMapper**: `while(rs.next())`로 돌며 데이터를 매핑하던 지루한 과정을 대체. `(rs, rowNum) -> Entity` 형태의 매핑 로직만 갈아 끼우면 됨.
* **타입 간극 해결**: DB의 `VARCHAR`("2026-04-29")를 Java의 `LocalDate` 객체로 변환할 때, JdbcTemplate이 훌륭한 통번역기 역할을 수행.
* **메서드 종류**: `query`(읽기), `update`(상태 변경), `queryForObject`(단건 조회) 등 직관적 사용법 체득.

#### 🔑 KeyHolder (바구니)
* DB가 `AUTO_INCREMENT`로 ID를 생성했을 때, 자바는 그 ID를 바로 알 수 없음.
* `GeneratedKeyHolder`라는 빈 바구니를 `jdbcTemplate.update()`에 함께 던져주면, 스프링이 중간에서 생성된 키를 낚아채어 바구니에 담아 돌려줌.

### 3. 전략 평가
* **효과적이었던 것**: **BFS 모드 도입**. 세세한 빈(Bean) 등록 원리나 예외 처리 로직에 깊게 빠지지 않고, `[Client] ➡️ [Controller] ➡️ [Repository] ↔️ [H2]` 라는 전체 흐름(Big Picture)을 먼저 잡은 덕분에 진도가 폭발적으로 빠졌음.
* **비효과적이었던 것**: (이번 세션에서는 BFS 모드의 목적대로 막힘없이 진행되어 특별한 비효율은 없었음)
* **궁합**: 스프링 프레임워크처럼 자체적으로 해주는 것이 많은 기술을 처음 붙일 때는, 원리 파악을 뒤로 미루고 일단 '동작'하게 만드는 BFS 전략이 더 잘 맞는 것 같음.

### 4. AI 피드백
* **제안 1 (기술 부채의 훌륭한 격리)**: 스프링 DI 원리나 `rs.getObject()` 심화 사용법을 파고들고 싶은 충동을 참아내고 **'기술 부채' 리스트로 따로 격리**해 둔 점이 예술적입니다. 이게 바로 실무 시니어들이 마감 기한을 맞추는 핵심 멘탈 모델입니다.
* **제안 2 (미션 밀착형 파괴 훈련 추천)**: 나중에 부채를 갚을 때, 기존 v3 프롬프트의 **'의도적 파괴'** 전략을 써서 포스트맨으로 이상한 날짜("2026/13/45")를 고의로 던져보고 500 에러가 어떻게 떨어지는지 눈으로 확인해 보는 것을 추천합니다.
