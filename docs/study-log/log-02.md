#### 실제 진행 과정

1. **학습 포인트 발견 과정**

   이번에도 역시 이번 단계의 요구사항 항목을 읽으면서 학습 포인트를 발견했다.

   > 1단계에서 만든 조회 · 추가 · 삭제 API를**모두 JdbcTemplate 기반**으로 전환한다
   >
    - 이전 레벨1에서 Jdbc를 기반으로 순수 자바 애플리케이션에서 DB 연결 및 트랜잭션 관리를 수행한 경험은 있다. 그래서 이와 유사하거나 혹은 Spring이 이를 보다 편리하게 사용할 수 있도록 제공하는

    - 그러나 실질적인 개념과 그리고 그 사용법에 대해서는 무지한 상태였다. 따라서 이 부분에 대해서 학습을 진행하고, 기존 단계1에서 작성한 인메모리기반 코드를 JdbcTemplate를 활용한 데이터베이스 기반
      코드로 개선해야할 필요를 느꼈다.
2. **학습 전략 적용**
    - **학습 목적 및 완료 조건 명시**
        - 목적: Spring의 JdbcTemplate에 대해서 학습한다.
        - 완료조건: 현재 API 기능을 유지하면서 JdbcTemplate으로 대체할 수 있다.
    - **학습 도구 선택: AI에게 완료 조건을 함께 전달하며 질문 및 기록**

      학습은 개념 이해 → 메서드 파악 → 구현 중 의문 해소 순서로 진행했다.

        - **AI 도구 활용 방식**
            - 이번 학습에서는 AI를 학습 가이드로 활용했다. 단, 처음부터 다음 두 가지 조건을 함께 전달했다.
            - 완료 조건을 명시해서 그 범위를 벗어난 깊은 학습으로 이어지지 않도록 했다
            - 코드 전문을 붙여넣어 AI가 대신 작성해주는 방식은 절대 사용하지 않았다. 개념을 이해하고 직접 구현하는 방식으로 진행했다
    - **학습 내용 요약**
        - **JdbcTemplate 개념 이해**

          이전 레벨1에서 순수 Java JDBC를 다뤄본 경험이 있었기 때문에, JdbcTemplate이 그것과 어떻게 다른지를 출발점으로 삼았다. 순수 JDBC에서는 Connection 생성,
          PreparedStatement 관리, ResultSet 닫기, 예외 처리까지 전부 직접 작성해야 했는데, JdbcTemplate은 이 반복 작업을 Spring이 대신 처리해주고 개발자는 SQL문과
          결과를 어떤 객체로 변환할지만 신경 쓰면 된다는 점을 파악했다.

        - **CRUD별 메서드 파악**

          Create / Update / Delete → 전부 `update()`로 처리

          Read 목록 → `query()`, Read 단건 → `queryForObject()`

    - **구현 중 생긴 의문 해소**

      구현을 진행하면서 다음 의문들이 생겼고 그때그때 해소했다.

        - **`query()`의 두 번째 인자로 람다가 오는 이유**
            - Spring은 SQL 실행과 ResultSet 반환까지만 담당하고, 그것을 어떤 객체로 변환할지는 알 수 없기 때문에 변환 로직을 람다로 직접 전달하는 방식을 택한 것
        - **`queryForObject()` 단건 조회 시 예외 처리**
            - 결과가 없으면 `null`이 아닌 `EmptyResultDataAccessException`을 던지기 때문에 `try-catch`로 직접 잡아서 `Optional.empty()`를 반환하도록
              처리해야 함
        - **KeyHolder를 사용하는 이유와 두 가지 형태**
            - `update()`는 기본적으로 영향받은 행 수만 반환하기 때문에, INSERT 후 DB가 생성한 id를 받아오려면 KeyHolder가 필요함
            - `PreparedStatement` 생성 시점에 `Statement.RETURN_GENERATED_KEYS` 상수를 넘기거나, `new String[]{"id"}`처럼 반환받을 컬럼명을 직접
              명시하는 두 가지 오버로딩 형태가 있음
        - **delete에서 존재하지 않는 값에 대한 처리**
            - `update()`의 반환값(영향받은 행 수)이 0이면 해당 id가 존재하지 않는 것이므로, 이를 활용해 예외를 던지고 API 레이어에서 응답을 달리 처리하도록 구성했다

### 3. 전략 평가

- **효과적이었던 것**
    - AI 도구를 활용할 때, 내가 현재 학습하고자 하는 것과 목표 그리고 완료 조건을 지침에 명시해 활용하니 학습의 완료 기준을 명확히 할 수 있었다.
- **비효과적이었던 것**
    - AI 만 학습의 도구로 활용하게 되는 것 같다. 명확한 지침이 있으니 직접 문서를 찾아보거나 포스팅을 찾아보는 순간이 현저히 적어지게 된다. 그런데 그렇다고 해서 학습의 질은 떨어지진 않은 것 같다고
      느껴진다. 다만 AI 가 명확하지 않은 답을 내렸을때 이를 판단할 장치가 없어지게 된다.
- **1번에서의 막힌 것의 종류와 현재 학습 전략의 궁합**
    - 낯선 개념과 그리고 그것의 사용법에 대해 몰랐고, 현재 학습 전략을 통해 마지막에 결국 이번 단계에서의 JdbcTemplate 으로 API 기능을 유지할 수 있었다.

### 4. AI 피드백

- **유용했던 제안: 막힌 유형별 도구 선택 전략의 기준 재조정**
    - 현재 전략 표에서 "사용법을 모르겠다 → 공식 문서/포스팅 우선"으로 정의했지만, 이번 타임에서 실제로는 AI를 주 도구로 사용하고도 학습 질이 낮지 않았다고 판단했다. 이는 현재 기준이 실제 행동과 맞지
      않는다는 의미다. 전략 표를 실제 사용 패턴에 맞게 수정하는 것이 낫다. 누적 전략의 도구 선택 기준 수정 제안은 다음과 같다:

      | 막힌 유형 | 도구 선택 |
              | --- | --- |
      | 개념 자체를 모르겠다 | AI에게 완료 조건을 함께 전달하며 질문 |
      | 개념은 알지만 사용법을 모르겠다 | AI로 먼저 파악 → 공식 문서에서 키워드 존재 확인 |
