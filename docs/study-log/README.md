## 실험을 해보는 경우
### 1. 선택지가 주어지고 차이를 학습하는 경우
	사용한 이유를 나조차도 모르겠을 때, 이 이유를 비교하며 학습해본다.
[싱글톤 vs 유틸함수 Comment (블랙잭 사이클1)](https://github.com/woowacourse/java-blackjack/pull/969#discussion_r2901753525)   
[stream을 사용하는 이유 - for문 vs stream 가독성 비교 (블랙잭 사이클1)](https://github.com/woowacourse/java-blackjack/pull/969#discussion_r2902918133)   
[메서드 파라미터 - 원시타입 vs Wrapper타입](https://github.com/woowacourse/java-blackjack/pull/1070#discussion_r2935741581)   
- 비교해야할 경우, 직접 코드를 작성한 뒤, 차이를 느껴본다.
- 차이를 느끼기 어렵다면 (**막힌 경우**)
    - AI에게 작성한 코드를 전달한 뒤, 차이를 물어본다.
    - 해당 비교나 실험을 해보고 자신의 생각을 적어둔 다른 사람의 글을 찾아 읽어본다.
    - **차이를 생각하기 귀찮아서 AI에게 자주 맡기는 편이다.**
- 장기 기억으로 옮기기 위해 복습한다. -> **실제로 복습을 잘 하지는 못했다.**

### 2. 특정 주제에 대해서 호기심이 생겨 직접 실험하는 경우
	 나에게 흘러들어온 주제에 대해서 갑자기 호기심이 생겨 직접 실험해보는 경우
[Enum 캐싱 - JVM WarmUp](https://koreaioi.tistory.com/195)   
[Scanner vs BufferedReader - GC 비교](https://koreaioi.tistory.com/197)   
[동시성 테스트하다 발견한 Docker CPU 계산](https://koreaioi.tistory.com/199)   
- 실험 환경을 스스로 조성할 수 있는 수준의 호기심이라면 직접 실험 환경을 조성해본다.
- 실험 환경을 **스스로 조성할 수 없는 수준**의 호기심이라면 AI에게 물어봐 실험 방법 가이드라인을 물어본다. (대부분 이 상황이었다.)
- 직접 실험해보고 기록한다.
- 실험의 결과가 예상과 다른 경우, AI에게 다시 물어본다. (점점 깊어진다.)
  이때 치명적인 문제가 있는데, 실험 환경이 AI에 의해 조성되고, 기본 베이스가 AI가 알려준 내용이다 보니, 정확한 정보인 지 확신이 없다. (실제 Docker CPU 계산 부분에서 순간적으로 CPU 사용률이 100%를 넘어 튀는 현상을 제대로 설명하지 못함. 말이 바뀜)
  - 학습하고자 하는 내용이 깊어질 수록 이를 이해하기 위한 CS 지식이 필요하다. 이게 부족하면 이해하는 과정 역시 AI에 의존하게된다.
  - AI의 답변이 올바른지 의심된다.
  - 0-90의 지식을 학습하는 것보다, 90-100의 지식을 학습하는 게 몇배는 더 어렵다는 검프의 말이 생각난다.

## 책을 읽는 경우 (Real MySQL)
- 목차를 살펴보고 내가 흥미가 가는 부분을 선정한다. (4, 5, 8, 9, 10장)
- 읽는다.
    - 읽으면서 드는 궁금증은 AI에게 물어본다.
        - 이 과정에서 계속해서 드는 궁금증을 알아보려고 하는데, 시간이 오래 걸린다.
    - AI와 책을 통해 이해한 내용을 바탕으로 정리한다.
- 4장을 읽는 도중, 기본적인 배경지식을 간단하게 쌓은 뒤, 책을 읽으면 더 효과적일거라 생각했다. -> 관련 내용을 다룬 **테코톡**이 있는 지 찾아보고 시청한다.

- 읽으면서, 드는 생각들을 크루들과 공유하는 것.
    - ex 옵티마이저가 실행 계획을 세울 때, 바라보는 것이 통계 정보라고 하네요~
    - ex 이런 궁금증이 있어서 이렇게 해봤는데, 저렇게 되네요. 신기방기
    - 근데 은근 잡담도 많이하게됨.

# Version 2
## 학습법 v2
- Spring이 아니라 새로운 언어와 프레임워크를 배울 때라고 가정.
1. 전체적으로 큰 틀의 목표를 적고, 그에 부합하는 작은 학습 목표를 구체적으로 적는다.
2. 호기심이 생기면, 학습 목표와 비교하여 적절한(탐구할만한) 호기심인지 판단한다.
    - 적절한 호기심이라면 알아본다.
    - 학습 목표와 어긋나는 호기심이라면, 다른 곳에 적어둔다. (ex A공부 중 이런 궁금증이 생겼었다.)
3. 공식문서, 블로그, AI에게 새롭게 학습하는 내용을 읽어본다.
4. 공식문서, 블로그에서 실제 사용 예시를 찾아보거나, AI에게 물어본다.
    - 사용 예시를 살짝 다르게 변경해보고 비교한다.
5. 사용 예시를 보고 아주 작은 단위의 프로젝트를 만들어본다.
6. 학습한 내용을 정리해본다. (ex A는 B이다.)
7. 시간이 남을 경우, 적어두었던 호기심을 주제로하여, 탐구하여 깊이있게 공부해본다.

        - "gradle을 사용할때와 사용하지 않을 때 차이를 어떻게 간단한 프로젝트로 실습할 수 있을까"
    - 그래서 gradle이 있을 때와 없을 때를 비교하는 간단한 프로젝트를 만들어 실행해봤음
    - 간단한 프로젝트라서 쉽게 해볼 수 있고 결과가 바로 나오니 재밌음.
    - 목표를 설정하니, 궁금증으로 인한 깊이 시간 낭비를 막을 수 있었다.
- 어디서 잘 동작하지 않았는가?
    - 처음에는 Spring에 있는 gradle 관련 공식문서를 읽으면서, 공부를 하려고 했다.
- 왜 그런가?
    - 처음 접하는 단어들이 많아서, 이해가 안됨. (ex `o.spring.dependency-management`) 그리고 그 단어가 무슨 의미인지도 모름. 이해안됨.
    - 내가 영어를 읽는데 친숙하지 않다. 공식문서를 읽는 게 어렵다.

AI를 통해, 전체적인 흐름을 파악한 뒤, 세부 목표를 잡는것도 괜찮아보인다.

# Version 3
## 처음 개념을 배우는 경우.
목적: “이 기술이 무엇이고, 왜 필요한지 감 잡기”

1. 큰 목표를 적고, 작은 학습 질문을 구체적으로 적는다.
    - 처음 배우는 개념이라 어떻게 학습 질문을 적어야할 지 정말 모르겠다면 다음 프롬프트 도움을 받아보자.
    - 다만, 내가 진짜 궁금해서 던지는 학습 질문을 놓치지 말자.
```text
"내가 지금 [새로운 기술 X]를 처음 배우려고 해. 내 목표는 [큰 목표]야. 
이 기술을 깊이 있게 이해하기 위해 내가 반드시 스스로 답해봐야 할 **'작고 구체적인 질문 5가지'**만 뽑아줘. (단, 초보자가 실험으로 검증할 수 있는 수준이어야 해)"
```
2. 공식문서로 바로 들어가지 않고,
   AI에게 “최소 비교 실험”을 설계해달라고 한다.
```text
// 추천 프롬프트

나는 [기술명]을 처음 배우고 있다.  
  
목표는 [학습 질문]을 이해하는 것이다.  
  
공식문서를 읽기 전에,  
이 기술이 있을 때와 없을 때의 차이를 비교할 수 있는  
아주 작은 실험 프로젝트를 설계해줘.  
  
조건:  
1. 30분 안에 실행 가능해야 한다.  
2. 파일 수는 최소로 해줘.  
3. 실행 결과로 차이가 바로 보여야 한다.  
4. 실험 후 관찰해야 할 포인트를 알려줘.  
5. 아직 깊게 들어가지 않아도 되는 개념은 따로 표시해줘.
```
3. 기술이 있을 때와 없을 때,
   또는 옵션 A와 옵션 B의 차이를 작은 프로젝트로 직접 실행해본다.
4. 실행 결과를 관찰한다.
    - 무엇이 편해졌는가?
    - 무엇이 자동화되었는가?
    - 무엇을 직접 하지 않아도 되었는가?
    - 어떤 에러가 발생했는가?
5. 그다음 공식문서/블로그/AI를 사용해서
   내가 관찰한 현상에 정확한 이름을 붙인다.
6. 학습 내용을 정리한다.
    - A는 B이다.
    - A가 없으면 무엇이 불편한가?
    - A를 쓰면 무엇이 달라지는가?
    - 내가 직접 확인한 차이는 무엇인가?
    - 아직 모르는 것은 무엇인가?
    - 덮어보고 다시 글로 써봐라.
7. 시간이 남으면 적어두었던 호기심 중,
   현재 목표와 연결되는 것만 깊게 탐구한다.

### **깊이감 있게 공부하는 학습법**
목적: “내부 원리, 경계 조건, 설계 이유까지 설명하기”

1. 깊게 이해하고 싶은 내용에 대해 학습 질문(목표)을 구체적으로 적는다.
    - 나쁜 목표 예: DB 인덱스 공부하기, OS 프로세스 공부하기
    - 좋은 목표 예: DB는 왜 어떤 쿼리에서 인덱스를 타고, 어떤 쿼리에서는 타지 않을까?
    - 왜 이것은 이렇게 동작하는가?, 무엇이 없으면 어떤 문제가 생기는가?, 어떤 조건에서 결과가 달라지는가?, 어떤 선택지가 있고, 각각의 비용은 무엇인가?
2. 정상적으로 동작하는 정상적으로 동작하는 최소 상황을 실험해본다.
    - 설정, 예상, 결과 관찰한 점을 반드시기록한다.
3. 일부러 불편한 상황을 만들어본다.
    - 이 기술이 없다면 무엇이 불편한가?
    - 사람이 직접 처리해야 하는 일은 무엇인가?
    - 실수하기 쉬운 지점은 어디인가?
4. 조건을 바꿔가며 비교 실험한다.
    - 조건 A:
    - 조건 B:
    - 예상 차이:
    - 실제 차이:
    - 왜 차이가 발생했는가:
5. 내부 흐름을 파악한다. 겉으로 보이는 결과 대신 안에서 실제로 무슨 일이 일어나는 지 파악한다.
    - ex 디버깅을 통해 내부 흐름을 파악
    - 시각화 자료(그림, 표)를 활용해 정리해본다.
6. 에러/경계를 실험해본다. -> 기술의 경계선을 파악한다.
7. 가능하면 작은 버전을 직접 구현한다.
    - 이 기능을 직접 만들려면 어떤 정보가 필요한가?
    - 어떤 상태를 저장해야 하는가?
    - 어떤 순서로 처리해야 하는가?
    - 어디서 복잡도가 생기는가?
8. 공부한 것들을 내가 스스로 설명해본다.
    - 이 주제는 어떤 문제에서 출발하는가?
    - 정상적으로는 어떻게 동작하는가?
    - 내부에서는 어떤 흐름으로 처리되는가?
    - 어떤 조건에서 깨지거나 달라지는가?
    - 왜 그런 결과가 나오는가?
    - 실무에서는 어떻게 판단해야 하는가?
    - 아직 모르는 것은 무엇인가?
