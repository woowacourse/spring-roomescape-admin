### 실제 학습 과정

### 1. 학습 포인트 발견 과정

이전 학습 로그에서 `Reservation`, `ReservationTime`을 record로 구현하는 것이 적절하다고 판단했었다. 그러나 개선 포인트를 찾는 과정에서 이 판단이 맞는지 다시 의문이 생겼다.
record가 불변을 보장하고 코드가 간결하다는 이점은 알고 있었지만, Entity와 Value Object의 관점에서 적절한 구현 방식인지 명확히 알지 못했다.

### 2. 학습 내용 요약

#### **Entity vs Value Object 핵심 차이**

Entity는 고유한 식별자(id)로 동일성을 판단하고 독립적인 생명주기를 가진다. Value Object는 id가 없고 값 자체로 식별되며 다른 객체에 종속된다.

예를 들어 같은 이름, 같은 날짜의 예약이 두 개 있어도 id가 다르면 다른 예약이다. 이것이 Entity다. 반면 `Money(1000, "KRW")`는 id 없이 값 자체가 동일하면 같은 것이다. 이것이
Value Object다.

#### **record와 Entity의 충돌**

record의 `equals()`는 모든 필드를 기준으로 비교한다. 그러나 Entity는 id로만 동일성을 판단해야 한다. 즉 record로 Entity를 구현하면 동일성 판단 방식이 Entity의 원칙과 맞지
않는다.

#### **`Reservation`, `ReservationTime`은 Entity인가 Value Object인가**

둘 다 별도 테이블이 있고 독립적인 CRUD가 존재한다. 즉 Entity다. 따라서 record보다 class로 구현하고 id 기반 `equals()`를 갖는 것이 이론적으로 맞다.

#### **그러나 현실적인 트레이드오프**

현재 코드에서 `equals()`를 직접 사용하는 곳이 없어 실질적인 문제는 발생하지 않는다. record가 주는 코드 간결성과 불변의 의미 전달이라는 이점도 있다. 그러나 이론적 정확성을 위해 class로 변환하는
것이 맞다고 판단했다.

**코드에 반영**

`Reservation`, `ReservationTime`을 class로 변환했다.
