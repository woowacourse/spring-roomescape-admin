## v1(학습법 튜닝 이전에 사용하던 방식)
문제정의 -> 쪼개기 -> 실험 -> 피드백 -> 균열 -> 성장

1. 문제정의 & 쪼개기
문제를 한 번에 해결하려 하지 않고, 해결 가능한 단위로 쪼갭니다.
이때 범위를 가능한 것 / 될 것 같은 것 / 불가능한 것으로 나누고,
'될 것 같은 것' 중에서 컴포트 존을 약간 벗어난 영역을 선택합니다.

2. 실험 설계 (가설 & 지표)
문제를 해결하기 전에, 가설과 이를 검증할 지표를 함께 설정합니다.

예를 들어,
"다형성을 적용하면 기존 코드의 변경 지점이 줄어들 것이다"라는 가설을 세우고
변경되는 코드의 범위를 기준으로 이를 검증합니다.

이 과정에서
다른 사람의 사례를 관찰하거나, 키워드를 기반으로 자료를 탐색하며
가설과 지표를 구체화합니다.

3. 실험 (집중 실행)
실험 단계에서는 하나의 관점에만 집중합니다.
예를 들어 "낮은 결합도"를 목표로 잡았다면,
다른 요소는 의도적으로 배제하고 해당 기준만으로 구현합니다.

이는 여러 요소를 동시에 고려할 경우,
어떤 선택이 결과에 영향을 미쳤는지 파악하기 어렵기 때문입니다.

4. 피드백
이후 스스로 점검하고, 동료와의 토론, 리뷰어의 피드백을 통해 결과를 검증합니다.
이때 초기 가설이 틀렸을 가능성을 항상 열어두고,
가설의 근본부터 다시 확인합니다.

5. 균열 -> 성장
가설과 결과가 어긋나는 순간, 기존의 사고에 균열이 발생합니다.
저는 이 균열을 실패로 받아들이지 않고,
다음 시도를 위한 학습의 기회로 활용합니다.

이 과정을 반복하며 점진적으로 사고를 확장해 나갑니다.



Level1 사례

문제정의
블랙잭 미션에서 리뷰어로부터 OCP 위배 가능성에 대한 피드백을 받았습니다.

쪼개기
OCP의 여러 요소 중 '낮은 결합도'에 집중했습니다.

가설 & 지표 설정
"다형성을 적용하면 기존 코드의 변경 지점이 줄어들 것이다"라는 가설을 세웠습니다.

실험
인터페이스와 추상화를 활용해 다형성을 적용했습니다.

피드백
리뷰어로부터 "과한 interface 사용"라는 피드백을 받았습니다.

균열
낮은 결합도에 집중한 결과, 오히려 응집도가 낮아져
구조가 더 복잡해졌다는 점을 인식했습니다.

성장
결합도와 응집도 사이에는 균형이 필요하며,
특정 원칙을 과도하게 적용하는 것이 오히려 문제를 만들 수 있다는 것을 깨달았습니다.

## v2 (학습법 튜닝 과정)
### 0. 정의

목적: 기존 학습 방식의 한계를 확인하고, 새로운 학습 자원을 탐색한다
성격: 방법론 ❌ / 탐색 실험 ⭕

### 1. 왜 시도하는가?

기존 방식(v1)은 다음과 같은 특징이 있었다.
- 가설 기반 학습
- 피드백 중심 반복
- 특정 개념에 대한 깊이 확보

하지만 다음과 같은 한계를 경험했다.
- 학습 자원이 제한적이었다 (문서, 코드, 리뷰 중심)
- 새로운 개념을 빠르게 탐색하는 데 시간이 오래 걸렸다
- 모르는 것을 모르는 상태에서 시작하기 어려웠다

판단: 문제 해결 능력은 있었지만, 탐색 속도가 느렸다

### 2. 실험 가설
AI를 학습 과정에 적극적으로 활용하면
탐색 속도를 높이고, 학습 진입 장벽을 낮출 수 있다

### 3. 실험 환경
   기존 학습 방식(v1)을 유지한 상태에서 진행
   새로운 개념(DB, SQL 등)을 빠르게 습득해야 하는 상황
   AI 사용에 대한 기존 거부감 존재
따라서: 기존 방식 위에 AI를 "보조 수단" 으로 얹는다

### 4. 적용 전략
####   4-1. AI 활용 방식 변화

기존: 내가 관심이 없는 부분은 AI를 이용해서 대충 구현
변경: 초기 탐색 단계부터 사용

사용 방식:
- 공식 문서 요약 요청
- 개념 이해를 위한 질문 요청
- 빠른 예제 코드 생성

목적: "모르는 상태"를 빠르게 벗어나기 위함
#### 4-2. 학습 흐름
- AI를 통해 개념의 큰 그림 파악
- 필요한 부분만 선택적으로 학습
- 이후 코드 구현 진행

특징:깊이보다는 진입 속도 우선
#### 4-3. 기존 방식과의 결합
핵심 문제 해결 과정은 v1 유지
AI는 탐색 단계에서만 적극 사용

 구조: AI (탐색) → v1 (실험 & 검증)

### 5. 관찰 포인트
- AI를 사용했을 때 학습 시작 속도가 빨라지는가?
- 개념 이해 없이 코드 작성으로 이어지는가?
- AI 의존도가 높아지는가?
- 깊이 있는 학습이 방해받는가?
- 
### 6. 결과 및 한계 인식
이 실험을 통해 다음을 확인했다.

AI는 빠른 학습에는 효과적이다. 
하지만 깊이 있는 이해로 이어지지 않을 수 있다.
문제 해결 과정 자체는 여전히 v1 방식이 더 효과적이다.


### 7. v3로의 전환

v1, v2를 통해 다음을 인식했다.

v1: 깊이를 학습하는 방식에는 효율적이지만, 다양하고 폭넓은 지식을 학습하기에는 적합하지 않다.
v2: AI를 활용한 학습은 효율적이지만, 활용 방식에 따라 그 수준이 너무 달라진다.

현실적으로 목요일 6시까지 미션을 제출하면서, 학습을 하기 위해서는 넓고 얕은 학습이 필요하다.
하지만 사이클을 반복하면서 깊이를 늘려간다면 깊이감을 더할 수 있다. - [나선형 학습](https://techcourse.woowahan.com/s/2IGLiKp8/ls/tBaSPAGQ) 참고

## v3(나선형 학습과 AI를 이용한 사이클 반복)

학습법 v3

0. 정의
   목적: 최적화 ❌ / 경험 수집 ⭕
   성격: 방법론 ❌ / 실험 설계 ⭕

1. 왜 시도하는가?
   기존 방식:
- 흥미 있는 부분 → 깊게
- 나머지 → 얕게 처리

결과:
- 특정 영역(OOP)은 깊어짐
- DB/SQL 등은 구조 없이 처리됨

판단: 특정 방식이 아니라 상황에 맞는 전략 선택 능력이 필요하다

2. 실험 가설

반복 기반 학습(나선형 요소) + AI 활용을 통해
짧은 시간 내에도 넓이와 최소한의 구조를 확보할 수 있다

3. 실험 환경 제약
- 미션 마감 존재 (목요일 6시)
- 시간 제한 있음
- 모든 개념을 깊게 학습하면서 제한 시간을 지키기는 불가능

따라서: 완전한 나선형 학습이 아닌, 일부 요소를 의도적으로 차용한다

4. 적용 전략
   4-1. 반복 구조 (핵심)

> 반복 단위 = 제출 → 리뷰

- 미션 제출
- 리뷰 수신
- 문제된 개념 재학습
- 다시 적용

특징:
계획된 반복 : 선택
피드백 기반 재방문: 필수

4-2. 나선형 요소 (부분 적용)

같은 개념을 여러 번 다시 만나되, 맥락을 바꿔 적용

처음: 개념 이해 수준 -> 코드 적용
이후: 리뷰 기반 수정 -> 리뷰가 없다면
리뷰가 없다면? - 1,2,3,4 파트별로 리뷰가 없는 부분은 의식적으로 다시 확인.

깊이는 자연스럽게 증가하도록 둠 (의도적 통제 X)

4-3. AI 활용

기존: 필요할 때만 사용
지금: 학습 진행을 위한 주요 도구

사용 방식:
- 공식 문서 기반 질문 생성 요청
- 정답 대신 사고 유도
- 막힐 경우 제한적 정답 허용
    - 3시간 이상 정체 시 개입 허용

4-4. 시간 전략
- 각 단계 시간 제한 설정
- 일정 초과 시: 이해보다 진행을 우선
    - 사이클 유지 > 완벽한 이해

5. 실험 원칙
1) 깊이보다 반복
- 한 번에 완벽히 이해하지 않음

2) 문제 발생 지점 중심 학습
- 필요할 때만 깊게 들어감

3) 전략도 실험 대상
- 방법 자체를 계속 의심

6. 관찰 포인트 (중요)
   이건 “성공 기준”이 아닌 관찰 대상.
- 리뷰가 없어도 재방문하는지? -> 어떻게하면 강제로 재방문 할지
- AI를 이용한 학습 방식이 이전 AI를 사용하지 않던 방식에 비해 어떻게 좋은지.
- 같은 개념을 다시 만났을 때 인식이 달라지는가?
- 얕은 학습이 구조를 만드는 데 도움이 되는가?

7. 이 실험의 본질

이 실험은 “정답 찾기”가 아니라,
다른 방식으로 학습했을 때 어떤 경험이 발생하는지 확인하는 과정입니다.
