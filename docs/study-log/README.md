```text
레벨1에서는 먼저 코드를 작성해보고, 막히면 강의나 책, AI, 공식문서를 참고하는 방식으로 학습해왔다.

모르는게 있으면 예전에는 AI에게 먼저 물어보는 편이었지만, 장기 미션부터는 공식문서처럼 신뢰할 수 있는 자료를 직접 찾아보려 노력했다.
다만 공식문서를 찾는 데 시간이 오래 걸리고, 문서만으로는 좋은 사용법이나 동작 원리까지 알기 어려워 블로그나 AI에 다시 의존하기도 했다. 또 책이나 강의를 통해 개념을 이해하려 했지만, 직접 적용해보지 않으면 금방 잊어버리는 한계가 있었다.

그래서 레벨1의 나는 리뷰와 경험을 통해 배우는 데 강점이 있었지만, 완벽하게 하려다 멈추는 습관과 자료를 실제 경험으로 연결하는 연습이 부족했던 것 같다.
```

## 핵심 원칙

> **기술을 작게 쪼개고, 직접 만들고, 깨뜨리고, 설명하고, 다시 구현한다.**
>

---

## 1. 스텝 쪼개기

각 스텝은 아래 3가지만 정합니다.

```
핵심 질문:
- 이 스텝에서 이해할 것은?

최소 구현:
- 가장 작게 만들어볼 코드는?

완료 기준:
- 설명할 수 있는가?
- 다시 구현할 수 있는가?
```

예시:

```
핵심 질문:
- JWT는 서버가 사용자를 어떻게 신뢰하게 만드는가?

최소 구현:
- 로그인 성공 시 access token 발급하기

완료 기준:
- JWT 구조를 설명할 수 있다.
- 문서 없이 token 발급 코드를 다시 만들 수 있다.
```

---

## 2. 각 스텝 진행 방식

```
1. 핵심 질문 정하기
2. 짧게 개념 학습하기
3. 최소 구현하기
4. 일부러 오류 만들기
5. 30초로 설명하기
6. 다음 날 검색 없이 다시 구현하기
7. 크루와 설계 근거 공유하기
```

---

## 3. 꼭 넣을 훈련 3가지

### 1) 오류 만들기

정상 동작에서 끝내지 말고 실패 상황을 만듭니다.

예:

```
refresh token 만료
token 위조
권한 부족
DB 중복 저장
동시 주문 요청
```

이렇게 해야 기술의 내부 구조가 보입니다.

---

### 2) 검색 금지 재구현

다음 날 25분 동안 검색 없이 다시 구현합니다.

막히면 이렇게 기록합니다.

```
기억나는 것:
헷갈리는 것:
검색이 필요한 정확한 질문:
```

목적은 “봤다”가 아니라 **꺼내 쓸 수 있다**로 바꾸는 것입니다.

---

### 3) 압축 설명

구현 후 짧게 설명합니다.

```
이 기술이 해결하는 문제:
내가 선택한 방식:
비교한 대안:
선택 이유:
포기한 것:
```

예:

```
기술: Refresh Token
문제: access token 만료 후 재로그인 불편
선택: Redis에 refresh token 저장
대안: 클라이언트에만 저장
이유: 강제 만료와 탈취 대응 가능
포기한 것: 완전한 stateless 구조
```
