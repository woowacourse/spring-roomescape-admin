Spring은 2003년에 등장
-> 기존 J2EE의 복잡성 해결 목적

> J2EE가 뭐지?
> Java 기반 서버 개발 표준 플랫폼임


### 당시 문제 :
- EJB 기반 개발 -> 너무 복잡
- 강한 결합
- 테스트 어려움

> 왜 이런 문제가 생긴거지?
> EJB는 컨테이너에 강하게 의존하는 구조라서 문제가 발생함
> - 복잡함 -> 인터페이스, 설정, 배포 구조 강제
> - 강한 결합 -> EJB API/서버에 코드가 묶임
> - 테스트 어려움 -> 객체를 직접 생성하지 못하고 컨테이너 필요

> 컨테이너는 뭔데?
> 컨테이너는 객체를 생성, 관리, 실행해주는 런타임 환경임
> EJB는 Java EE Application Server라는 런타임 환경이 필요하지만, Spring은 JVM 위에서 실행 가능함


> EJB가 뭐지?
> [[EJB]]에 정리함


### Spring 해결 방식 :
- POJO 기반 개발
- DI로 결합도 감소
- 테스트 용이성 확보

### 스프링의 탄생
EJB는 컨테이너로부터 필요한 객체를 꺼내쓰는 방식으로 객체들 간의 의존성을 해결하려는 것이었지만, 비즈니스 로직에 특정 기술이 종속된다는 것이 가장 큰 문제임. 이에 2002년 로드 존슨이 이를 지적하며 책을 출간함.

특정 클래스나 인터페이스를 구현하지 않는 평범한 자바 클래스(POJO(plan old java Object))를 이용함

![[Pasted image 20260427160903.png]]

스프링은 위 그림과 같은 여러 객체들의 의존성 해결(DI) 및 제어(IOC)하며 객체들의 라이프 사이클을 관리해줌.

> 스프링 말고 다른 방식은 없었어? 왜 다 스프링을 선택한거지?
> 여러 대안들이 많았으나 기능이 조각났거나, 통합이 안되거나, 여전히 설정/복잡성 문제가 존재했음.
> 
> POJO 기반 때문에 스프링을 씀
> - 그냥 자바 객체로 개발 가능
> - 특정 기술에 종속되지 않음
>   
> MVC + DI + AOP + DB + 트랜잭션
> → 하나의 프레임워크에서 해결
>
> 그런데 왜 자바 객체로 개발 가능한게 장점임?
> 그냥 자바 기반으로 하면 결합도가 낮아지고, 테스트하기 편하고, 유지보수하기에도 편하기 떄문이다.
> 그니까 즉 프레임워크 때문에 실패할 가능성도 없고, 프레임워크 없이도 돌아가는 구조이기 때문임.
