### 1. 막힌 것의 종류

이번에 막힌 것은 어떤 종류의 어려움이었는가? (해당하는 것에 체크)

- [ ] 개념 자체를 모르겠다 (예: "스프링 빈이 뭔지 모르겠다")
- [ ] 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 (예: "JdbcTemplate 문법을 모르겠다")
- [x] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [x] 기타: 처음 접하는 개념 학습 (`@RestControllerAdvice`, `@ExceptionHandler`)

**내용**:  
크게 세 가지가 막혔다.

1. **dto 패키지 위치**: `web/dto` → `service/dto` → 도메인 패키지 루트(`dto/`)까지 총 세 번 이동했다.  
   처음엔 `web` 하위에 뒀더니 `service`가 `web`에 의존하게 돼서 계층 방향이 역전되는 느낌이었다.   
   `service` 하위로 옮겼더니 이번엔 `controller`가 `service/dto`에 의존하는 게 이상하게 느껴졌다.(`service`에 의존하는 자체가 이상한 것이 아닌, `service`계층의
   dto에 의존하는 것이 이상했다..)  
   결국 `controller`, `service`, `domain`과 동일한 레벨에 `dto` 패키지를 따로 뒀다. 구글링을 해도 각 블로그마다 위치가 달라서 나만의 결론을 제대로 내지 못한 채로 마무리됐다.

2. **service가 service를 참조**: `ReservationService`에서 `ReservationTimeRepository`를 직접 참조하다가, 계층 분리 후
   `ReservationTimeService`를 참조하도록 변경했다.   
   그런데 이렇게 하면 다른 도메인의 `service`를 참조하게 되어 도메인 간 결합이 생기는 게 마음에 걸렸다.   
   `ReservationRepository`와 `ReservationTimeRepository` 둘 다 `ReservationService`에서 직접 참조하는 것도 계층 역할이 흐릿해지는 느낌이라 싫었다.   
   Facade 패턴도 검토했지만 현재 규모에서는 오버 엔지니어링이라 판단하고 일단 `service` → `service` 참조로 해결했다.

3. **`@RestControllerAdvice` / `@ExceptionHandler`**: 직접 일일이 작성해서 해보는 것은 거의 처음이어서 동작 원리부터 찾아봤다. 코드 자체는 단순하지만 어떻게 돌아가는지
   이해하기 위해 추가로 학습을 진행했다.

### 2. 이번 타임의 학습 전략

- 이전 타임에서 바꾸기로 한 전략(DDL 작성 시 FK 참조 방향 먼저 확인)은 이번 타임에서 해당 상황이 없었다.
- 계층 분리는 처음에 도메인 구분 없이 한 번에 진행했는데, 분리 결과를 보니 `reservation`과 `reservationtime` 양쪽 구조가 `controller`, `service`,
  `repository`, `domain`으로 완전히 동일하게 나왔다. 이걸 보고 도메인별 패키지로 나누는 게 맞겠다고 판단해서 `reservation/`, `reservationtime/`으로 분리했다.
- dto 패키지 위치는 코드를 실제로 이동시켜보면서 의존 방향을 직접 보면서 판단했다. 직접 움직여보는 방식은 2단계 때도 효과적이었지만, 어느 방향이 옳은지 혼자 결정을 내리기 쉽지 않았다.
- `@RestControllerAdvice`는 동작 원리를 파악하기 위해 소스 코드를 직접 열어서 확인했고, 동작 검증은 실제 예외를 던져서 응답이 어떻게 오는지로 확인했다.

### 3. 전략 평가

**효과적이었던 것**:

- dto를 실제로 여러 위치에 옮겨보면서 의존 방향을 직접 느낀 것. service가 web에 의존하면 이상하다는 것을 직접 코드 패키지를 이동시켜 가면서 확인했다.
- `@RestControllerAdvice`를 실제로 예외를 발생시켜 응답을 확인하는 방식으로 검증한 것. 개념 이해와 동작 확인을 분리하지 않고 한 번에 처리했다.

**비효과적이었던 것**:

- dto 위치에 대해 블로그 여러 개를 읽으면서 시간을 쓴 것. 가지각색이어서 오히려 헷갈렸다. 이 시간에 나만의 기준 세우기에 집중하는 편이 나았을 것 같다.

**막힌 것의 종류와 전략의 궁합**:

- dto 위치와 service 참조 문제는 둘 다 "코드는 돌아가는데 맞는지 모르겠다"는 종류였다. 이런 막힘은 검색보다 직접 구현해보고 불편함을 느끼는 방식이 잘 맞는다는 걸 이번에도 확인했다.
- 다만 결론이 나지 않은 채로 끝난 고민(dto 위치, service 참조)은 [나중에 반드시] 태그를 달아두지 않아서 다음 미션에서 다시 같은 고민을 반복할 위험이 있다.

### 4. AI 피드백

**dto 패키지 위치에 대해**:

> dto 패키지 위치에 정답은 없지만, 결정 기준은 있다: "이 dto를 누가 만들고 누가 쓰는가"를 따라가면 된다.  
> Request dto는 controller가 받아서 service에 넘기는 객체고, Response dto는 service가 만들어 controller가 반환하는 객체다. 둘 다 controller와
> service가 함께 사용하기 때문에 어느 한쪽 하위에 두면 반대쪽이 역방향 의존을 갖게 된다.  
> 도메인 패키지 루트에 `dto/`를 두는 결정은 이 기준에서 일관성이 있다. 다음 미션에서 의심이 들면 "누가 만들고 누가 쓰는가"를 먼저 따져보는 것을 습관으로 삼아보자.

**service → service 참조에 대해**:

> service가 service를 참조하는 것이 불편하게 느껴지는 감각은 옳다. 단, 지금 규모에서 Facade를 넣는 것도 오버스펙이라는 판단도 맞다.  
> 현재 선택(service → service 참조)의 핵심 비용은 "도메인 간 결합"이다. `ReservationService`가 `ReservationTimeService`의 존재를 알게 되는 것이다.  
> 이 결합이 문제가 되는 시점은 두 도메인이 독립적으로 배포되거나 테스트될 필요가 생길 때다. 지금은 그 시점이 아니므로 현재 결정을 유지하되, 언제 이 판단이 바뀔 수 있는지를 메모해두면 나중에 리팩토링 타이밍을
> 잡기 쉬워진다. [나중에 반드시] 태그를 달아두자.
