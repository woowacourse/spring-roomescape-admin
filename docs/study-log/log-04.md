### 1. 막힌 것의 종류

- [ ] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [x] 기타: 주로 메서드 이름이나 어노테이션 정의에 대한 궁금함이어서 자료를 찾아보거나 AI를 활용해 쉽게 해결했다.

### 2. 이번 타임의 학습 전략
- 이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?

- 실제로 어떻게 학습했는지 디테일한 과정을 써보세요.

  - 비슷한 기능을 하는 메서드들이 계층별로 나누어져 있다고 생각해서 메서드명을 고민하고 변경하였다.
  - 패키지를 계층별로 나누어 정리하였다.
  - DTO 변환 책임을 Service에서 Controller로 변경하였다.

### 3. 전략 평가
- 효과적이었던 것과 그 이유
  - 패턴으로 남겨두는 것은 빠르게 학습한 것을 상기할 수 있어서 좋은 것 같다.
- 비효과적이었던 것과 그 이유
  - 비효과적이었다고 생각되는 부분은 없는 것 같다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
  - 추가로 공부해야할 것을 남기지 않는 학습이었는데, 그러한 것들이 한 눈에 표시되어서 좋다.

### 4. AI 피드백
- 자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고,
  유용했던 제안 1가지 이상 기록
  - 자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고, 유용했던 제안 1가지 이상 기록
    - 현재 학습 전략은 잘 작동하고 있으며, 특히 “막힘 → 해결 → 기록” 흐름이 안정적으로 유지되고 있음
    - 다만 이번 단계에서는 막힘이 깊지 않고 “빠르게 해결되는 궁금증” 위주였기 때문에, 단순 해결에서 끝나지 않고 패턴으로 남기는 것이 핵심
    - 핵심 제안:
      - “알게 된 것”보다 “다음에 바로 쓸 수 있는 규칙”을 남기는 데 집중한다
      - 즉, 학습 결과를 이해가 아니라 재사용 가능한 행동 기준으로 압축

### 5. 다음 타임에 바꿀 것
- 유지할 것과 그 이유
  - 막힘 해결 기록 → 문제 해결 흐름을 잃지 않고 안정적으로 진행 가능
  - 얕게 끊는 학습 → 불필요하게 깊게 파지 않고 속도 유지
  - 흐름 1줄 요약 → 단계가 올라가면서 구조 변화 인식 가능
  - 패턴 기록 → 학습 내용을 빠르게 다시 꺼내 쓸 수 있음

- 바꿀 것과 그 이유
  - 이번 단계는 구조적으로 잘 작동했기 때문에 크게 바꿀 것은 없음

## 4단계: 계층 분리

### 0. 목표/기대 설정
- **레이어드 아키텍처**로 레이어별 책임에 따라 코드를 분리한다.
- 레이어별 책임과 역할에 따라 클래스를 분리하고, 분리한 클래스를 **Spring Bean으로 등록**한다.

| 레이어                  | 책임       |
| -------------------- | -------- |
| **Controller**       | 웹 요청·응답  |
| **Service**          | 비즈니스 플로우 |
| **DAO (Repository)** | DB 접근    |
| **Domain**           | 비즈니스 규칙  |

### 2. 막힘 해결
1. DTO와 도메인 객체에도 `@Component`를 붙여줘야하나?
  - 왜 붙여야 하는지를 알 수 없음, 절대 붙이지 않는다고 함
  - 동작에 문제가 없어 붙이지 않기로 결정
2. 시간 관리 기능 계층 분리하며 삭제 테스트에 문제가 있는 것을 발견
  - 미리 넣어둔 데이터 + 테스트에서 새로 집어넣은 데이터 때문에 테스트에서 강제로 id 1번을 삭제하는데, 이미 삭제해두어 실패발생
  - id AUTO_INCREMENT가 1부터 다시 부여될 수 있도록 삭제 쿼리 수정
    - `jdbcTemplate.update("DELETE FROM reservation_time;");`
    - `jdbcTemplate.update("ALTER TABLE reservation_time ALTER COLUMN id RESTART WITH 1;");`
3. Controller, Service, Dao 메서드 명 고민
  - AI의 도움을 받아 해결
  - Controller: HTTP API 동작 이름
  - Service: 유스케이스 이름
  - DAO: DB 접근 방식 이름

### 3. Output 생성
- 계층 분리 및 패키지 분리
- Service 계층 추가
- DTO 변환 책임 Controller로 리팩터링
- 테스트 코드 작성

**전체 흐름**
프로그램 실행 -> 테이블 생성 -> 기본 예약 시간 데이터 추가(선택할 수 있도록)
예약 요청 -> Controller -> service -> Dao -> DB -> 응답 반환

**패턴**
메서드 명이 고민되면
1. 클라이언트의 입장에서 요청하는 내용을 표현하는 메서드 이름을 고려한다.
2. 아래 정리 내용을 참고한다.
  - Controller: HTTP API 동작 이름
  - Service: 유스케이스 이름
  - DAO: DB 접근 방식 이름
