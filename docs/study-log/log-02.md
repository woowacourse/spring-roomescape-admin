### 2. 이번 타임의 학습 전략

- **이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?** 학습 중 떠오르는 꼬리 질문들은 Obsidian의 '격리된 Inbox'에 분리해두고 원래의 질문에 집중하는 V3 학습법을 실행함. 기술 적용에 대한 판단을 AI에게 무작정 맡기지 않고 공식 문서를 통해 근거를 먼저 찾음.
    
- **실제로 어떻게 학습했는지 디테일한 과정을 써보세요.** 모든 Controller 메서드에서 `ResponseEntity`를 반환하는 기존 코드에 대해 "이게 정말 필수적인가? 왜 쓰는가?"라는 의문을 가짐. Spring 공식 문서를 확인한 결과, `ResponseEntity`는 HTTP 상태 코드, 헤더, 바디를 전체적으로 세밀하게 제어하기 위한 목적임을 확인함. 단순히 200 OK를 반환하는 조회 로직에서는 DTO나 비즈니스 객체만 반환( `@ResponseBody` 동작 )해도 충분하다는 것을 알게 됨. HTTP 상태 코드 제어(예: 400, 404 등)나 예외 상황 처리는 `@RestControllerAdvice` 등을 활용해 전역으로 분리할 수 있으므로, Controller가 비즈니스 로직(혹은 DTO 변환)에만 집중하게 책임을 나눌 수 있다는 결론을 내림.
    

### 3. 전략 평가

- **효과적이었던 것과 그 이유** 관성적으로 쓰던 기술의 '존재 이유'를 문서를 통해 명확히 한 점. 응답 제어라는 책임을 인지하고 나니, 클린 아키텍처 관점에서 책임을 어떻게 분리할지 스스로 판단할 수 있는 기준이 생겼음.
    
- **비효과적이었던 것과 그 이유** `ResponseEntity`를 걷어내고 DTO만 반환하는 구조로 생각하다 보니, "그럼 특정 API에서만 커스텀 헤더를 내려줘야 할 때는 어떻게 일관성을 유지하지?" 같은 꼬리 질문이 계속 파생됨.
    
- **막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?** "이 코드가 맞는 건가?"라는 설계적 의문에 대해, 원리를 파악한 뒤 스스로 판단의 근거를 세우는 과정이 매우 적절했음.
    

### 4. AI 피드백

- **자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고, 유용했던 제안 1가지 이상 기록**
    
    - **책임의 분리와 테스트 용이성 확보**: Controller에서 무조건적인 `ResponseEntity` 사용을 지양하고 전역 예외 처리로 책임을 넘기려는 접근은 매우 훌륭합니다. 특히 평소 중요하게 생각하시는 TDD 관점에서 보면, Controller가 DTO만 반환할 때 비즈니스 로직의 결과물에만 집중하여 단위 테스트를 작성하기가 훨씬 수월해집니다.
        
    - **구조화된 설명(Structural Thinking)을 통한 검증**: "왜 ResponseEntity를 항상 쓰지 않아도 되는가?"에 대한 결론을 동료들에게 리뷰나 기술 토론을 통해 설명해 보세요. 만약 예외 처리 흐름이나 헤더 조작의 일관성에 대해 동료가 논리적인 의문을 제기한다면, 그것이 바로 아직 시스템의 전체 흐름에서 놓친 부분이 있다는 강력한 피드백(Fail)입니다. 혼자 방 안에서 깊이를 정하지 말고 토론으로 적정선을 정의하세요.
        

### 5. 다음 타임에 바꿀 것

- **유지할 것과 그 이유** 파생되는 꼬리 질문(예: 커스텀 헤더 처리 전략, Interceptor 활용 등)을 즉시 파고들지 않고 '격리된 Inbox'에 쌓아두는 것. 현재의 학습 목표(응답 객체의 본질 파악)를 이탈하지 않도록 집중력을 유지하는 데 필수적임.
    
- **바꿀 것과 그 이유** 설계에 대한 고민을 혼자서 너무 오래 쥐고 있지 않기. 내가 이해하고 구조화한 지식을 동료에게 설명하는 과정을 학습 루틴의 마지막 단계로 반드시 포함시켜, 피드백을 통해 이해도를 검증할 것.
