### 2. 이번 타임의 학습 전략

제공된 학습 테스트를 기반으로 학습하고 직접 공식문서를 기반으로 AI 없이 학습해보기
학습 과정에서 AI를 판단의 기준을 평가받는 리뷰어로 사용한다.

이를 하기 위해서 먼저 제공된 Spring 테스트를 기반으로 전체적으로 JdbcTemplate의 동작 방식에 대해서 한 번 훑어본 뒤 바로 구현에 들어감.
막히는 지점이 있으면 그것에 대한 컨텍스트를 제공하고 AI로부터 공식문서 링크를 끌어온 뒤 이를 읽으면서 해결해보고자 하였음.
구현 과정에서는 직접 구현해본 뒤, 이에대한 평가를 AI로부터 받아내며, 내가 미처 닿지 못한 부분들을 채울 수 있었음.

예를 들어서 기존 1단계에서 작성한 Controller 테스트 코드가 DB로 수정하는 과정에서 JdbcTemplate을 Controller의 생성자로 주입해주어야 했다.
따라서 Repository 계층을 나누어 처리해볼까 고민하다가, 일단 만들고 리펙토링을 하기 위해서 따로 repository계층을 도입하는 대신
dataSource를 따로 Controller테스트의 @BeforeEach 에서 매번 생성 시에 jdbcTemplate을 직접 생성해서 주입시켜주는 방향으로 진행하는 식으로 생각했고,
이에 대한 AI로부터의 피드백을 받아보았다.

### 3. 전략 평가

#### 효과적이었던 점

AI를 기반으로 나의 선택에 대해 평가를 받게 되니, 단순한 막연함이 사라지고, 판단의 기준을 더욱 발전시켜나갈 수 있었음.

#### 비효과적이었던 점

AI를 사용하게 되니, 문제가 발생하는 상황에서 나도 모르게 습관적으로 빠르게 해결책을 얻어내려고 하는 경향이 종종 나타났음.

#### 막힌 것에 대한 것과 전략의 궁합

디버깅을 AI로 바로 수정해버리면, 성장에 큰 도움이 되지 않는 거 같다.

### 4. AI 피드백

현재 전략의 약점:

- 구현 판단에는 AI를 리뷰어로 잘 쓰고 있는데, 디버깅 순간에는 AI가 너무 빨리 “정답 생성기”가 된다.
- 문제가 생겼을 때 증상에서 원인까지 가는 중간 가설을 세우고, 어느 계층에서 깨졌는지 분리해 확인하는 과정이 어려웠다.

디버기에 대한 관점을 바꿔봐라. 디버깅은 코드를 고치는 활동이 아니라, 내 머릿속 실행 모델과 실제 시스템의 차이를 줄이는 활동이다.

예상: JSON 요청 -> DTO 생성 -> 값 검증 -> SQL 실행 -> DB 저장 -> 생성 id 반환
실제: 어느 지점에선가 예상과 다르게 동작함

디버깅은 이 두 흐름의 차이를 좁히는 작업

#### AI의 해결책

AI에게 해결책을 묻기 전에, 반드시 “디버깅 스냅샷”을 먼저 작성한다.


### 5. 다음 타임에 바꿀 것

이전의 학습법은 그대로 가져가되, 아래의 디버깅 방법을 추가한다.
문제가 발생하면 AI에게 바로 해결책을 요청하지 않고, 먼저 디버깅 스냅샷을 작성한다.

- 기대한 동작
- 실제 동작
- 현재 가설
- 확인할 가장 작은 실험

AI에게는 정답 코드가 아니라 내 가설의 타당성과 다음 관찰 포인트를 요청한다.

### 단계 전환 체크

- 공식문서를 기반으로 AI 없이 학습해보며, 학습 과정에서 AI를 판단의 기준을 평가받는 리뷰어로 사용한다. 는 그대로 유지
- 이 것에 더불어 디버깅 시에는 디버깅 스냅샷을 작성하고 가설을 세운 뒤 멘탈모델을 평가받는식으로 추가한다.
- 3단계에서는 테스트로 학습할 수 있는 경우가 없으므로, 일단 해보면서 계속해서 AI로부터 피드백을 받자.

이는 디버깅 시에는 AI의존도가 높다는 문제가 있고 이를 해결하기 위함이다.
