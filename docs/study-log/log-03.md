### 2. 이번 타임의 학습 전략

이번 타임의 학습 전략은 이전 전략의 “학습 목표와 완료 조건 작성”을 유지하면서, 학습 진행 유형에 따른 도구 선택 기준표를 재정립한 버전으로 수행해 보는 것이다. 또한, 기존 “도구 선택” 이라는 명칭에서 “접근
방법”으로 수정했다.

학습 유형에 따라 접근 방법을 다음과 같이 재정립해보았다:

| **막힌 유형**               | 접근 방법                                  |
|-------------------------|----------------------------------------|
| 개념 자체를 모르겠다             | AI에게 완료 조건을 함께 전달하며 질문                 |
| 개념은 알지만 사용법을 모르겠다       | 공식 문서 또는 포스팅 우선 참고                     |
| 코드는 돌아가는데 이게 맞는 건지 모르겠다 | 학습의 완료 조건은 “이 설계를 선택한 근거를 말할 수 있다”로 설정 |

#### 실제 학습 과정

1. **학습 포인트 발견 과정**
   인텔리제이가 도메인 클래스에 대해 Record로 변환하길 제안하는 것을 발견했다.
    - Record는 DTO나 불변 객체를 표현할 때 사용한다는 것은 알고 있었다. 그러나 도메인 객체에도 적용하는 것이 적절한지, 기존에 익숙하게 사용해온 Class 선언 방식과 어떤 차이가 있는지는 명확히
      알지 못했다. 따라서 이 부분에 대한 학습이 필요하다고 느꼈다.
2. **학습 전략 적용**
    - **학습 목적 및 완료 조건 명시 (나선형 학습으로 2단계 진행)**
        - 1단계
            - 목적: 도메인 객체를 구현할 때 Class로 선언하는 것과 Record로 선언하는 것의 차이를 이해한다.
            - 완료 조건: 도메인 객체를 구현할 때 왜 Record로 구현했는지 설명할 수 있다.
        - 2단계
            - 목적: Record의 사용 범위를 이해한다.
            - 완료 조건: Record를 무조건 사용하는 것이 좋은가?에 대한 나의 의견을 말할 수 있다.
    - **학습 내용 요약**
        - **Class vs Record 핵심 차이 이해**
          Class로도 모든 필드를 `final`로 선언하면 불변을 보장할 수 있다. 그러나 생성자, `equals`, `hashCode`, `toString`을 직접 작성해야 한다. Record는 이를
          자동으로 제공하며, 코드만 보고도 **"이건 불변 데이터다"** 라는 의도가 명시적으로 드러난다는 점이 핵심 차이다.
        - **"수정"에 대한 관점 전환**
          만약에 예약을 수정하는 API가 생기면 Record를 쓸 수 없다고 생각했으나, Record는 객체 자체의 상태 변경을 금지할 뿐 새로운 객체로 교체하는 것은 허용한다. 즉 숫자 `3` 자체는
          변하지 않지만 `x = 4`로 재할당은 가능한 것과 같은 원리다.
        - **Record의 사용 범위**
          기술적으로는 상태가 변하는 객체도 새 객체 교체 방식으로 Record를 쓸 수 있다. 그러나 Record를 보는 사람은 "이건 안 바뀌는 데이터구나"라고 읽기 때문에, 상태가 변하는 객체에
          Record를 쓰면 코드의 의도가 흐려진다. 따라서 **상태가 변하지 않는 객체에 Record를 쓰는 것이 좋으며, 무조건 쓰는 것은 좋지 않다.**
    - **코드에 반영**
        - 학습 진행 후, 현재 작성한 도메인 클래스 (Reservation, ReservationTime)에 대해서 Class로 선언하는 것 보다 Record로 선언하는 것이 좋다고 판단해 반영하였다.
        - 판단의 이유는 Reservation과 ReservationTime 모두 상태가 변하지 않는 객체이고, 추후에 수정 기능이 추가되더라도 새 객체로 교체하는 방식을 적용하면 된다고 생각한다.
          Record가 제공하는 메서드와 불변을 보장해주는 것이 이점이 크다고 판단했다.

### 3. 전략 평가

- **효과적이었던 것**
    - 학습 목표와 완료 조건을 명시한 덕분에 학습 범위가 명확했다. 나선형 학습으로 자연스럽게 깊이를 더할 수 있었고, 1단계 완료 후 2단계로 이어지는 흐름이 자연스러웠다.
    - 완료 조건을 "설명할 수 있다"로 설정한 덕분에 단순히 읽고 끝내는 것이 아니라 스스로 말로 정리하는 과정이 학습을 확실히 마무리하는 데 도움이 됐다.
- **비효과적이었던 것**
    - AI가 샛길을 과잉 차단하는 경우가 있었다. 샛길인지 아닌지는 스스로 판단해야 하는 부분인데, AI가 먼저 막아버리면 그 판단 기회 자체를 잃게 된다. 앞으로는 AI에게 샛길 차단을 맡기기보다 스스로 "
      이게 지금 학습 목표와 관련 있는가?"를 판단하는 연습이 필요하다.
- **1번에서의 막힌 것의 종류와 현재 학습 전략의 궁합**
    - 이번 막힌 유형은 "코드는 돌아가는데 이게 맞는 건지 모르겠다"였고, 전략표에 따라 완료 조건을 "이 설계를 선택한 근거를 말할 수 있다"로 설정했다. 궁합은 좋았다. 단순히 Record 문법을 익히는
      것이 아니라 왜 쓰는지를 설명할 수 있는 수준까지 도달했기 때문이다.

### 5. 다음 타임에 바꿀 것

- **유지할 것과 그 이유**
    - 학습 목표와 완료 조건을 명시하는 전략은 유지한다. 학습 범위를 스스로 통제할 수 있었고, 완료 시점을 명확히 판단할 수 있었기 때문이다.
    - 나선형 학습 방식도 유지한다. 1단계에서 기초를 잡고 2단계에서 깊이를 더하는 흐름이 자연스럽고 효과적이었다.
- **바꿀 것과 그 이유**
    - 샛길 차단은 AI에게 맡기지 않고 스스로 판단한다. "이게 지금 학습 목표와 관련 있는가?"를 스스로 묻는 습관을 들이는 것이 장기적으로 더 중요하다고 판단했다.
