<div markdown="1">

1. **Problem-Driven**
   > 이걸 왜 공부하지? 먼저 정의

   예시: “Controller 왜 쓰지?”, “서비스 레이어 왜 나누지?”

2. **i+1**
   > 한번에 하나의 키워드만 정해서 무엇인지만 이해하기

   - ❌ “Spring MVC 전체”
   - ✅ “@Controller 역할 하나만”
3. **Input**
   > 만든 결과물을 AI를 통해 검증
4. **Output**
   > 가설을 설정하고 직접 만들어보기
   가설은 아무자료 없이 사전 지식으로만
   - @Controller는 ~~일 것이다.
   - Controller 없이 코드 작성해보기

5. **Self-Explanation**
   > - Output 내용을 기반으로 해당 학습내용을 스스로 설명해보기 막히는 경우, 해당 부분만 다시 AI에게 Input.
   > - 최종적으로 학습했던 것 정리 노트 만들기

6. **Takeaways**
   > - 학습한 내용 최종 정리하기 
   > - 이전처럼 전체 개념 정리 X
   - 핵심 개념
     - 적용한 결과물
     - 다음에 적용할 것
     
       예시:
         - 다음부터 HTTP 요청 처리 로직은 Controller에만 둔다
         - 비즈니스 로직은 절대 Controller에 넣지 않는다
7. **Backlog**
   > - 나중에 알아야 할 것 같은 개념이나 더 깊은 개념이 있다고 느껴지는 부분 기록 해두기. 
   > - 학습은 추후 Problem Driven이 확고해질 때 다시(예: 프로젝트 하다가 막힌 경우)

### 3. 전략 평가
- 효과적이었던 것과 그 이유
- 비효과적이었던 것과 그 이유
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?

효과적이었던 것은 `Problem Driven`을 통해 학습 이유를 설정하고 `i+1`을 통해 학습 범위를 제한하는 것이었다.
당장 필요한 내용만을 공부하다보니 빠르게 궁금증을 해소할 수 있었다. 
또한 바로 정답을 보기 보다는 먼저 정답에 대한 가설을 내려보고 실제로 증명해보면서 해당 주제에 대해서 더 깊게 생각해볼 수 있었고 
관련된 다른 주제도 새로 알게 될 수 있었다.

비효과적이었던 것은 학습이 끝나고 최종적으로 정리하는 `Takeaways` 과정이었다. 다 학습을 한 뒤 마지막에 한번 더 문서로 정리하면
나중에 해당 내용을 다시볼 때 편할 것 같아서 넣었던 과정이었는데, 
막상 해보니 그전까지 과정을 거치며 적어놨던 부분들에서 크게 벗어나지 않는다는 것을 알게되었다. 
같은 일을 두 번 하는 것 같은 느낌이 들었다.

막힌 것과 전략의 궁합은 아주 좋았다고 생각한다. 미션을 하다보면 요구사항 중 내가 모르는 내용이 나오는 경우가 많을 것 같은데,
그럴 때 빠르게 한번 학습 한 뒤 미션을 이어나갈 수 있을 것 같다.
