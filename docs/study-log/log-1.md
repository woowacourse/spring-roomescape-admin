### 2. 이번 타임의 학습 전략

**이전에 바꾸기로 한 전략**: v3 프레임워크 적용 (실제 문제 출발 → 한 문장 정의 → 아는 것/모르는 것 분리)  
**실행 여부**: 실행함

**실제 학습 과정**:

**1단계 (실제 문제 출발)**: "예약 API에서 연관관계 테이블을 어디서 어떻게 조회할까"에서 출발

**2단계 (한 문장 정의) + 3단계 + 4단계 (혼자 생각하기)**: 세 가지 선택지를 스스로 정리하고 각각의 장단점을 먼저 혼자 분석

**5단계**: 구글링을 통해 관련 지식을 조사

**6단계 (AI 질문)**: 
- JDBC 환경이라는 제약 조건을 명시해서 ORM 전제의 조언을 걸러냄 
- 이해 안 되는 부분은 즉시 파고들음
- 답변에 대한 되물음으로 답변 검증

**실제 적용**: API 스펙(`POST /reservations`)을 가져와서 배운 원칙을 적용
    - `findAllWithTime` 네이밍
    - `save` 메서드 설계
    - id 없는 객체 문제

### 3. 전략 평가

**효과적이었던 것**:  
먼저 혼자 장단점을 정리한 질문하는 흐름이 좋았다. 본인의 분석이 꽤 정확했다는 확인을 받으면서도, 관계 방향(to-one vs to-many)이라는 새로운 판단 기준을 얻었다. 또한 추상적 원칙에서 멈추지 않고 실제 API 스펙에 적용까지 간 것이 효과적이었다.

**비효과적이었던 것**:  
범위 제한(3단계)이 약했다. "조회 전략"이라는 하나의 주제에서 시작했지만, JOIN vs 분리 vs JSON 서브쿼리 → 메서드 네이밍 → save 설계 → 도메인 객체 설계까지 연쇄적으로 확장되었다. 하나의 세션 기준으로 보면 범위가 넓었고, 각 주제의 깊이가 분산되었을 수 있다.

**막힌 것의 종류와 전략의 궁합**:  
"코드는 돌아가는데 이게 맞는 건지 모르겠다" 유형의 설계 판단 문제에서 혼자 먼저 선택지를 정리한 뒤 자료 조사로 비교하는 전략이 잘 맞았다. 본인의 분석을 먼저 깔고 가니까 자료를 수동적으로 받아들이는 게 아니라 자기 생각과 대조하면서 판단 기준을 세울 수 있었다.

### 4. AI 피드백

**개선 제안**:  
"연결 하나만 확실히 만든다"는 3단계 원칙을 더 엄격하게 적용할 것. 이번 세션의 핵심 연결 하나를 확실히 잡았으면 하나의 원칙이 더 단단하게 자리잡았을 것이다.

### 5. 다음 타임에 바꿀 것

**유지할 것**:  
전체적인 단계는 혼자 생각하는 시간 -> 자료를 찾아보는 시간 -> 자료를 검증하는 과정으로 체계화되어있다고 생각하여 유지한다.

**바꿀 것**:
