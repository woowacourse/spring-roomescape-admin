### 💬 Apply 01

#### Repository / DAO 분리의 의도 

[이전 커밋](https://github.com/nn98/spring-roomescape-admin/commit/99753c7aaf55043aada0b7e340eb6016708aaf49) 에선 DAO 로직을 Repository 내부에 구현했었습니다!   
레포지토리 구현체에서 바로 작성하는 경우도 많음을 [이전 미션](https://github.com/woowacourse/java-janggi/pull/316#discussion_r3055110229) 에서도 로빈이 언급해 주셨었지만

도메인 Reservation 에 대응할 Repository 를,  
데이터베이스 reservation, reservation_time 각각에 대응할 Dao 를  
직접 구현해 보며 이후 이 로직이 어떻게 추상화될 것인지, 그 내부를 추론할 수 있도록  
이전 미션에서 학습했던 내용을 반영하려는 의도로 분리를 선택했습니다.  

#### 인터페이스화

단순한 요구사항이기에 직접적인 구현으로 충분한 상황이었지만  
필요한 최소한의 구현보단 인터페이스로 의존을 추상화해놓는 것의 이점이 훨씬 크다 생각했어요.  

크루들과 함께 북스터디를 진행하며 (조영호 개발자의 오브젝트)  
인터페이스를 도입해 내부를 추상화함으로써 얻을 수 있는 의존성 감소 효과가  
확장성 측면에서 매우 효과적이라 생각했고, 실증적으로 검증하기 위해  
이번 미션에서 직접 사전 분리와 기능 확장을 경험하려는 의도로 인터페이스화 해 보았어요.  

#### 정리 

과도한 분리와 근거/기준 없는 인터페이스화는  
개발 소요 증가와 클래스 과도화라는 역효과를 유발하기에 지양해야 마땅하겠지만  

- 기능이 확장될 것으로 예상되는 미션(도메인) 
- 이전 미션의 연장선으로 배운 내용을 실습 
- 그 과정에서의 개념 학습과 기준 확립 

을 목적으로 시도했습니다.  

웨지의 피드백 덕분에 다시 한 번 생각을 되짚으며 구현의 근거를 찾을 수 있었네요.  
다만 제가 선제적으로 코드나 구현의 근거를 전달했다면 더 효과적으로, 더 효율적으로  
진행 가능했을 부분이라 스스로 반성하게 되었습니다.  

학습은 분명 중요하지만 그 핵심 과정으로 리뷰/피드백이 존재하는 이상,  
효율적인 리뷰를 위해 더 많은 시간을 배분하고 일정을 조율해야겠다 생각했습니다.

#### `@Repository` 어노테이션

우선 직관적으로 와닿은 Spring Repository 의 차이점은 `throws SQLException` 의 배제였습니다.  
이전 미션에선 Repository / DAO 의 모든 Connection 메서드에 throws 구문을 붙여야 했지만  
그것이 생략되었다는 것은 Spring 이 어떤 방식으로나마 예외를 처리(not Solve)해 주기 때문이라 생각했어요.  

어노테이션의 Javadoc 내용을 활용해 학습해봤어요.

`번역`  

- 이 어노테이션이 붙은 클래스는 도메인 주도 설계(DDD)에서 정의한  
  "저장, 조회, 검색 행위를 캡슐화하여 마치 객체 컬렉션처럼 동작하는 메커니즘"인 'Repository' 임을 나타냅니다.
- [X] 전통적인 J2EE 패턴인 'DAO(Data Access Object)'를 구현하는 팀들도  
  이 어노테이션을 사용할 수 있지만, 적용하기 전에  
  DAO와 DDD 스타일 Repository의 차이를 이해하는 것이 좋습니다.
- 이 어노테이션이 붙은 클래스는 PersistenceExceptionTranslationPostProcessor와 함께 사용될 때,  
  하부 데이터베이스의 원시 예외를 스프링의 범용적인 DataAccessException으로  
  자동 변환(Translation)해 주는 자격을 얻습니다.
- 또한, 이 어노테이션은 @Component의 특수한 형태이므로 클래스패스 스캔을 통해  
  스프링 컨테이너에 자동으로 빈(Bean)으로 등록됩니다.

생각했던 대로 `데이터베이스의 원시 예외를 범용직인 예외로 변환` 한다는 내용이 포함되어 있었습니다.  
또한,  
데이터베이스의 원시 예외는 사용하는 기술에 따라 다르기에 그것을 직접 던진다면  
서비스는 예외 처리에 데이터베이스의 종류에 의존하게 되고, 그것을 방지하기 위해  
`@Repository` 어노테이션이 예외를 변환해서 던져 주는 것임을 확인할 수 있었어요.  

이런 계층간 의존/종속 제거에 [앞선 답변]() 내용이 포함된다 생각했어요.  
예외 처리 측면에서 예외를 포장해서 던짐으로써 하부 데이터베이스의 종류에 대한 종속을 제거하듯  
기능 구현 측면에서 저장소를 인터페이스로 추상화함으로써 동일한 종속 제거가 가능한 것이 아닐까요?
