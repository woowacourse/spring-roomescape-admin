# 학습법 정리
## 학습법 v1
각 미션의 토픽을 주로 공부했었고, 코드리뷰가 달리면 그 부분에 대해서 답을 하지 못하면 해당 부분에 대해서 공부를 자연스럽게 진행했고, 그것들이 하나 둘 씩 모이게 된다면 공통적인 주제를 찾고 상위개념으로 전진하면서 꼬리질문 형식으로 공부를 진행했었던 것 같습니다. 그러한 과정에서 코드를 작성하고 나서 나에게 “왜 이렇게 작성했어?”를 했을 때 대답하지 못하면 그 부분에 대해서 추가적인 학습을 진행했고, 자연스럽게 문서를 찾고, 블로그를 찾고 여러 레퍼런스를 찾아서 추가적인 학습을 진행했습니다.

## 학습법 v2
미션의 토픽을 주제로 궁금증이 생기면 작은 기억의 조각의 단위로 일단 정리를 한 뒤에,
하나씩 뭉쳐나가는 방법을 그대로 고수하면서, 정리를 하다가 궁금증이 생기면 나만의 언어로 이해한 뒤에
이것들을 모두 이어가는 것으로 한다.

추가적으로 현재 조각의 범위에서 모은 범위대로 정리를 하되,
다른 사이클의 단계로 넘어가지 않도록 의식하며 공부한다.

맨처음의 목적을 다시 새기면서 처음에 세웠던 목표만 수행 할 수 있도록 하자.

## 학습법 v3
### ① Reverse Engineering 학습
방법: 이미 잘 만든 서비스/코드를 “왜 이렇게 설계했는지” 역으로 파헤침
예: Spring → “왜 DI를 이렇게 강제했지?”

멘탈 모델
“자연은 항상 이유 없이 설계되지 않는다”
- 좋은 코드는 우연이 아님 → 문제 해결의 결과물
- 너 혼자 생각하는 것보다 이미 검증된 사고를 역추적하는 게 훨씬 빠름

### ② 제약 기반 학습 (Constraint Learning)
방법: 일부러 제한을 걸고 개발
예:
- “DB 없이 구현해보기”
- “락 없이 동시성 해결해보기”
- “Thread 100개 상황 가정”

멘탈 모델

“이해는 ‘깨지는 지점’을 만났을 때 발생한다”
- 평범한 상황 → 생각 안 함
- 제약 → 반드시 설계 고민 발생
- 즉, 문제 상황이 사고를 강제함

### ③ 타인 시뮬레이션 설명 (Adversarial Teaching)
방법: “까다로운 면접관”을 가정하고 설명

스스로 공격:
- “그게 왜 맞지?”
- “반례는?”
- “다른 방법은?”

멘탈 모델

“이해는 방어할 수 있을 때 완성된다”
- 설명 가능 ≠ 이해
- 반박 대응 가능 = 진짜 이해


## 주말에 시도할 것: 깊이는 이해 기준이 아니라, 사용 기준으로 끊는다. 즉 문제를 해결할 정도의 수준이 되면 멈춘다.

적용 시나리오:
1. 새로운 개념을 처음 공부할 때 또는 코드 작성 중 막혔을 때
2. 역할을 나만의 언어로 요약, 어디에 쓰는지, 없으면 뭐가 불편한지
3. “+1 깊이” 딱 한 개만
