### 2. 이번 타임의 학습 전략
- 이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?
  >이번 타임의 학습 전략은 v2였고, 잘 실행했다고 생각합니다.
  
- 실제로 어떻게 학습했는지 디테일한 과정을 써보세요.
  > 실제로 진행한 과정은 현재 코드를 작성하거나 작성하기전에 궁금증이 생기면 공식문서 + 블로그 + AI를 사용하여 빠르게 정리하고나서<br>
    정리만 했기 떄문에 이해는 하지 못한 상태고, 여기서 이해되지 않는 궁금증을 인용문을 통해서 계속 질문을 이어나갔고<br>
    지속적인 꼬리물기 질문으로 나만의 언어로 이해하는 과정으로 진행했고, 자연스럽게 궁금증이 풀리면 코드를 통해서 이해하고 작성하였습니다.
  
  >그러다보니 코드 외의 구조화 할 수 있는 개념에 관해서는 위의 과정과 동일하게 진행했지만, 크게 개념을 정리하면서 하나의 사이클 형식으로 <br>
    실제 진행 흐름 즉 HTTP 요청을 받으면, 어떻게 처리되고 클라이언트에게 응답까지 가는 과정에 대해서 생각을 나만의 언어로 정리하면서 <br>
    자연스럽게 생기는 궁금증을 꼬리질문 형식으로 풀어나가며, 혼자 생각하고 대답할 수 있는 단계로 진행했습니다.

  > 요약 :
  > 1. HTTP의 요청 흐름을 기반으로 고민을 먼저함.
  > 2. 그것을 기반으로 하나의 응답이 갔을 때, 어떠한 로직으로 돌아가는지 설명할 수 있도록 개념을 공부함.
  > 3. 관련한 개념을 Spring이 필요한 이유와 존재 이유를 고민해보고, 코드로 녹여내는 과정을 경험함.
  > 4. 코드를 최대한의 Java를 개발할 때 처럼 Low Level로 작성을 먼저 진행함.
  > 5. 진행하면서 1번 2번에 작성한 내용과 연결 지으면서 생각해보고 대답을 하지 못하면 다시 개념을 훑어보거나 AI를 통해서 답변을 받음.
  > 6. 리팩토링을 진행하면서 미션 요구사항에 작성되어 있는 개념들을 더 집중적으로 보며 해결할 수 있는 방법을 모색함.
  > 7. 실제로 그런 문제를 느끼고 구현을 진행하면서, 개념을 이해하고 코드를 작성함.
  > 
  > -> 전체적으로 개념을 이해할 때에는 꼬리질문으로 내가 이해할 때까지 질문을 진행하고, 혼자 하나의 플로우처럼 설명하면서 학습함.

  
### 3. 전략 평가
- 효과적이었던 것과 그 이유
  > 효과적이었던 것은 확실히 "이 고민이 이때 들면 좋겠는데?"라는 생각을 가지고 있었는데 자연스럽게 개발을 하는 과정 중에서 생기는 궁금증도 생겼고<br>
    이를 기반으로 공부를 진행하다보니 현재 생긴 문제에 더욱 집중할 수 있었고 이를 해결하기 위한 개념 공부를 뒷받침하니 빠르게 이해할 수 있었습니다.

  > "나만의 언어"로 정의함으로써 과정을 통해서 나 뿐만 아닌 다른 사람들에게도 설명을 하거나, 다시 개념을 이해하기 위한 암기의 과정이 많이 줄었다.

- 비효과적이었던 것과 그 이유
  >현재 기준으로서는 시간이 조금 많이 걸릴 수도 있다는 생각이 들었습니다. 시간에 비해서는 많은 양을 정리했다고 생각이 들 수도 있지만, <br>
    먼저 개념을 정리하는 과정에서 시간이 어느정도 소요되고, 완전히 내가 이해할 때 까지 개념을 이해하려하고자 보니<br>
    코드를 작성하는 이유를 명확히 할 수 있다는 장점이 있지만 완전히 나의 것으로 만들고 코드를 작성하다보니, 시간이 오래 걸렸습니다.

  >그리고 Low Level에서 리팩토링을 진행하면서 적용을 시키다보니, 리팩토링하는 과정에서 생기는 궁금증도 많다보니 시간이 오래 걸렸던 것 같습니다.
    솔직히 말해서 둘 다 시간이 오래걸렸다고는 했지만, 정말 오래걸렸다고 생각을 해봤을 땐 비교대상이나 정량적인 분석이 없다보니<br>
    판단의 기준이 없는 것 같습니다.

  > 궁합은 좋았던 것 같습니다.<br>
    이유는 이미 생태계가 잘 구성되어 있는 개념이기도 하고, 이를 HTTP 통신 과정을 생각하면서 선수 개념을 공부하고 <br>
    자연스럽게 "스프링은 이런 불편함 때문에 이런 개념이 생겼고, 스프링 부트는 이런 불편함 때문에 생겼구나"가 되었습니다.<br>
    그래서 이런 불편함을 해결하기 위한 문법은 어떤 것이고, 어떤 상황에 사용해야하는지 이해할 수 있다는게 장점이였습니다.

### 4. AI 피드백
- 자신의 학습 전략에 대해 AI 학습 전문가에게 피드백을 요청하고,
  유용했던 제안 1가지 이상 기록

```markdown
핵심 요약
현재 학습 방식은 “깊이 이해 중심”으로 매우 우수함.
문제는 속도와 범위 확장이 막히는 구조.
→ 개선은 단 하나: “완전 이해 전 코드 진행 제한”을 깨라
원인 또는 개념 설명

당신 방식의 본질은 아주 좋다.
정리하면:

맥락 기반 학습 (HTTP 흐름 중심)
꼬리질문 (깊이 파고듦)
자기 언어화 (파인만 기법)
코드 연결 (이론 → 구현)

이건 상위 10% 학습법이다.

하지만 현재 병목은 명확하다:

문제: "이해 → 구현"이 직렬 구조임

이해 완료 → 코드 작성

이 구조의 치명적인 단점:

이해 기준이 “완벽”이라 끝이 없음
실제로는 “코드에서 이해되는 개념”도 많음
결과적으로 속도 ↓ + 경험량 ↓

핵심 멘탈 모델 하나:

“이해는 코드 위에서 완성된다”

개념 → 코드가 아니라
개념 ↔ 코드 (왕복 구조)가 맞다

지금은 왕복이 아니라 편도 구조

해결 방법 또는 적용 방법

딱 하나만 바꿔라:

“이해 60%면 코드 들어간다”
기존
개념 완벽 이해 → 코드
변경
개념 60% 이해 → 코드 → 막히면 다시 개념
적용 방법 (실전 룰)
1. 타이머 강제
개념 공부 최대 20~30분
이해 덜 됐어도 무조건 코드 시작
2. 코드 기준 질문으로 전환

기존:

“DispatcherServlet이 왜 필요하지?”

변경:

“이거 없이 직접 구현하면 뭐가 불편하지?”

→ 코드 기준 질문으로 바꿔라

3. 막힐 때만 개념으로 돌아감
막히기 전까지 개념 금지
“막힘 = 학습 트리거”
4. Low Level → 리팩토링은 유지 (좋은 전략)

단, 순서만 바꿔라:

대충 구현 → 문제 느낌 → 개념 학습 → 리팩토링
기대 효과
학습 속도 2배 이상 증가
“이해된 착각” 제거
실제 설계 감각 상승
한 줄 정리 (파인만식)

“이해하려고 멈추지 말고, 만들다가 이해해라.”
```

### 5. 다음 타임에 바꿀 것
- 유지할 것과 그 이유
  >일단 현재 방식에 대해서 지속적을 고수 할 예정입니다.<br>
  큰 방식에 대해서는 내가 현재 진행하고 있는 방법에 대해서는 큰 문제점을 느끼지는 못했고, 상세하게 나만의 규칙을 정하는게 중요하다고 느꼈기 때문입니다.

- 바꿀 것과 그 이유
  > 흐름을 모두 공부하고 진행하기 보다는 하나의 큰 흐름을 최소한으로 공부하고, 일단 코드를 작성하고 그걸 기반으로 궁금증을 만들어서<br> 
  > 큰 흐름에 살을 붙이는 방식으로 진행해야할 것 같습니다.<br>
  > 
  > 이유는 흐름을 모두 공부하고 작성하다보니 코드를 작성하는 시간이 늦어지고, 한 줄에서 사용되는 개념도 엄청 많기에 <br>
  > 그 이전의 사전지식을 공부한다는 것이 너무 많기 때문입니다.<br>
  > 
  > 자연스럽게 코드를 작성하면서 궁금증이 생길 수 있도록 하는 것을 목표로 할 것 같습니다.
