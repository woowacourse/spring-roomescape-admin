### 2. 이번 타임의 학습 전략
* **이전 전략**: v3 프롬프트 적용 (이종 도메인 강제, 마이크로 미션, 가지치기 통제). 하지만 메인 미션과 병행하며 완전히 새로운 도메인의 마이크로 미션을 구현하는 것은 컨텍스트 스위칭(Context Switching) 비용이 너무 크다는 현실적 한계를 느낌.
* **학습 과정 상세**:

#### 🌐 ContentType과 Jackson의 역할
* 자바는 네트워크를 탈 때 객체를 문자열(JSON)로 바꿔야 함. 스프링은 이 번역 작업을 **Jackson(`ObjectMapper`)** 라이브러리에 위임.
* **직렬화 (Object -> JSON):** `Getter`를 통해 데이터를 읽음. (Getter 필수)
* **역직렬화 (JSON -> Object):** Jackson이 일단 **빈 종이(기본 생성자)**를 꺼내 객체를 만들고 그 안에 값을 채워 넣음.

#### 🛡️ DTO의 불변성 딜레마 (Final vs Jackson)
* **문제:** DTO는 안전성을 위해 `final`을 써서 불변으로 만들어야 한다고 생각했으나, `final`을 쓰면 기본 생성자를 만들 수 없어 Jackson이 에러를 냄.
* **해결 (Java Record):** Record는 모든 필드를 한 번에 넣는 **전문화된 생성자(Canonical Constructor)**를 보장함. Jackson이 이를 인식하고 빈 객체 생성 없이, 모아둔 데이터를 한 번에 밀어 넣어 불변성을 지키면서도 객체를 생성해냄. (팩스 데이터 비유로 체화)

| 구분 | 일반 클래스 (Mutable) | 자바 레코드 (Immutable) |
| :--- | :--- | :--- |
| **생성 시점** | 빈 객체 생성 후 나중에 값 채움 | 모든 값을 모아서 한 번에 생성 |
| **안전성** | 생성 후 값이 변할 수 있어 위험 | **생성 후 절대 변하지 않아 안전** |

#### ⚙️ Lombok의 컴파일 타임 마법
* 롬복은 실행 중(Runtime)이 아니라 코드가 만들어질 때(Compile-time)만 끼어들어 코드를 짜주고 사라지는 마법사.
* **`compileOnly`**: (기획자) IDE에게 "이런 코드가 생길 거야"라고 알려줌. 결과물 용량 감소.
* **`annotationProcessor`**: (실무자) 바이트 코드로 변환될 때 실제로 `Getter`, `Builder` 등의 코드를 타이핑해서 밀어 넣음.

#### 🚥 HTTP StatusCode (상태 코드)
* 데이터를 실어 나르는 봉투의 머릿말로, 가장 짧고 강렬한 서버의 첫마디.
* **200 OK**: 일반적 성공 / **201 Created**: 새로운 데이터 생성 성공 (ID나 전체 객체 반환 여부에 따른 트레이드오프 존재).

### 3. 전략 평가
* **효과적이었던 것**: "DTO는 불변이어야 한다"는 나의 생각과 "Jackson은 기본 생성자가 필요하다"는 프레임워크 제약 간의 모순을 AI와 토론하며 돌파한 것.
* **비효과적이었던 것**: 개념이 꼬리를 물고 이어져(Jackson -> Lombok -> AccessLevel) 인지 과부하가 발생함.
* **궁합**: 막힌 개념에 대해 억지로 외우지 않고 팩스 데이터 같은 비유를 만들며 체화한 방식이 매우 효과적이었음.

### 4. AI 피드백
* **제안 1 (스스로 제동 걸기 - 메타인지)**: 꼬리를 무는 개념 학습 중 "지금은 과부하라 AccessLevel은 나중에 하겠다"라고 판단한 것은 뇌의 작업 기억 한계를 인정한 훌륭한 'Hard Start - Jump to Easy' 전략임.
* **제안 2 (미션 밀착형 아웃풋으로 전환)**: 완전히 새로운 도메인의 마이크로 미션을 짜는 것이 현실적으로 부담스럽다면, 현재 미션 코드 내에서 **'학습 테스트(Learning Test)'**를 작성하거나 잘 돌아가는 코드의 어노테이션을 고의로 지워보는 **'의도적 파괴(Deliberate Breaking)'** 방식을 도입해 아웃풋(60%) 비중을 채우는 것이 효율적임.
