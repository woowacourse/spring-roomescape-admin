## V1 학습법

**시점**: 레벨 1 종료

### 방식
코드 먼저 작성 → 찜찜함 포착 → 리팩토링 → 글 정리 → 리뷰어 피드백.  
객체지향 고민 중심. AI 코드를 빠르게 받아 진입.

### 충돌 지점

**충돌 1 — AI 코드 무검토 진입**  
AI 코드를 검토 없이 사용하다 보니 문제 있는 코드도 인식 못하고 넘어감.  
→ 언제 드러나는가: 새 기술(스프링, JPA 등)을 처음 쓸 때.

**충돌 2 — 방향 설정의 외부 의존**  
방향 설정을 리뷰어·코치 피드백에 의존 → 혼자 방향 잡는 능력 훈련 부족.  
→ 언제 드러나는가: 매번 확인을 받을 수 없는 상황.

### 해결 방향
갈아엎지 말고 최소 보정만.  
"개념·흐름 정도는 알고 가고, 코드 원리에 대해 학습을 추가한다."  
"지금은 학습 과정이다. 하던 대로 하되 사고를 조금씩 확장한다."

## V2 학습법

**시점**: 레벨 2 초입  
**원칙**: V1 골격 유지. 충돌 지점 1에 얇은 보정 (Structural Thinking 적용).

### 흐름

```
[새 미션 시작]
    ↓
1단계  Problem-Driven  : "이 기술이 푸는 문제는?" 한 문장
        Structural     : 흐름 스케치 5~10분 (???로 비워두기)
        i+1            : "반드시 이해할 한 가지" 설정
    ↓
2단계  코드 작성 (V1 골격, AI 코드 OK)
    ↓
3단계  빠른 루프  : AI에게 원리·문제점 검증 / 공식문서 / 키워드 검색
    ↓
4단계  리팩토링 + 글 정리 (설계 의도/찜찜함 한 단락)
    ↓
5단계  느린 루프 : 리뷰어 검증 → 내 판단과 비교
    ↓
   (막히면 Resourceful: 공식문서 → AI → 크루 → 코치, 비순차적으로)
```

### V1 대비 변경 사항

- **1단계 신규**: "이 기술은 ___ 문제를 풀려고 만들어졌다" 한 줄 + 흐름 스케치 5~10분
- **3단계 신규**: 리팩토링 전 AI 검증 / 공식문서 교차 확인 — AI는 코드 생성기가 아니라 검증자
- **4단계 추가**: 글 정리에 "설계 의도·찜찜함" 한 단락 묻기 (충돌 지점 2 관찰 장치)
- **Resourceful**: 공식문서·크루를 자원 목록에 명시 추가

### 의도적으로 안 바꾼 것
- V1 골격 (코드 먼저 → 찜찜함 → 리팩토링 → 글 → 리뷰): 작동하고 있다
- 충돌 지점 2에 대한 별도 조치: 관찰만. 재료가 충분히 쌓이지 않은 상태에서 처방하면 오버엔지니어링

## V3 학습법

**시점**: 레벨 2 Gradle 학습 회고 후  
**원칙**: V2 골격 유지. 세 지점만 보정 — 흐름 스케치 자원, 노트 재사용 구조, 회고→다음 이터레이션 연결.

### 흐름

```
[새 미션 시작]
    ↓
0단계  이전 회고의 i+1 후보 3개 확인  ← V3 신규
    ↓
1단계  Problem-Driven  : "이 기술이 푸는 문제는?" 한 문장
        Structural     : 흐름 스케치 5~10분
                          - AI overview 요청 (절단 지시)  ← V3 변경
                          - 키워드 3~5개를 공식문서로 교차 확인  ← V3 변경
        i+1            : "반드시 이해할 한 가지" 설정
        메타 점검       : 모르는 걸 알고 있는가?
    ↓
2단계  코드 작성 (V1 골격, AI 코드 OK)
    ↓
3단계  빠른 루프  : AI에게 원리·문제점 검증 / 공식문서 / 키워드 검색
    ↓
4단계  리팩토링 + 글 정리
        - 미션 정리 문서 (설계 의도/찜찜함 한 단락)
        - 핵심 개념을 evergreen note로 분리  ← V3 신규
        - 노트마다 ??? 섹션  ← V3 신규
    ↓
5단계  느린 루프  : 리뷰어 검증 → 내 판단과 비교
        회고       : 학습법이 잘/못 작동한 지점
                   다음 i+1 후보 3개 명시  ← V3 신규
    ↓
   (막히면 Resourceful: AI(overview) ↔ 공식문서(reference) → 크루 → 코치)
```

### V2 대비 변경 사항

| 영역 | V2 | V3 |
|------|----|----|
| 흐름 스케치 자원 | 공식문서 개요 | AI overview + 공식문서 키워드 교차 확인 |
| AI 사용 시점 | 빠른 루프(검증)만 | 흐름 스케치 + 빠른 루프 |
| AI 질문 형식 | 자유 | 정형 질문 + "그 외는 빼라" 절단 지시 |
| 노트 단위 | 미션별 한 문서 | 미션 문서 + 개념별 evergreen note |
| 찜찜함 처리 | 미션 정리 끝에 모음 | 노트별 ??? 섹션 + 회고에 i+1 후보 3개 |
| Resourceful 우선순위 | 공식문서 → AI → 크루 → 코치 | AI(overview) ↔ 공식문서(reference) → 크루 → 코치 |
| 미션 시작점 | Problem-Driven부터 | 0단계: 이전 회고의 i+1 후보 확인부터 |

### Evergreen Note 규칙
- 한 노트는 한 개념만
- 제목은 개념 이름 그 자체 (예: "Gradle implementation 스코프")
- 내용은 본인 언어로 — 공식문서 복붙 금지
- 다른 노트로의 링크 최소 1개
- 찜찜한 부분은 노트 끝에 **??? 섹션**으로 명시

### 의도적으로 안 바꾼 것
- V1 골격, i+1 원칙, Problem-Driven 한 줄: 그대로
- 충돌 지점 2 처방: V4 이후로 미룸. 5단계 끝의 i+1 후보 3개가 부분 보완

## 설계 원칙 (PiFSR)

매 버전을 관통하는 5원칙. 버전이 올라가도 원칙은 바뀌지 않고, 적용 방식만 정밀해진다.

| 원칙 | 한 줄 |
|------|-------|
| **Problem-Driven** | 기술이 푸는 문제부터 |
| **i+1** | 한 번에 이해할 한 가지만 |
| **Feedback Loop** | 분 단위(빠른) + 며칠 단위(느린) 루프 |
| **Structural Thinking** | 흐름 스케치로 구조를 먼저 잡기 |
| **Resourceful** | 자원을 상황에 맞게 비순차로 활용 |

---

> 매 버전은 이전 버전을 갈아엎지 않는다.  
> 실제 충돌 지점에서 드러난 최소 보정만 추가한다.
