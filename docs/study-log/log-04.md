**학습 범위**: 4단계: 계층 분리

### 1. 막힌 것의 종류
이번에 막힌 것은 어떤 종류의 어려움이었는가? (해당하는 것에 체크)
- [ ] 개념 자체를 모르겠다 (예: "스프링 빈이 뭔지 모르겠다")
- [ ] 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 (예: "JdbcTemplate 문법을 모르겠다")
- [ ] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [x] 기타: 리팩터링 과정에서의 테스트 환경 격리 및 의존성 주입 설정 문제

### 2. 이번 타임의 학습 전략
- 이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?
  - 4단계 요구사항인 계층 분리를 진행하며, 단순히 코드를 분산시키는 것이 아니라 각 레이어가 가져야 할 고유한 책임에 대해 깊이 고민하며 리팩터링을 완료했다.
- 실제로 어떻게 학습했는지 디테일한 과정을 써보세요.
  - 컨트롤러가 DAO를 직접 의존하지 않도록, 비즈니스 흐름을 담당하는 Service 레이어를 중간에 도입했다.
  - 또한 레이어를 분리하는 과정에서 클래스의 패키지 구조 역시 역할에 맞게 재구성하여, 레이어드 아키텍처의 전형적인 구조를 갖추고자 했다.

### 3. 전략 평가
- 효과적이었던 것과 그 이유
  - 책임을 기준으로 한 명확한 계층 분리가 매우 효과적이었다. 단순한 코드 이동이 아니라 이 로직이 웹 요청/응답을 위한 것인지, 비즈니스 규칙인지를 기준으로 판단하며 구조를 나누었기 때문에, 응집도는 높이고 결합도는 낮추는 리팩터링을 수행할 수 있었다.
- 비효과적이었던 것과 그 이유
  - 이번 타임에서는 특별히 비효과적이었던 전략은 없었다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
  - 전반적으로 궁합이 잘 맞았다. 이미 구현된 코드를 역할에 따라 분리하는 과정이었기 때문에, 전략을 적용하는 데 큰 어려움 없이 안정적으로 진행할 수 있었다.

### 4. AI 피드백
계층 분리를 통해 응집도를 높이는 전략은 매우 훌륭합니다. 여기서 한 걸음 더 나아가, 서비스 계층에서 도메인 객체(Reservation, ReservationTime)를 반환할 때 컨트롤러가 필요한 데이터만 담은 DTO로 변환하여 응답하는 구조를 고민해 보세요. 
이는 도메인의 변경이 API 스펙에 직접적인 영향을 주지 않도록 보호하는 좋은 전략이 될 것입니다.
