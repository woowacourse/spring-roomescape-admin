### 1. 막힌 것의 종류
이번에 막힌 것은 어떤 종류의 어려움이었는가? (해당하는 것에 체크)
- [ ] 개념 자체를 모르겠다 (예: "스프링 빈이 뭔지 모르겠다")
- [ ] 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 (예: "JdbcTemplate 문법을 모르겠다")
- [ ] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [x] 기타:  
  - 롬복을 기존에 자주 쓰다보니 발생한 문제가 있었다.  
  - 항상 롬복을 사용해 getter를 처리했는데 이번에는 까먹고 붙이지 않았다.
  - 그래서 Spring의 직렬화 과정에서 DTO에 getter가 없어 발생한 406 에러의 원인을 확인하는데에 시간이 들었다.

### 2. 이번 타임의 학습 전략

- 이전에 정한 전략(v3)은 따로 적용하지 않았다.  
미션 자체가 간단한 CRUD 수준이어서 코드를 작성하고 에러를 만나면 직접 찾아보는 방식으로 진행했다.
- 코드 작성 → 테스트 실패 → 에러 메시지 확인 → 원인 탐색 → 수정의 사이클로 진행
- 406 에러를 만났을 때 상태 코드의 의미부터 찾아봤고, 이를 계기로 HTTP 상태 코드 전반을 간략히 공부했다. 주제 전환이 1번 발생했고 그 선에서 끊었다.

### 3. 전략 평가

**효과적이었던 것**: 
- 에러 메시지에서 출발해 HTTP 상태 코드라는 연결된 개념까지 자연스럽게 확장된 흐름이 좋았다.   
- v2 전략대로 전환 횟수를 1번에서 끊어낸 것도 잘 지켜졌다.

**비효과적이었던 것**: 특별히 없었다.

**막힌 것의 종류와 전략의 궁합**: 
- 이번 막힘은 처음 접한 개념이어서가 아니라 롬복에 의존하던 과거의 습관에 따른 실수였다.  
- 에러를 실마리로 삼아 관련 개념을 넓히는 나의 기존 학습 방식은 이런 종류의 막힘에 잘 맞았다고 생각한다.

### 4. AI 피드백

> 에러를 단순히 해결하는 데서 끝내지 않고 HTTP 상태 코드 전반으로 확장한 것은 좋은 접근이다.  
> 다만 상태 코드를 공부할 때 "이 코드가 나타내는 상황"과 "서버가 이 코드를 반환하게 되는 조건"을 함께 정리해두면, 다음에 비슷한 에러를 만났을 때 훨씬 빠르게 원인을 좁힐 수 있다.  
> 특히 4xx 계열은 클라이언트 문제인지 서버 설정 문제인지 경계가 모호한 경우가 있으므로, 각 코드의 정확한 의미를 한 번쯤 정리해두는 것을 추천한다. 

### 5. 다음 타임에 바꿀 것

**유지할 것**: 에러를 출발점으로 삼아 관련 개념을 1단계만 확장하는 흐름. 미션 규모에 맞게 학습 깊이를 조절하는 것.

**바꿀 것**: 
- 공부한 내용에 [나중에 반드시] 태그 여부를 판단해서 기록으로 남기는 습관을 추가한다.  
- 이번에 공부한 HTTP 상태 코드는 반복해서 등장할 개념이므로 노션에 간략히 정리해둘 것.
