1. **Problem-Driven**
   > 이걸 왜 공부하지? 먼저 정의

   예시: “Controller 왜 쓰지?”, “서비스 레이어 왜 나누지?”

2. **i+1**
   > 한번에 하나의 키워드만 정해서 무엇인지만 이해하기

  - ❌ “Spring MVC 전체”
  - ✅ “@Controller 역할 하나만”
3. **Input**
   > 만든 결과물을 AI를 통해 검증
4. **Output**
   > 가설을 설정하고 직접 만들어보기
   가설은 아무자료 없이 사전 지식으로만
  - @Controller는 ~~일 것이다.
  - Controller 없이 코드 작성해보기

5. **Self-Explanation**
   > - Output 내용을 기반으로 해당 학습내용을 스스로 설명해보기 
   > - 막히는 경우, 해당 부분만 다시 AI에게 Input. 
   > - 최종적으로 학습내용 정리하기

6. **Backlog**
   > - 나중에 알아야 할 것 같은 개념이나 더 깊은 개념이 있다고 느껴지는 부분 기록 해두기.
   > - 학습은 추후 Problem Driven이 확고해질 때 다시(예: 프로젝트 하다가 막힌 경우)

이번에는 부분적으로만 Problem-Driven 학습법을 실행했다.
JdbcTemplate의 기초 문법을 까먹어서 Problem-Driven 학습법대로 학습을 해볼까 했었지만,
기존에 따로 노션에 정리해둔 자료도 있었고, 우테코에서 제공하는 학습자료도 있었다.
대놓고 좋은 학습 방법이 나와있는 상황에서 굳이 Problem-Driven 학습법을 고수할 필요는 없다고 생각했다.

그외에 학습 방법이 애매하다 싶은 부분은 Problem-Driven 학습법대로 학습했다.
JdbcTemplate 기초 문법을 학습하다가 batchInsert()가 궁금해졌고, 기존에 정리해둔 자료도 없고 우테코에서도 제공하는 자료도 없었기 때문에
Problem-Driven 학습법을 적용하였다.

Problem-Driven 학습법 자체는 효과적이었다. 막힌 것과의 궁합도 좋았다. 다만, 이 학습법을 모든 상황에 대해 적용하는 것은 좋지 않다고 생각했다.
JdbcTemplate 기초문법처럼 기존에 노션에 정리해둔 자료가 있거나, 우테코에서 제공하는 자료가 있다면, 그 자료를 활용하고

## **장점**

가장 큰 장점은 **능동적 학습**입니다. 

`JdbcTemplate 문법 보기 → 따라 치기`에서 끝나지 않고,  “batchUpdate는 어떤 상황에서 쓰는 걸까?”
“직접 써보면 어떤 차이가 날까?”처럼 질문을 만들고 실험했습니다.
이건 단순 암기가 아니라 **기술의 사용 맥락을 이해하는 학습**입니다. 백엔드에서는 특히 중요합니다. 왜냐하면 백엔드 기술은 “문법을 아는 것”보다 “언제, 왜 쓰는지 아는 것”이 더 중요하기 때문입니다.
또 하나의 장점은 **Backlog 전략**입니다. 지금 당장 깊게 파지 않아도 되는 개념을 보류하는 건 좋습니다. 이걸 못 하면 Spring, DB, 트랜잭션, 커넥션 풀, 성능 최적화가 한꺼번에 튀어나와서 학습이 터집니다.

## **단점**

단점은 학습법이 나쁜 게 아니라, **적용 조건이 아직 명확하지 않다**는 점입니다.
이번 회고에서 이미 스스로 발견했습니다.
기존에 좋은 자료가 있는 경우에는 굳이 내 학습법을 고수할 필요가 없다.
자료가 마땅치 않거나 직접 판단해야 하는 경우에는 효과적이다.

이 판단은 아주 좋습니다. 다만 아직은 감각적으로 판단하고 있습니다.
즉, 현재 문제는 이것입니다.
“이 학습법을 어떻게 개선할까?”가 아니라
**“언제 이 학습법을 쓸지 어떻게 빠르게 판단할까?”**입니다.

## **딱 하나만 개선한다면**

**학습 시작 전에 ‘자료 기반 학습’과 ‘탐구 기반 학습’을 나누는 2분 분류 단계를 추가하세요.**
멘탈 모델로 표현하면 이것입니다.

**Map vs Territory 모델**

- Map: 이미 잘 정리된 지도
  예: 공식 문서, 우테코 자료, 본인이 정리한 노션
- Territory: 직접 걸어보며 확인해야 하는 실제 지형
  예: batchUpdate의 사용 상황, 성능 차이, 실제 코드에서의 판단 기준

당신은 지금 Territory를 탐험하는 학습법을 만들었습니다. 그런데 JdbcTemplate 기초 문법처럼 이미 좋은 Map이 있는 상황에서도 같은 방식을 적용하려고 하면 비효율이 생깁니다.

그래서 개선점은 단 하나입니다.

## **개선안: “2분 학습 모드 선택”**

학습 시작 전에 아래 질문 3개만 체크하세요.

```markdown
## 학습 모드 선택

1. 이미 신뢰할 만한 자료가 있는가?
- 공식 문서 / 우테코 자료 / 내가 정리한 노션 / 검증된 강의

2. 내가 지금 막힌 지점은 무엇인가?
- A. 문법을 까먹음
- B. 개념의 역할이 헷갈림
- C. 언제 써야 하는지 판단이 안 됨
- D. 직접 써봤는데 예상과 다름

3. 학습 모드 결정
- A라면: 자료 기반 학습
- B, C, D라면: Problem-Driven 학습
```

## **적용 예시**

JdbcTemplate 기초 문법을 까먹었다면:

```markdown
막힌 지점: 문법을 까먹음
좋은 자료: 기존 노션, 우테코 자료 있음
선택: 자료 기반 학습
행동: 빠르게 복습하고 예제 1개만 작성
```

batchUpdate가 궁금하다면:

```markdown
막힌 지점: 언제 쓰는지 판단이 안 됨
좋은 자료: 없음
선택: Problem-Driven 학습
행동: 가설 세우기 → 직접 코드 작성 → 결과 비교 → 설명 정리
```

## **최종 제안**

당신의 기존 학습법을 바꾸지 마세요. 대신 앞에 **“학습 모드 선택”**만 붙이세요.

현재 구조는 이렇게 바꾸면 됩니다.

```markdown
0. 학습 모드 선택
- 자료 기반 학습인가?
- 탐구 기반 학습인가?

1. Problem-Driven
2. i+1
3. Input
4. Output
5. Self-Explanation
6. Backlog
```

핵심은 이겁니다.
좋은 자료가 있으면 지도를 보고 빠르게 이동한다.
지도가 없거나 판단력이 필요한 영역이면 직접 탐험한다.

이번 회고에서 나온 가장 중요한 개선점은 **학습법의 강화가 아니라, 학습법을 꺼내는 조건의 명확화**입니다.
