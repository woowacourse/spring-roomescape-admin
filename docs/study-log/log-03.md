- [x] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")

### 2. 이번 타임의 학습 전략

- **이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?**
    - **바꾸기로 한 전략** : 공식 문서로 시작하여 예제 코드로 갈아탄 후, 다시 공식 문서로 돌아가보기
    - **실행 여부** : 해당 단계에서 새롭게 마주하는 개념은 없었기 때문에 실행하지 못했다.
  > **[3단계 재구성]** 학습한 개념이 실질적으로 '내 것'이 되었는지 확인하는 핵심 질문에만 집중한다.
  >  - **STEP 01 입력** : 구현에 필요한 최소한의 원리만 빠르게 파악한다. 현재 단계에서 필요하지 않은 부분은 간단히 학습한다.
  >  - **STEP 02 인출** : 자료를 닫고 딱 두 가지 질문에만 답하며 나만의 언어로 정리한다.
  >    - 이 기술(객체)은 왜 필요한가?
  >    - 어떤 원리로 문제를 해결하는가?
  > - **STEP 03 동기화** : 내가 정리한 문장과 원문을 비교해 핵심 키워드가 빠졌는지 체크한다.
  > **[가속 전략]** 새로운 개념을 마주했을 때 미션의 맥락을 유지하면서 효율적으로 습득한다.
  >   - **A. 탐색** : 훑어보며 What & Why 위주로 핵심 키워드만 파악(최대 5분)
  >   - **B. 적용** : 공식 문서로 시작하여 예제 코드로 갈아탄 후, 다시 공식 문서로 돌아가본다. 일단 코드에 녹여서 문제를 해결하고 테스트를 통과시킨다.
  >   - **C. 심화** : 미션 종료 후 혹은 여유 시간에 공식 문서를 통해 Edge Case를 확인한다.


- **실제로 어떻게 학습했는지 디테일한 과정을 써보세요.**
    - 3단계는 기존에 학습한 개념을 적용하는 단계였기 때문에 새로운 개념 자체에서 막히지는 않았다.
      대신 Reservation과 ReservationTime을 연결하는 과정에서, 한 번에 통합을 시도했다.
      SQL alias 불일치와 같은 문제는 공식 문서나 구글링만으로 해결하기 어려웠다.
      해결하기 위해 AI를 활용해 원인을 파악하고 수정하는 방식으로 진행했다.

### 3. 전략 평가

- **효과적이었던 것과 그 이유**
    - **효과적이었던 것** : 3단계 재구성의 방향성 자체 (Why / How 중심으로 이해하려는 접근) 
    - **이유** : 단순 구현이 아니라 “왜 필요한가, 어떻게 문제를 해결하는가”를 기준으로 사고하려는 시도는 유지되었다. 이는 개념을 수동적으로 소비하지 않고 능동적으로 정리하는 데 도움을 주었다.
- **비효과적이었던 것과 그 이유**
    - **비효과적이었던 것** :  가속 전략 B (공식 문서 → 예제 코드 → 다시 공식 문서)
    - **이유** : 이번 문제는 새로운 개념을 이해하는 문제가 아니라, 객체 간 책임이 정리되지 않은 상태에서 통합을 시도하여 문제가 발생했다. 
      따라서 공식 문서나 예제 코드를 참고하는 방식으로는 근본적인 원인을 해결할 수 없었다.
- **막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?**
    - 이번 막힘은 SQL alias 불일치와 같은 에러였지만, 문제는 개념이나 구조가 아니라 에러의 원인을 정확히 파악하지 못한 데 있었다. 
      공식 문서나 예제 코드는 올바른 사용 방법을 설명해주지만, 현재 발생한 에러가 어떤 맥락에서 발생했는지를 직접적으로 알려주지는 않았다.

### 단계 전환 체크

- **이전 단계에서 쓴 접근법을 그대로 쓸 것인가, 바꿔볼 것인가?**
    - 바꿔볼 것이다. 기본 개념 학습은 유지하되, 특수한 맥락(통합 오류, SQL 매핑 등)에서 발생하는 문제에 대한 해결법을 추가하려고 한다.
- **바꾼다면 왜? 바꾸지 않는다면 왜?**
    - 공식 문서나 구글링은 '올바른 길'은 알려주지만, 내가 낸 '오타'나 '잘못된 매핑' 같은 내 코드만의 맥락적 실수까지는 찾아주지 못하기 때문이다. 
      3단계처럼 복잡도가 올라가는 시점에서는 스스로 가설을 세우고 AI를 디버깅 가이드로 활용하는 것이 시간 낭비를 줄이는 길임을 깨달았다.
- **이전 단계에서 발견한 "나에게 맞는 전략"이 새 단계에서도 통할 것 같은가?**
    - 절반은 통하고 절반은 보완이 필요하다. "Why/How 중심으로 정리하기"는 설계의 단단함을 유지하는 데 여전히 효과적이다. 
      하지만 구현 단계에서는 여기에 "가설 기반의 단계적 검증"을 추가해야만, 이번 alias 사건처럼 사소한 실수로 인해 학습 흐름이 통째로 끊기는 것을 방지할 수 있을 것 같다.
