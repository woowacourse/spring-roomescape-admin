### 2. 막힘 해결
1. 요구사항 테스트 코드를 추가했는데, `ReservationDao` 테스트가 깨짐
  - 새로운 테이블인 `reservation_time`이 추가되었고, 이 테이블은 테스트마다 생성하며 충돌이 발생하고 있었음
  - 테이블 스키마에 `IF NOT EXISTS`를 추가하여 해결
2. 예약 시간과 연결에서 막힘
  - `Reservation` 클래스의 `time`필드를 객체로 변경하였는데, 이게 `@RequestBody`로 자동으로 주입이 되는지 모르겠음
  - `@RequestBody`로 객체까지 주입받는 방법은 없는지 찾다가 문제를 까먹고 그냥 `time`필드를 `timeId`로 바꿔버리고 요구사항을 충족시키려 쭉 달림
  - 잘못된 것을 깨닫고 롤백 시전
3. `@RequestBody`로는 예약과 시간을 연결시켰을 때 객체로 바로 받을 수 없음
  - 크루들과 AI에게 2번 막힘에서의 고민을 이야기하여 결국 DTO로 해결하는 방법을 찾아냄
  - 내가 했던 고민들
    - RequestBody가 생성자를 이용하나?
    - 생성자에서 ReservationTime을 만들어야 하나?
    - 정적 팩토리 메서드를 써야 하나?
    - 그럼 생성 책임이 Reservation에 들어오나?
  - `@RequestParam`으로도 해결할 수 있을 것 같음
    - `@RequestParam`: 간단한 검색 조건, 필터, 페이지 번호, 단일 값
    - `@RequestBody`: 하나의 생성/수정 요청 데이터 묶음
    - 예약을 생성하는 것이므로 `@RequestBody` + DTO로 해결해보기로 결정
  - DTO도입을 떠올리는 포인트
    - 지금 들어온 데이터가 “도메인 객체 그 자체”인가, 아니면 “도메인 객체를 만들기 위한 재료”인가?
    - DTO: 아직 도메인은 아니지만, 도메인을 만들기 위해 외부에서 들어온 입력값 묶음
    - 외부 요청 모양은 DTO가 받고, 도메인은 완성된 객체 상태로 만든다.
    - 요청값 중에 도메인 필드가 아닌 “찾기 위한 id”, “선택 옵션”, “비밀번호 확인값”, “체크박스 값” 같은 게 섞여 있다
      → DTO를 의심한다.
4. 필드를 변경하며 수정되는 코드가 너무 많아서 막힌다.
  - `ReservationDao.findBy(Long id)` sql에서 엔터입력을 빠뜨려서 고생함
  - `Reservation`, `ReservationController`, `ReservationDao`, `ReservationRequest`(DTO) 외 테스트 수정
  - 범위도 범위지만 동작 구조를 이해하며 코드를 수정하는 부분이 어려웠다.

객체를 필드로 갖는 경우는 학습 테스트 예제에도 나와있지 않아서 고민을 많이했다. 물론 직접 생각해냈던 방법들은 모두 불편함이 느껴지는 식이었고, 
크루들과 AI를 활용해 최종적으로 DTO가 왜 필요한지, 어떨때 필요한지에 대한 이해가 생겼다. 현재 발생한 문제와 관련된 기초 지식이 거의 
없는 상태에서 문제를 만났을 때 느껴지는 막막함은 너무나도 컸다. AI에게 답을 알려달라고 말하고 싶기도 했다. 
하지만 분명한 학습 전략이 있고, 목표가 있었기에 견뎌내고 최대한 내 경험으로 만들어낸 것 같다. AI에게 조금 더 의존했더라면 더욱 쉽게 
문제를 해결할 수 있었을 거라고 확신한다. 다만 고통을 받긴 했지만 이만한 성장을 해내고 성취감을 얻지는 못했을 것이다. 
현재 학습법은 꽤나 효과적이라고 생각된다. 단점은 산출물을 작성하는 시간이 생각보다 길다. 이 부분에 대해서 AI를 활용하던, 
글을 빨리쓰던 개선이 필요해보인다.
