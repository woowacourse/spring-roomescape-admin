### 1. 막힌 것의 종류

이번에 막힌 것은 어떤 종류의 어려움이었는가?

- [ ] 개념 자체를 모르겠다 (예: "스프링 빈이 뭔지 모르겠다")
- [ ] 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 (예: "JdbcTemplate 문법을 모르겠다")
- [x] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [ ] 기타: ___

이번 막힘은 `RowMapper`를 "쓸 줄 모르겠다"가 아니라, **람다로 인라인 처리할지 / 별도 `RowMapper`로 분리할지 / 어디까지 재사용할지**에 대한 설계 판단 문제였다. 기능은 동작하지만, 중복 제거를 위해 추상화하는 시점이 지금인지 확신이 없는 상태였다.

### 2. 이번 타임의 학습 전략

**이전에 바꾸기로 한 전략**: 세션 시작 시 막힘의 종류를 먼저 분류하고, 유형에 따라 단계 배분을 조정하기. 설계 판단 유형이면 혼자 생각하기와 판단 기준 정리에 더 시간을 쓰기.

**실행 여부**: 실행함

**실제 학습 과정**:

**1단계 (실제 문제 출발)**: 시간 조회/예약 조회 코드를 보면서 "`RowMapper`가 여러 곳에 반복되기 시작했는데, 지금 분리하는 게 맞는가?"라는 실제 문제에서 출발

**2단계 (한 문장 정의)**: "이번 20분은 `RowMapper`를 언제 인라인으로 두고, 언제 별도 객체나 메서드로 빼는지 기준 2~3개만 정리한다"로 문제를 한 문장으로 정의

**3단계 (범위 제한)**: `ResultSetExtractor`, DAO 공통화, 제네릭 추상화, 테스트 전략 같은 확장 주제는 이번 세션에서 다루지 않기로 하고 메모만 남김

**4단계 (혼자 생각하기)**: 먼저 지금 코드 기준으로 경우를 나눠봄
- 컬럼이 2~3개고 한 메서드 안에서만 쓰이면 람다로 둬도 읽기 어렵지 않다
- 같은 매핑이 두 번 이상 반복되면 중복 제거 이점이 생긴다
- 하지만 재사용을 성급하게 하면 "지금은 한 군데만 쓰는 추상화"가 될 수도 있다

이 과정에서 "`재사용 가능성`이 아니라 `현재 중복`과 `가독성 저하`를 기준으로 판단해야 한다"는 가설을 세움

**5단계 (구글링)**: 블로그 예시를 보며, `RowMapper`를 람다/익명 클래스/별도 클래스로 두는 패턴이 어떤 상황에서 쓰이는지 확인

**6단계 (AI 질문)**:
- "`JdbcTemplate`에서 `RowMapper`를 분리하는 기준은 무엇인가?"
- "작은 프로젝트에서도 미리 분리하는 것이 좋은가, 아니면 중복이 생길 때까지 기다리는 게 좋은가?"
- "메서드 내부의 private 정적 `RowMapper` 필드와 별도 클래스 분리 중 어떤 차이가 있는가?"

답변을 통해, `RowMapper`는 "무조건 재사용" 대상이 아니라 **중복, 복잡도, 도메인 의미 노출 필요성**을 기준으로 분리한다는 점을 확인

**7단계 (AI 검증)**: 얻은 기준을 현재 코드에 다시 대입해봄. 시간 엔티티 매핑처럼 단순하고 한 군데에서만 쓰는 것은 인라인 유지 가능, 예약처럼 여러 조회에서 반복될 가능성이 높은 매핑은 private 메서드나 상수 `RowMapper`로 추출하는 쪽이 낫다고 정리

**8단계 (20분 세션 종료 -> 5분 비우기 + 안 보고 떠올리기)**:
자료를 덮고 아래 세 가지를 안 보고 떠올려봄
- 한 번만 쓰이고 짧으면 인라인 가능
- 두 번 이상 반복되거나 읽는 비용이 커지면 추출 고려
- 별도 클래스 분리는 "재사용"보다 "의미 있는 이름 부여"가 필요할 때 유리

**실제 적용**: 당장 모든 `RowMapper`를 공통화하지 않고, 반복 가능성이 높은 매핑부터 `private` 메서드나 상수로 추출하는 방향으로 기준만 세움

### 3. 전략 평가

**효과적이었던 것**:
설계 판단 문제로 분류한 것이 적절했다. `log-2`처럼 곧바로 레퍼런스를 찾기보다, 먼저 "지금 추상화하면 어떤 이득/손해가 생기는가"를 따져본 뒤 자료를 보니 답을 더 선별적으로 받아들일 수 있었다. 또 이번에는 세션 목표를 "`RowMapper`를 빼기"가 아니라 "`RowMapper`를 빼는 기준 정하기"로 둔 것이 좋았다.

**비효과적이었던 것**:
실제 코드 예시를 1~2개만 더 정확히 놓고 비교했으면 판단이 더 단단해졌을 것 같다. 이번에는 원칙 정리는 됐지만, "현재 코드의 어떤 중복부터 추출 대상인가"까지 완전히 닫히지는 않았다.

**막힌 것의 종류와 전략의 궁합**:
이번처럼 "코드는 돌아가는데 이게 맞는 건지 모르겠다" 유형은 혼자 생각하기 -> 기준 세우기 -> 자료로 검증하는 흐름과 잘 맞았다. 특히 설계 판단 문제에서는 정답을 찾기보다 **판단 기준을 명시하는 것**이 학습의 핵심이라는 점이 분명했다.

### 4. AI 피드백

**개선 제안**:
이번 세션에서 가장 유용했던 피드백은 "`추상화 여부`를 고민할 때는 '재사용 가능성'처럼 미래 예측 기준보다, **현재 중복 횟수 / 현재 읽기 비용 / 이름을 붙였을 때 생기는 의미** 같은 현재 기준으로 판단하라"는 제안이었다.

이 피드백이 좋았던 이유는, 내가 자꾸 "나중에 또 쓸 수도 있는데 미리 빼야 하나?"라는 미래 중심 고민으로 빠지는 경향을 줄여주기 때문이다. 앞으로는 추상화를 할 때도 "지금 코드가 이미 불편한가?"를 먼저 묻는 편이 더 안정적일 것 같다.
