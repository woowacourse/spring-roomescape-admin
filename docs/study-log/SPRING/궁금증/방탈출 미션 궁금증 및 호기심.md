### 개발 중 궁금증
#### 팩터리 메서드를 사용하는 이유
팩터리 메서드는 객체 생성 규칙(검증, 가공, 정책)을 한 곳에 강제하기 위해서 씀.
생성 로직을 숨긴다.
> 근데 생성자를 할때 검증을 넣으면 되는거 아닌가?
> 1. 핵심 한 줄 요약  
    **생성자에 검증 넣는 건 가능하지만, “통제력”과 “의미 표현”에서 팩터리가 더 강력하다.**
>2. 개념 정리 (헷갈리는 부분 중심)
>
>- 네 말 맞음: 생성자에도 검증 넣을 수 있음  
>    → 하지만 문제는 **외부에서 생성자를 계속 직접 호출 가능**하다는 것
>- 핵심 차이
>    - 생성자 public → 아무나 `new` 가능 → **생성 방식 통제 불가**
>    - 팩터리 + 생성자 private → **생성 경로 강제 (단 하나로 고정)**
>- 추가 차이 (중요)
>    1. **이름으로 의도 표현 가능**
>        - `new Member(...)` → 의미 없음
>        - `Member.signUp(...)` → 가입 상황 명확
>    2. **생성 방식 확장 가능**
>        - 캐싱, 다른 객체 반환, 조건 분기 가능
>        - 생성자는 무조건 자기 자신만 생성
>    3. **생성 정책 변경 대응**
>        - 팩터리 내부만 수정하면 됨
>        - 생성자 직접 쓰면 전부 수정해야 함

#### 저장할 때
```java
@Override  
public Reservation save(Reservation reservation) {  
    KeyHolder keyHolder = new GeneratedKeyHolder();  
  
    jdbcTemplate.update(connection -> {  
        PreparedStatement ps = connection.prepareStatement(  
                "INSERT INTO reservation (name, date, time) VALUES (?, ?, ?)",  
                Statement.RETURN_GENERATED_KEYS  
        );  
  
        ps.setString(1, reservation.getName());  
        ps.setString(2, reservation.getDate().toString());  
        ps.setString(3, reservation.getTime().toString());  
  
        return ps;  
    }, keyHolder);  
  
    Number key = keyHolder.getKey();  
    if (key == null) {  
        throw new IllegalStateException("ID 생성 실패");  
    }  
  
    Long id = key.longValue();  
  
    return Reservation.of(  
            id,  
            reservation.getName(),  
            reservation.getDate(),  
            reservation.getTime()  
    );  
}
```
>동작 방식에 대한 궁금증 Key가 어떻게 들어감?
>KeyHolder는 DB가 생성한 auto-increment PK를 JDBC가 받아서 담아주는 컨테이너임.
>
>동장 원리
>- `Statement.RETURN_GENERATED_KEYS`  
    → 이 옵션이 있어야 DB가 생성한 키를 JDBC에게 반환함
>- `PreparedStatement` 실행 흐름  
    → INSERT 실행 → DB가 PK 생성 → JDBC Driver가 생성된 키를 ResultSet 형태로 받음
>- `KeyHolder` 역할  
    → JDBC가 받은 “생성된 키 ResultSet”을 내부에 저장  
    → `keyHolder.getKey()`로 꺼낼 수 있음
>- 중요한 포인트  
    → Key는 **JdbcTemplate이 넣는 게 아니라 JDBC Driver가 넣고, KeyHolder는 그걸 담는 그릇**
```
1. INSERT 실행 (RETURN_GENERATED_KEYS 옵션 포함)
2. DB: PK 생성 (예: 1)
3. JDBC Driver: 생성된 키를 ResultSet으로 받음
4. JdbcTemplate: 이 값을 KeyHolder에 복사
5. keyHolder.getKey() → 1 반환
```

#### Optional을 넣는 이유
```java
package roomescape.domain.reservations.infrastructure;  
  
import java.util.List;  
import java.util.Optional;  
import roomescape.domain.reservations.entity.Reservation;  
  
public interface ReservationRepository {  
    Reservation save(Reservation reservation);  
    Optional<Reservation> findById(Long id);  
    List<Reservation> findAll();  
    void deleteById(Long id);  
}
```
> Optional을 넣는 이유
> 값이 없을 수 있음(null 가능)을 명시해서 호출자에게 처리 가제하는 타입임.

![[Pasted image 20260429134953.png|712]]

> 컨트롤러가 객체를 직접 생성하면 왜 DI가 꺠지지?
> 객체 생성과 의존성 연결을 스프링 컨테이너가 대신 해주는 것이기 때문임.
> 스프링이 넣어줘야 할 객체를 네가 `new`로 만들면, 스프링의 주입 과정 밖에서 생성되기 때문에 DI가 깨진다.
> 
> 필드에 선언만 한다고 주입되는 게 아님. 생성자 파라미터로 받아야 스프링이 넣어준다.
> 
> 그러면 레포지토리에 @Repository 를 선언 함으로써 어떻게 되는거지?
> → `@Repository` 붙이면 스프링이 그 클래스를 **Bean으로 등록하고 DI 대상**으로 만든다.
```
1. 스프링 실행
2. @Repository 발견
3. 객체 생성
4. 컨테이너에 등록
5. Controller에서 요청 시 주입
```

#### SimpleJdbcInsert 이건 뭐지?
 `SimpleJdbcInsert` 는 테이블에 쉽게(batch) 삽입할 수 있는 다중 threaded 재사용 가능한 객체입니다. 기본 삽입문을 구성하는 데 필요한 코드를 간소화하기 위해 메타 데이터 처리를 제공합니다. 테이블 이름과 a만 제공하면 됩니다 `Map` 열 이름과 열 값을 포함합니다.

메타 데이터 처리는 다음을 기반으로 합니다 `DatabaseMetaData` JDBC 드라이버 제공. JDBC 드라이버가 지정된 테이블의 열 이름을 제공할 수 있는 한, 이 자동 감지 기능에 의존할 수 있습니다. 그렇지 않은 경우 열 이름을 명시적으로 지정해야 합니다.

`SimpleJdbcInsert`는

- **테이블명 + 컬럼만 알면 INSERT SQL 자동 생성**
- **Generated Key 자동 처리 (내부에서 KeyHolder 사용)**  
    → 즉, “INSERT boilerplate 제거”

컨트롤러에서 DI를 하는걸 개발자가 하면 안되는 건가?
DI는 직접 하는 게 아니라 선언만 하는 것

DI = 의존 객체를 외부에서 주입하는 것임.

왜 오류까지 내보내는 것일까?
스프링이 관리 못하는 객체를 주입하려 해서

답변 이해가 안됨
컨테이너에 없는 객체를 달라고 해서 그럼

근데 DI 에서 컨테이너에 없는 객체를 달라고 하는 거잖아 다른 컨테이너에서는 만들어진거 아님??
- 스프링 DI는 **하나의 컨테이너 기준**이라, 그 컨테이너에 없으면 “없는 것”으로 판단해서 바로 에러
  
아아 스프링이 처음 생성될 때 Bean으로 등록하면 싱글톤으로 생성되서 열린 객체가 한번만 열리고 재사용하려고 그런건가?
- 맞는 방향이지만, 핵심은 “싱글톤 재사용”이 아니라 **객체 생성·의존성·공통 기능을 스프링이 통제하려는 것**

#### Bean?이 컨테이너에 등록되고 쓰는 그런거 모르겠음
- Bean은 “스프링이 대신 생성·관리하는 객체”, 컨테이너는 “그 객체를 보관하고 꺼내주는 저장소”

#### 메서드를 사용할 때 마다 객체를 생성하는게 뭐가 문제인거지?
- 매번 객체 생성은 "비용 + 상태 일관성 + 공통 기능 적용" 문제를 야기함

객체 생성은 비용이 있음 (메모리 할당 + GC 대상 증가) -> 추후에 공부 할 내용 (저 2개는 왜 비용이 드는지?)
매번 다른 객체가 생기면 상태가 공유가 되지 않음, 캐시, 설정, 연결 정보 유지가 불가능함.
스프링 기능 적용 불가능 함.

#### 도메인을 @Component로 등록하면 어떻게 될까?
- Domain/Entity는 **상태 데이터 객체라서 공유하면 안 되기 때문에 Bean으로 등록하지 않는다**
#### sql 문 2개 이상 작동되는 메서드에 대한 트랜잭션 적용법
스프링 탄생배경을 공부하고 자연스럽게 AOP를 공부하다보니 트랜잭션도 대표적인 예시라고 들었다, 그래서 내 코드에 sql문 2개 이상 사용하는 로직이 있다보니 트랜잭션의 도입을 하려고 했는데, 이전에 트랜잭션을 관리하기 위해서 트랜잭션 매니저라는 객체를 생성해서 직접 관리를 했어야 했지만, @Transactional 이라는 어노테이션으로 진행할 수 있었다.
- `@Transactional = 트랜잭션 로직을 AOP로 "자동 삽입"하는 설정`
