# 학습 로그

## v1 — 전체 이해 후 시작

### 방식

1. 전체 개념 다 훑어본다
2. 진행하다 궁금한 점 생기면 딥다이브한다 (동작방식의 파악)


### 핵심 학습 패턴

> 꼬리질문 방식

- 특정 개념이 나오면 꼬리질문을 계속 만들며 깊게 파고든다
  - `@Component` → Bean이 뭔지 → DI가 뭔지 → 왜 생성자 주입이 권장되는지
- 동작 원리 이해를 할 수 있어 이후에 에러가 발생했을 때 어느정도 미리 원인을 예측할 수 있다

### 발견한 문제 2가지

1. **학습이 더디다**
   - 연결된 개념이 계속 나와 처음 목적에서 멀어진다
   - 결론적으로 시간 내에 학습 목표를 이루지 못한다

2. **정작 중요한 부분을 놓치기 쉽다**
   - 꼬리를 따라가다 보면 동작 원리는 이해되지만 지금 당장 필요한 것과 나중에 알아도 되는 것의 구분이 흐려진다
   - 정신 차려보면 정작 학습해야 했던 부분이 부족하고 지엽적인 부분을 많이 학습하게 됨
   - `@ExceptionHandler` 문서 읽으려다 생뚱 맞은 JSON 직렬화 동작 방식을 공부하고 있다

## v2 — PiFSR (효율 개선)

### 방식

> Problem-Driven + i+1 + Feedback Loop + Structural Thinking + Resourceful

LMS+에서 추천한 방식 그대로 준수해본다

### 적용 결과
- 학습법 자체에 대한 메타인지가 생긴다
- [스프링 학습 테스트](https://github.com/cho-log/spring-learning-test)를 빠르게 학습하여 "스프링 부트 기능을 익힌다"는 목표를 효율적으로 달성했다
- 학습하다 중간에 `ExceptionHandler`, `Static Resources` 등 지금 당장 필요 없는 문서를 확인하려는 v1 습관이 튀어나오기도 했다

### 이번 주 의식할 원칙

> **Problem-Driven**
> 
> 지금 당장 부딪힌 문제가 아니면 넘어가기

## v3 — PiFSR + 딥다이브 큐 (현재 적용 중)

### 방식

> PiFSR 베이스 + 동작 방식이 궁금할 때 실제 문제가 아니면 옵시디언에 주제만 기록해두고 미션 마무리 후 딥다이브

### 핵심 변경점

- v2와 동일하게 PiFSR 원칙 유지한다
- 꼬리질문 충동이 올라올 때 바로 딥다이브 하지않고 옵시디언에 주제만 기록한다
- 미션 완료 후 혹은 PR 제출 후 시간이 남을 때 기록한 주제를 모아서 딥다이브한다

### 기대 효과

- 꼬리질문의 장점인 동작 원리 이해를 위해 공부하면서 미션 진행의 흐름을 끊지 않는다
- 나중에 알아도 되는 것과 지금 필요한 것을 명확히 분리한다
