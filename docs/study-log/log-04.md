### 2. 이번 타임의 학습 전략

구현을 하는 과정에서 변경 사항이 생기는 경우에 기존 코드 흐름 추적한 뒤에 구현을 시작하자.
이 과정에서 따로 아키텍처를 그리거나 문서화시키거나 하는 방식으로 머리속에 구조화를 해보도록 한다.

또한 기존의 디버깅 로그들 작성에 관한 부분은 다 삭제하고, 따로 AI한테 물어볼 때 가설을 세우고 이에 대해서만 평가를 받아보도록 한다.

### 3. 전략 평가

구현을 하기 전 각 객체들 그리고 흐름이 어떻게 지나가는지를 먼저 판단해보고 이해한 뒤 코드를 작성하였기 때문에,
더 쉽게 이해가 되고 속도가 붙어서 구현이 가능했다.

다만, 계층 분리와 추상화 영역에 대해서는 개인이 트레이드오프를 고려해야하는 문제라고 생각한다.
이러한 지점에서 트레이드오프를 어떻게 고려하면 되는지 살짝 막연했다.

### 4. AI 피드백

```
계층 분리와 추상화는 “예쁘게 나누는 것”이 아니라,
변경 이유가 다른 것들을 서로 덜 흔들리게 두는 장치다.

요구사항/정책 판단이면 Service 쪽
HTTP 요청/응답 모양이면 Controller/DTO 쪽
DB 접근 방식이면 Repository 쪽
지금 변형이 1개뿐이고 중복도 적으면 추상화하지 않기
변형 가능성이 실제로 보이거나 중복이 생기면 그때 추상화하기

각각의 무언가를 도입할 때 그것을 도입함으로서 얻을 수 있는 이점과 단점을 분리하여 생각한다.
그리고 장점이 단점보다 크다고 생각한다면 이를 도입한다.
```

### 5. 다음 타임에 바꿀 것

무언가를 도입하는 경우에 장점/단점을 분리해서 하나씩 말해본 뒤 장점이 단점보다 크다고 생각하면 이를 도입한다.
이 과정에서 크루들과 토론을 하는 방향이나 AI와 토론하는 방향으로 진행한다.
