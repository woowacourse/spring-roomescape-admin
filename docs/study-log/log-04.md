### 2. 이번 타임의 학습 전략

- 이전에 바꾸기로 한 전략은 무엇이었고, 실행했는가?
    - **새 룰 1: "공식문서 펼치기 전 AI에게 위치를 먼저 묻기"**
        - 이번 단계는 코드 막힘이 거의 없어 적용할 자리가 적었다.
    - **새 룰 2: "미션 문서를 받을 때 *학습 유도 장치*를 미리 찾아 읽기"**
        - 미션 문서 끝의 *"(선택) 콘솔 UI"* 가 단순한 추가 과제가 아니라 *"계층 분리가 실제로 다른 UI에 재사용 가능한 구조를 만들었는지 검증"* 이라고 명시되어 있는 걸 *처음부터 인지하고 들어갔다*. 결과적으로 콘솔 UI를 *판단 마일스톤의 외부 검증 도구* 로 위치 지을 수 있었다 - 이전 같았으면 *"시간 남으면 해보는 부가 과제"* 정도로 가볍게 받아들였을 것이며, 마감 직전 같은 압박에서 그저 나의 의식과 인식 없이 놓아주며 학습과 성장 포인트를 놓쳤을 것 같다.
- 실제로 어떻게 학습했는지 디테일한 과정을 써보세요.

우선 주어진 테스트를 통과 시키기 위해 Repository 분리를 했고 이후 서비스 계층을 분리했다. 그 후 콘솔 UI 지원 기능을 추가해 보았다.

학습 목표와 맞는 계층별 패키지 구조를 선택하고, Controller→Repository 임시 상태를 거쳐 점진적으로 Service를 분리하면서 어색한 시그니처와 중복 인자를 자연스럽게 해소했고, ReservationTimeService의 필요성, Domain 계층 책임의 어색함 인지, DTO 누수 같은 설계 신호들을 발견해 기록하며 판단력을 다듬었고, 마지막에는 5개의 계층과 관련된 자기 점검 질문에 모두 답한 뒤 Spring 컨테이너 없이 메모리 저장소를 직접 주입한 콘솔 UI를 조립해 기존 Service, Controller 수정 없이 정상 동작시키며 계층 분리가 실제로 작동함을 직접 경험했다.

### 3. 전략 평가

- 효과적이었던 것과 그 이유
    - 지금 당장 필요한 것과 나중에 깊게 볼 것을 구분하는 전략이 이번에도 효과적이었다. 4단계역시 호기심이 뻗을 만한 자리(어노테이션 동작 원리, DI 컨테이너,  트랜잭션 등)가 많았는데, *지금 미션이 요구하는 것* 으로 좁힐 수 있었다. 현재의 나에게 아주 효과가 좋다고 생각한다.
    - **콘솔 UI를 외부 검증 도구로 위치 지은 결정**.
        - 4단계의 “잘 분리됐는가”를 실제 코드에서 import를 하고 있는지 확인하며 의존성을 확인하는 것을 넘어, 콘솔 UI가 서비스, 컨트롤러, 레포지토리 계층의 코드를 안고치고 동작하는것을 통해 분리가 잘 되었지만 완벽하지 않은 부분도 인지할 수 있었다.
- 비효과적이었던 것과 그 이유
    - **새 룰 1: "공식문서 펼치기 전 AI에게 위치를 먼저 묻기"**
        - `@Repository`, `@Service` 어노테이션의 정확한 역할 같은 자잘한 검증에서는 같은 흐름(맥락 → AI → 위치 안내 → 공식문서 검증)이 비효율적인 것을 확실히 느꼈다. 마지막 공식문서 검증의 경우는 AI와 검색을 통해 진행을 하다가 충돌이 발생한 경우에 사용하도록 하는게 좋을 것 같다.
- 막힌 것의 종류(1번)와 전략의 궁합은 어땠는가?
    - 역시 최종적으로 궁합이 아주 좋았다.  기존의 학습법이었으면 여러 개념과 동작원리들을 학습하기 위해 하루를 날리고 그럼에도 불안감과 찜찜함이 남은 채로 남은 미션을 진행을 했었을 것이다. 하지만 현재 당장에 필요한것과 앞으로 더 알면 좋을것을 명확하게 인지하고 정리를 하니, 찜찜함없이 미션을 진행할 수있었다. 그로 인해 찜찜함 없이 미션에서 배울 부분은 잘 배우고 앞으로 더 배워야할 부분에 대해서는 명확히 정리가 동시에 되니 처음 계획한 나선형 학습 계획이 잘 이루어 질수 있도록 된것 같다.

  유용했던 제안 1가지 이상 기록
