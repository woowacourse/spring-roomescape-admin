### 1. 막힌 것의 종류

이번에 막힌 것은 어떤 종류의 어려움이었는가? (해당하는 것에 체크)

- [ ] 개념 자체를 모르겠다 (예: "스프링 빈이 뭔지 모르겠다")
- [ ] 개념은 알겠는데 코드로 어떻게 쓰는지 모르겠다 (예: "JdbcTemplate 문법을 모르겠다")
- [ ] 코드는 돌아가는데 이게 맞는 건지 모르겠다 (예: "계층 분리를 이렇게 해도 되나?")
- [x] 기타: 기존의 코드와 충돌되는 지점에서 이를 제대로 동작하기 위해서 다양한 의존 코드들을 수정하는 과정에서 큰 어려움이 있었다.

### 2. 이번 타임의 학습 전략

공식문서를 기반으로 AI 없이 학습해보며, 학습 과정에서 AI를 판단의 기준을 평가받는 리뷰어로 사용한다

이에 더해서 아래의 디버깅 방법을 추가한다.
문제가 발생하면 AI에게 바로 해결책을 요청하지 않고, 먼저 디버깅 스냅샷을 작성한다.

- 기대한 동작
- 실제 동작
- 현재 가설
- 확인할 가장 작은 실험

AI에게는 정답 코드가 아니라 내 가설의 타당성과 다음 관찰 포인트를 요청한다.

### 3. 전략 평가

- 효과적인 것은 따로 AI를 기반이 아니라 직접 코드를 작성한 뒤 이런이런 선택들이 있고 이에 대해서 AI한테 피드백을 받을 수 있어 좋았다.
- 디버깅 하는 과정에 대해서는 따로 큰 도움이 되지 않았으며, 실제 디버깅하는데에 큰 도움이 되지 않았다. 따로 기록을 하는 방식에 대해서는 기록을 하는 것에 더 많은 공수를 들이게 되어 비효율적이었다.
- 따로 기존의 코드를 요구사항에 맞게끔 Reservation의 ReservationTime을 구축하는 과정에서 도움이 많이 되지 못했다. 즉, 수정사항이 발생하는 경우에 효과적인 학습방법이 아니라고 생각한다.

### 4. AI 피드백

```
코드를 바로 고치기 전에 5분 정도만 다음 흐름을 머릿속으로 따라가세요.

이 값은 어디서 들어오는가?
어떤 객체가 이 값을 책임지는가?
DB에는 어떤 형태로 저장되는가?
조회할 때 다시 어떤 형태로 복원되는가?
테스트나 API 응답에서 어떤 형태를 기대하는가?

예를 들어 Reservation에 ReservationTime을 붙이는 작업이라면, “Reservation이 timeId만 알면 되는가, ReservationTime 객체를 직접 가져야 하는가, 
응답에서는 어떤 형태로 나가야 하는가”를 먼저 정합니다. 그다음 Controller, Service, Repository, Domain, DTO, Test를 하나의 흐름으로 봅니다.

기존 코드 흐름 추적 -> 변경될 계약 하나 정하기 -> 직접 구현 -> AI에게 계약/영향 범위 리뷰 요청
```

### 5. 다음 타임에 바꿀 것

구현을 하는 과정에서 변경 사항이 생기는 경우에 기존 코드 흐름 추적한 뒤에 구현을 시작하자.
이 과정에서 따로 아키텍처를 그리거나 문서화시키거나 하는 방식으로 머리속에 구조화를 해보도록 한다.

또한 기존의 디버깅 로그들 작성에 관한 부분은 다 삭제하고, 따로 AI한테 물어볼 때 가설을 세우고 이에 대해서만 평가를 받아보도록 한다.

### 단계 전환 체크

- 이번 단계에서는 직접 디버깅에 관련해서 가설 -> 평가를 반복한다.
- 수정사항이 발생하는 경우에는 아키텍처를 그려보거나, 흐름을 구조화시킨 뒤 구현에 들어가자.
