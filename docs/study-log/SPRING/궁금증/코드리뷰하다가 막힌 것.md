#### IlegalArgumentException을 던지면 Spring이 그대로 500으로 내보내서 클라이언트 입장에서는 자신의 요청이 잘못됐는지 서버가 죽은 건지 알 수 없어요. 어떻게 개선해볼 수 있을까요?
자바 프로그램에서 예외 즉 IlegalArgumentException 같은 RuntimeException을 스프링에서 처리하지 않고 내보내면 무조건 HTTP로 답을 보낼 때 500 Error를 보내는건가?
-> 스프링이 끝까지 처리 못한 예외는 기본적으로 500으로 응답함.

내가 디스패처서블릿을 배웠잖여, 보통 메서드마다 AOP를 적용시키면 AOP가 실행되는거고 IlegalArgumentException이 터졌을 때 에러를 핸들링하지 않으면 즉 AOP로 에러를 잡아서 처리하지 않고 보내면 http status code를 기본 값으로 500을 디스패처서블릿으로 보내는거고, 만약 내가 처리를 진행했으면 각각 맞은 status code를 내비치는건가?
-> HTTP 상태코드는 AOP가 아니라 “예외 처리기(HandlerExceptionResolver)”가 결정하고, 처리 안 되면 기본 500이다
-  **AOP는 부가기능(로깅, 트랜잭션), HTTP 응답 결정 주체 아님**
흐름:
```markdown
Controller
  ↓ (AOP 지나감)
Exception 발생
  ↓
DispatcherServlet
  ↓
HandlerExceptionResolver
  ↓
없음 → 500
있음 → 지정한 status (예: 400)
```

aop랑 HandlerExceptionResolver 다른 개념인거임?
-> AOP는 “공통 로직 삽입”, HandlerExceptionResolver는 “예외 → HTTP 응답 변환”으로 완전히 역할이 다르다
```markdown
개념 정리 (헷갈리는 부분 중심)
- AOP
    - 대상: **메서드 실행 전/후/예외 시점**
    - 목적: 로깅, 트랜잭션, 권한 등 **공통 관심사 처리**
    - HTTP 개념 없음 (상태코드 모름)
- HandlerExceptionResolver
    - 대상: **컨트롤러에서 발생한 예외**
    - 목적: **예외를 HTTP 응답으로 변환 (status, body)**
    - 예: `@ExceptionHandler`, `@ControllerAdvice`, `@ResponseStatus`
```

aop로 http 헤더를 못바꾸는건가?
-> AOP에서도 HTTP 헤더 변경 가능하지만, 권장 위치는 아니다 (컨트롤러/필터/인터셉터/예외처리기가 책임)

왜 쓰면 안되는건지 잘 이해가 안됨
-> **AOP로 헤더를 바꾸면 “계층 책임이 깨지고, 흐름이 숨겨져 유지보수가 어려워진다”**

아 AOP는 서비스 레벨이고, 예외처리 핸들러는 Controller의 역할은 헤더랑 바디를 조합하니까 컨트롤러에서 하는건가?
-> **AOP는 계층이 아니라 “횡단 관심사”, 예외 처리기는 “웹 계층에서 HTTP 응답 생성” 역할이다**

```markdown
개념 정리 (헷갈리는 부분 중심)
- 잘못 이해한 부분 교정  
    ❌ “AOP는 서비스 레벨이다” → 아님  
    👉 **AOP는 모든 계층에 걸쳐 적용 가능 (Controller/Service/Repository 전부)**
- AOP 역할
    - 목적: **공통 기능 삽입 (로깅, 트랜잭션 등)**
    - 특징: **비즈니스/HTTP 둘 다 직접 책임지지 않음**
- 예외 처리 핸들러 역할
    - 대상: **컨트롤러에서 올라온 예외**
    - 역할: **HTTP 응답으로 변환 (status + header + body)**
    - 위치: 웹 계층 (Controller 주변)
```

```markdown
[Client]
  ↓ HTTP 요청

[Spring Server]
  ↓
DispatcherServlet
  ↓
Controller        ← (AOP before)
  ↓
Service           ← (AOP before)
  ↓
비즈니스 로직 수행 중 예외 발생 (IllegalArgumentException)
  ↓
Service → Controller로 예외 전파 ← (AOP afterThrowing)
  ↓
DispatcherServlet
  ↓
HandlerExceptionResolver
  ↓
예외 매핑

    ├─ @ExceptionHandler 존재
    │     → status: 400
    │     → body: 에러 메시지
    │
    ├─ @ResponseStatus 붙은 예외
    │     → 해당 status
    │
    └─ 아무 처리 없음
          → status: 500

  ↓
HTTP Response 생성 (status + header + body)
  ↓ 응답 수신
[Client]
```

Controller로 예외 전파하고 나서 헤더랑 바디를 조합해서 디스패처 서블릿으로 전파하잖아, 그러면 이제 조합된걸 디스패처 서블릿에서 핸들러예외리졸버로 넘겨서 화긴하고 클라이언트로 주는건가?
-> Controller에서 응답을 조합하는 게 아니라, 예외는 DispatcherServlet → HandlerExceptionResolver에서 HTTP 응답으로 변환된다
```markdown
Controller
  ↓
throw IllegalArgumentException
  ↓
DispatcherServlet (예외 받음)
  ↓
HandlerExceptionResolver
  ↓
(@ExceptionHandler 실행)
  ↓
ResponseEntity 생성 (status + header + body)
  ↓
DispatcherServlet
  ↓
HttpMessageConverter
  ↓
Client 응답
```

디스패처서블릿은 throw IllegalArgumentException 이걸 응답 받는거면 처음엔 500이라고 이해하는거 아님?
-> DispatcherServlet은 처음부터 500으로 판단하지 않고, 예외 처리기를 다 돌려본 뒤 못 처리하면 그때 500이다

약간 HandlerExceptionResolver가 디스패처서블릿의 AOP 느낌인건가? 느낌상
-> 느낌은 비슷하지만, HandlerExceptionResolver는 AOP가 아니라 “예외 전용 처리 전략 체인”이다

그러면 예외 핸들링을 어디서 해야함? 컨트롤러에서 하는건가? 근데 컨트롤러에서는 IllegalArgumentException을 넘기는거잖아
-> 컨트롤러에서 직접 처리하지 말고, 전역 예외 처리기(`@RestControllerAdvice`)에서 처리하는 게 정석이다
```markdown
Controller → throw
  ↓
DispatcherServlet
  ↓
HandlerExceptionResolver
  ↓
@RestControllerAdvice 실행
  ↓
HTTP Response (400)
```

근데 안에 IllegalArgumentException이거 메세지를 받아서 처리를 하지만 저렇게 되면 status가 고정 아니야?
-> 맞음. `IllegalArgumentException` 하나에 `400`으로 매핑하면 status는 고정된다.

근데 RestControllerAdvice는 전역에서 하는거라며, Controller가 많아 질수록 IllegalArgument를 반환하는게 많아지면 처리하기 어려워지잖아
-> 맞음. 그래서 `IllegalArgumentException` 하나로 다 처리하지 말고 **의미 있는 커스텀 예외로 나눠야 한다.**

근데 커스텀 예외를 여러개 만드는 것은 도메인이 늘어날 때마다 엄청 많아질 것 같은데 한 곳에서 하는게 더 나아보일 것 같은데 아닌가? 아니면 도메인별로 나누는게 맞는건가?
-> 트레이드 오프임.

답변: 
`IllegalArgumentException` 같은 `RuntimeException`을 별도 처리 없이 던지면 Spring이 끝까지 처리하지 못했을 때 기본적으로 500 응답을 내려줍니다. 그러면 클라이언트 입장에서는 요청 값이 잘못된 건지, 서버 내부 오류인지 구분하기 어렵습니다.

그래서 예외를 HTTP 응답으로 변환하는 전역 예외 처리기를 두는 방식으로 개선할 수 있습니다.

다만 `IllegalArgumentException` 하나로 모든 예외를 처리하면 상태 코드가 `400 Bad Request`로 고정됩니다. 
컨트롤러가 많아지고 예외 상황이 다양해지면 어떤 에러인지 구분하기 어려워질 수 있습니다.

그래서 더 개선한다면 `ErrorCode`와 커스텀 예외를 만들어서 예외마다 적절한 상태 코드와 메시지를 가지도록 할 수 있습니다.

즉, 처음에는 `IllegalArgumentException`을 `400 Bad Request`로 매핑해서 클라이언트 요청 오류임을 명확히 알 수 있게 만들고, 이후에는 커스텀 예외와 `ErrorCode`를 사용해서 예외 상황별로 응답을 더 명확하게 나누는 방식으로 개선할 수 있습니다.
