# 학습법 변천 기록

## v1 - 직관 기반 학습

막히면 페어와 각자 생각하는 시간을 갖고, 생각을 공유한 뒤 방향이 안 나오면 구글링 -> AI 질문 순서로 해결했다. AI 답변이 나와도 검증 과정은 거쳤다.

**설계에 대한 깨달음**

- 블랙잭: 설계를 대략적으로 하고 바로 구현 -> 빠르게 완료
- 장기: 설계에 오랜 시간 투자 -> 오래 걸렸고, 결국 페어의 설계를 따름

일정 수준 이상의 요구사항은 머릿속에서 잘 그려지지 않는다. 당연한 문제부터 설계·구현을 시작해 하나씩 제거해나가며, 구현 과정에서 마주치는 문제를 시각적으로 직면했을 때 해결하는 방식이 훨씬 효율적이었다.

> 스프링 프레임워크 경험은 어느 정도 있어 큰 막막함은 없지만, 이 과정을 마치고 내가 얻어가는 게 있을까에 대한 두려움이 있다.

## v2 - 구조화된 문제 해결 프로세스

v1의 흐름을 단계별로 명확히 정리했다.

1. **막힘** -> 문제를 한 문장으로 정의한다 ("뭐가 안 되는지"를 글로 적는다)
2. **혼자 생각하는 시간** - 최소한 아는 것 / 모르는 것을 분리한다
3. **구글링** - 공유 후에도 "모르는 것"이 남아있을 때
4. **AI 질문** - 구글링으로 3~5분 내에 방향이 안 잡힐 때
5. **AI 검증** - 답이 나왔더라도 "왜 이게 맞는지" 근거를 확인

## v3 - 인지 과학 기반 학습 (금요일 코칭 반영)

v2에 코칭에서 받은 아이디어를 적용하여 8단계로 확장했다.

### 1단계: 실제 문제에서 출발

학습 주제를 추상적 개념이 아닌 실제 문제에서 시작한다.

### 2단계: 문제를 한 문장으로 정의

막히는 순간, "뭐가 안 되는지"를 한 문장으로 적는다.

### 3단계: 아는 것 / 모르는 것 분리 + 범위 제한

기존처럼 분리하되, 이번 세션에서 연결할 요소를 **최대 2개로 제한**한다.

> 예) "이번 20분은 'DispatcherServlet -> ExceptionResolver' 연결 하나만 확실히 만든다."

세 가지 이상이 동시에 떠올라야 설명이 되면, 범위를 더 좁혀야 한다는 신호다. 작업 기억의 용량(3~5개)을 초과하면 뇌는 정의만 기억하고 관계를 버리는 단순화 전략을 취한다.

### 4단계: 혼자 생각하는 시간 (브라우저 차단)

10분 안에서 **실행 시뮬레이션**을 수행한다. 구체적 시나리오 하나를 정해 입력부터 출력까지 단계별로 무슨 일이 일어나는지 손으로 적는다. 적다가 막히는 지점이 진짜 모르는 것이며, 이후 구글링·AI 질문의 정확한 타겟이 된다.
